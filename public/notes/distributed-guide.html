01What "distributed" actually means

A distributed system is a set of independent machines that coordinate over a network to look, to the user, like one system. You go distributed for three reasons: scale (more than one box can handle), availability (survive a machine dying), and locality (be close to users). The price is that everything hard about computing — failure, time, ordering, consistency — gets multiplied.

partial
failure: some nodes fail while others run — there is no single "it's up or down"
no clock
no shared global time; you can't trust "when" two events happened across nodes
async
messages can be delayed, reordered, duplicated, or lost

Distributed vs microservices — not the same axis

"Distributed" is about physical deployment (work split across machines). "Microservices" is a software architecture (one app split into small, independently deployable services by business capability). Microservices are one way to build a distributed system, but you can be distributed without microservices (e.g. a sharded database) and "micro" in spirit without true distribution (a modular monolith).

A distributed system is a restaurant kitchen with many cooks: faster and more resilient than one chef, but now they must coordinate — orders get lost, two cooks grab the same pan, nobody agrees what time it is. Every topic below is a tool for that coordination problem.
Frame the whole field around three impossibilities: you cannot avoid partial failure, you cannot share a perfect clock, and (per CAP) you cannot have consistency and availability during a partition. Distributed systems are the engineering of good-enough answers to those three.

02CAP theorem

For a single piece of data replicated across nodes, you can have at most two of: Consistency (every read sees the latest write), Availability (every request gets a non-error response), and Partition tolerance (the system keeps working when the network splits).

The most-missed point: P is not optional — in any real network, partitions happen. So CAP is really a binary choice during a partition: CP (sacrifice availability — reject requests rather than serve stale) or AP (sacrifice consistency — stay up, reconcile later). "CA" only exists in a single node that never partitions.

ChoiceMeansExamples
CPConsistency over availability; minority side stops servingZooKeeper, etcd, HBase, (Redis Cluster leans here for the majority)
APAvailability over consistency; serve, reconcile laterCassandra, DynamoDB, Eureka, DNS
Two bank tellers lose their phone line (partition). CP: both refuse withdrawals until the line is back — no wrong balances, but customers wait. AP: both keep serving from their last-known balance — nobody waits, but the accounts can disagree until they sync.
Never say "my system is CA." Say: "partitions are a given, so I chose CP here (e.g. config/locks must be correct) or AP there (e.g. a product catalog must stay up). CAP is a per-feature decision, not a whole-system label."

03BASE & consistency models

BASE is the AP-side philosophy, the opposite of database ACID: Basically Available, Soft state, Eventual consistency. You give up "always correct right now" for "always answers, and converges to correct."

Basically Available

The system stays responsive under failure — maybe degraded (slower, partial), but not down.

Soft state

State may be in-flight / inconsistent between nodes for a while, even with no new writes.

Eventual consistency

Stop writing and, given time, all replicas converge to the same value.

The consistency spectrum

ModelGuaranteeTrade-off
Strong / linearizableEvery read sees the latest write, as if one copySlow, needs consensus, blocks on partition (CP)
Read-your-writesYou always see your own latest writeSession stickiness or read-from-master
EventualConverges "later", reads may be stale meanwhileCheap, fast, available (AP)
ACID vs BASE is the same trade-off as CP vs AP, one layer up: pick ACID/CP when wrong data is unacceptable (money, locks), BASE/AP when uptime matters more and a brief staleness is fine (feeds, catalogs, counters).

04Consensus — getting nodes to agree

How do multiple nodes agree on one value (or one ordered log of operations) even as some crash? That's the consensus problem, and it underlies leader election, replicated state machines, and coordination services. All practical algorithms need a majority (quorum) to make progress — which is why clusters use an odd number of nodes.

Raft — the one to know cold

In one line: a single leader takes every write and drives replication; heartbeats + majority voting elect that leader.

Raft splits consensus into leader election and log replication. Time is divided into terms (a logical clock); each term has at most one leader, and every node is a Follower, Candidate, or Leader.

start a new term| C["Candidate"]:::s C -->|wins majority of votes| L["Leader"]:::l C -->|sees a higher term| F L -->|discovers higher term| F L -.->|heartbeats keep
followers as followers| F classDef s fill:#e7ecfb,stroke:#5b54c7,color:#2a2470; classDef l fill:#fde6e4,stroke:#dc382d,color:#7a1810;

Leader election

  1. Followers expect periodic heartbeats. Hearing nothing for its (randomized) election timeout, a follower becomes a Candidate: it increments the term, votes for itself, and sends RequestVote to everyone else.
  2. It becomes Leader on a majority of votes. Each node grants at most one vote per term, and only to a candidate whose log is at least as up-to-date as its own — this election restriction is what guarantees the new leader already holds every committed entry.
  3. Because timeouts are randomized, a split vote (nobody reaches a majority) is rare and self-heals: nodes time out at different moments, so one wins the next round.

Log replication

  1. All client writes go to the leader; it appends the entry to its log (uncommitted) and sends AppendEntries to followers — an empty AppendEntries doubles as the heartbeat.
  2. Once a majority have stored it, the leader commits it, applies it to its state machine, acks the client, and advances its commit index — which it passes to followers so they apply it too.
  3. Log matching: every AppendEntries carries the previous entry's index + term; a follower whose log doesn't line up rejects it, so the leader walks nextIndex back and re-sends until they match, overwriting any conflicting follower entries. Logs converge, and committed entries are never lost.
sequenceDiagram participant Cl as Client participant L as Leader participant F1 as Follower 1 participant F2 as Follower 2 Cl->>L: write x=5 Note over L: append to log at (term, index), uncommitted L->>F1: AppendEntries (x=5) L->>F2: AppendEntries (x=5) F1-->>L: ack F2-->>L: ack Note over L: majority stored it → committed here, leader applies to state machine L-->>Cl: ok L->>F1: AppendEntries (commitIndex advanced) L->>F2: AppendEntries (commitIndex advanced) Note over F1,F2: committed here too → followers apply to state machine

Two pointers make this work — worth picturing:

leader log  1 2 3 4 5
commitIndex = 3 — entries 1–3 are stored on a majority, so they're committed and applied (green). Entries 4–5 are replicated but not yet on a majority → still uncommitted (amber).
nextIndex[F2] = 4 — for each follower the leader tracks the next entry to send it; if that follower rejects (log mismatch), the leader decrements its nextIndex and retries until the logs line up.

Raft jargon that trips people up

TermWhat it actually means
append → commit → applyAn entry's three stages: append = written to the log, still tentative (could be lost); commit = a majority stored it → now permanent, can never be lost or changed; apply = run it against the state machine (and ack the client). Only committed entries are applied.
commitIndexThe highest committed position — every node applies its log up to here, in order.
nextIndex[follower]A per-follower cursor = the next entry the leader will send it. On a log mismatch the leader walks it backward and re-sends, so one AppendEntries both appends new entries and catches up a lagging follower — Raft needs no separate "sync" protocol (an empty AppendEntries is also the heartbeat).
"sees a higher term"Every RPC carries the sender's term. Any node — even an old, partitioned leader — that gets a higher term steps down to Follower, so a stale leader discovers it's been replaced and two leaders never both commit.
Raft is a team electing a captain by majority vote each round (term). The captain calls every play (writes), and a play only counts once most of the team has written it down. If the captain goes quiet, someone times out and calls a new election.

Paxos — the original (and notoriously hard)

Roles: Proposers propose values, Acceptors vote, Learners just learn the outcome. Basic Paxos gets a cluster to agree on one value, in two phases that each need a majority — read them as: Phase 1 = stake a claim and find out if anything's already chosen; Phase 2 = actually lock the value in. (Throughout, n is a proposal number — just an increasing sequence number that orders competing proposals, not data — and v is the value being agreed on. What gets chosen and handed to Learners is v, never n.)

  1. Prepare / Promise (phase 1 — stake a claim): the proposer picks an ever-increasing number n and sends Prepare(n). An acceptor that hasn't seen a higher number promises not to accept anything numbered lower, and reports back the highest-numbered value it has already accepted (if any). This reserves n and surfaces any value that might already be in flight.
  2. Accept / Accepted (phase 2 — lock it in): Accept(n, v) is the proposer telling acceptors "vote to accept value v under number n." The catch: v is not free — if any promise reported an already-accepted value, the proposer must reuse the highest-numbered one (only if none did may it use its own). An acceptor accepts unless it has since promised a higher n. Once a majority have accepted (n, v), v is chosen.
sequenceDiagram participant P as Proposer participant A1 as Acceptor 1 participant A2 as Acceptor 2 participant A3 as Acceptor 3 Note over P,A3: Phase 1 — Prepare / Promise P->>A1: Prepare(n) P->>A2: Prepare(n) A1-->>P: Promise(n), no value yet A2-->>P: Promise(n), no value yet Note over P,A3: Phase 2 — Accept / Accepted P->>A1: Accept(n, v) P->>A2: Accept(n, v) A1-->>P: Accepted(n, v) A2-->>P: Accepted(n, v) Note over P,A3: majority accepted, v is chosen

What "chosen" means, and what happens next: a value is chosen the moment a majority of acceptors have accepted it — and from then on it can never change. The acceptors propagate that result to the Learners, which apply it and answer clients. Why is it immutable? Because of the phase-2 rule above: any later proposer, even with a bigger number, will discover the chosen value during its Prepare phase and be forced to propose that same v — so the cluster converges on one value forever.

Multi-Paxos — from one value to a log

Real systems don't agree on a single value, they agree on an ordered log of commands — so you run one Paxos instance per log slot. Running both phases for every entry is slow and invites duelling, so Multi-Paxos elects a stable leader (a distinguished proposer): it does Phase 1 just once, then each new entry needs only Phase 2. That "one leader + an append-only replicated log" shape is essentially what Raft later repackaged in an understandable way.

The livelock trap (duelling proposers)

With two competing proposers, Basic Paxos can stall forever: P1 prepares n=1; P2 prepares n=2 (acceptors now promise 2, so P1's Accept(1,…) is rejected); P1 retries with n=3 (now P2's Accept(2,…) is rejected); they keep pre-empting each other and nobody finishes Phase 2. The fix is to stop competing — randomized back-off, or just elect a single leader (→ Multi-Paxos). That's the practical reason raw Basic Paxos is almost never used directly.

ZAB — ZooKeeper Atomic Broadcast

Leader-based, with two modes:

  • Atomic broadcast (normal running): the leader stamps each write with a monotonically increasing zxid and broadcasts it 2PC-style — PROPOSE → a majority ACK → COMMIT — giving a strict total order of writes.
  • Crash recovery: if the leader dies, elect a new one — the node with the highest zxid wins (it holds the most-committed data) — sync followers up to it, then resume broadcasting. The zxid embeds an epoch (like Raft's term), so writes from an old leader can't be mistaken for new ones.
sequenceDiagram participant Cl as Client participant L as Leader participant F1 as Follower 1 participant F2 as Follower 2 Cl->>L: write x=5 Note over L: stamp zxid, append to log, uncommitted L->>F1: PROPOSE (zxid, x=5) L->>F2: PROPOSE (zxid, x=5) F1-->>L: ACK F2-->>L: ACK Note over L: majority ACKed → committed here, leader applies to state machine (znode tree) L-->>Cl: ok L->>F1: COMMIT (zxid) L->>F2: COMMIT (zxid) Note over F1,F2: committed here too → followers apply to state machine (znode tree)

Raft vs ZAB — bottom-up (same skeleton, alike but not identical)

Build both from the bottom and they're almost the same machine; the real differences sit at just two layers. Read ① → ④:

Layer (bottom-up)RaftZAB (ZooKeeper)

So where do they actually differ? The skeleton — leader + replicated ordered log + majority-commit + apply-to-a-state-machine — is the same (yes, ZooKeeper has a state machine: the znode tree, to which committed zxids are applied in order). Only three things really differ:
  1. Raft's state machine is generic; ZAB's is hard-wired to the znode tree.
  2. After an election, Raft serves immediately and catches followers up during normal AppendEntries, while ZAB gates serving behind an explicit "recovery" phase that syncs a quorum to the new leader first — same end result (a consistent quorum), but continuous vs. an up-front step.
  3. Raft keeps the leadership term and the log index as two numbers; ZAB fuses them into one zxid.
Raft vs Paxos vs ZAB: same goal — agree on an ordered log via majority quorums. Paxos is the most general but subtle; Raft trades a little generality for understandability (etcd, Consul); ZAB is Raft-like and purpose-built for ZooKeeper's primary-backup replication. Name-drop: etcd/Consul → Raft, ZooKeeper → ZAB.

05Distributed transactions

When one logical operation spans multiple services or databases (deduct stock and charge payment and create order), you need them to all-commit or all-abort. A local DB transaction can't span machines, so you reach for one of these patterns.

2PC — two-phase commit

sequenceDiagram participant Co as Coordinator participant A as Service A participant B as Service B Co->>A: phase 1 — prepare? Co->>B: phase 1 — prepare? A-->>Co: yes, ready (locked) B-->>Co: yes, ready (locked) Note over Co: all voted yes Co->>A: phase 2 — commit Co->>B: phase 2 — commit
2PC's flaws: it's synchronous and blocking — participants hold locks while waiting for phase 2, and if the coordinator dies after "prepare" they're stuck (uncertain), not daring to unilaterally commit or abort. It also scales poorly.

3PC — three-phase commit

3PC attacks 2PC's blocking by splitting "prepare" into two steps and adding timeouts on both sides:

sequenceDiagram participant Co as Coordinator participant P as Participants Co->>P: 1. CanCommit? (cheap check, no locks) P-->>Co: yes / no Note over Co: all said yes Co->>P: 2. PreCommit (now lock and prepare) P-->>Co: ack Co->>P: 3. DoCommit P-->>Co: committed
  1. CanCommit: the coordinator asks "could you commit?" — a cheap check with no locking yet. Any "no" aborts early.
  2. PreCommit: if all said yes, everyone now locks resources and writes undo/redo, then acks. At this point every node knows the decision is "commit".
  3. DoCommit: the coordinator tells everyone to actually commit.

The win is timeouts: a participant that got PreCommit but then loses the coordinator will commit on timeout (PreCommit already meant "everyone agreed"), while one still waiting in CanCommit/PreCommit aborts on timeout — so nobody blocks forever.

But 3PC still isn't safe under a network partition: if the cluster splits after PreCommit, the reachable side commits-on-timeout while an isolated participant that missed PreCommit aborts → inconsistency. So 3PC trades 2PC's blocking for a small chance of disagreement, plus an extra round-trip of latency. In practice neither is used much — the eventual-consistency patterns below win.

The practical patterns

TCC — Try / Confirm / Cancel

Business-level 2PC: for each action you implement three methods. Try reserves resources without finalizing (freeze the balance, hold the stock). If every Try succeeds, Confirm commits using only what was reserved; if any fails, Cancel releases the reservations. Confirm/Cancel must be idempotent and handle empty-rollback (a Cancel that arrives before its Try). Strong control, but 3× the code — reserve it for high-value flows like payments.

Saga — a chain of local transactions

Split the global transaction into local steps T1…Tn, each with a compensating undo Ci. Run forward; if a step fails, run the compensations backward to unwind whatever already committed. No locks are held across services (high availability), but you must design correct, idempotent compensations.

flowchart LR T1["T1 deduct stock"]:::ok --> T2["T2 charge payment"]:::ok --> T3["T3 create order ✗"]:::bad T3 -.fails, compensate back.-> C2["C2 refund payment"]:::comp C2 -.-> C1["C1 restock"]:::comp classDef ok fill:#e4f5e9,stroke:#3aa856,color:#1d6b32; classDef bad fill:#fdeceb,stroke:#c52a20,color:#7a1810; classDef comp fill:#fbf3da,stroke:#c9a83a,color:#6b5212;

Two flavours: orchestration (a central coordinator calls each step) or choreography (each service emits an event the next one reacts to).

Local message table / transactional outbox — the everyday choice

The trick that makes "update my DB and reliably tell another service" atomic: in one local transaction, write the business change and an event row into an outbox table. A relay then polls the outbox and publishes to the MQ, retrying until acked; consumers process idempotently (dedupe by message id). The event is sent if and only if the business data committed — no lost or phantom messages.

Say it plainly: "Strong distributed transactions (2PC) are expensive and block, so in practice we use eventual consistency — Saga or a reliable message (local message table + MQ) with idempotent consumers — and reserve TCC for the few flows that truly need near-strong guarantees, like payments."

06Distributed locks

A mutex that works across machines — only one node may hold it at a time. Two common backends:

Redis

SET key token NX PX 30000 — atomic acquire + auto-expiry so a crashed holder can't deadlock. Release with a Lua check-token-then-DEL so you only free your own lock. Redlock extends it across N independent masters (debated for correctness-critical use).

ZooKeeper

Create an ephemeral sequential znode; the lowest sequence number holds the lock. Each waiter watches the node just ahead of it. Ephemeral = the lock auto-releases if the holder's session dies — no TTL guesswork.

Redis lockZooKeeper lock
StyleAP — fast, may be unsafe under failoverCP — safe, slightly slower
ExpiryTTL you must tune (+ watchdog)Session/ephemeral, automatic
Use whenEfficiency lock (avoid dup work)Correctness lock (must be exclusive)

Why "efficiency" vs "correctness"?

A Redis lock can break exclusivity two ways:

  1. TTL expiry — if the holder pauses (a GC stop-the-world, a slow disk) for longer than the TTL, the key auto-expires and a second client acquires it; now two run at once, and neither Redis nor the resource notices.
  2. Async failover — if the master grants the lock then crashes before replicating, the promoted replica has no record of it, so another client locks it too.

That's tolerable for an efficiency lock (worst case = some duplicated work), but fatal for a correctness lock (two writers = corruption).

What makes a lock "efficiency" vs "correctness"? First, the lock is a permission ("this task is mine to run right now"), never the work itself — both kinds follow the same flow acquire → do the work → release. The label is about what goes wrong if exclusivity fails and two clients hold it at once. An efficiency lock only prevents redundant work — the action is harmless (or idempotent) if it runs twice, so two holders just waste CPU: regenerating a cache, sending a daily report, processing a job a peer already grabbed. A correctness lock is one where exclusivity is the correctness — two holders produce wrong data: deducting a balance, transferring money, any non-atomic read-modify-write. "Tolerable, worst case you do it twice" only applies to the first kind; for the second, two holders = corruption.

ZooKeeper closes those holes — and a third layer guards the residual case:

  1. Session lease — the lock lives as long as the client's session (kept alive by heartbeats), not a guessed TTL, so there's no "expired while I was still working" gap to mis-tune. (Closes Redis hole ①.)
  2. Strong consistency — the lock state is agreed by a ZAB majority, so a failover never forgets who holds it. (Closes Redis hole ②.)
  3. Fencing token — the backstop — even ZK can't stop a holder that pauses past its session timeout; so each grant carries a monotonically increasing token, and the resource accepts only the highest token it has seen and rejects older ones, so a "zombie" old holder simply can't write. Detailed below.

How the ZooKeeper lock actually works

First, what a session is: when a client connects, ZooKeeper opens a session with a timeout, kept alive by the client's periodic heartbeats. Miss enough heartbeats (crash, long pause, network gone) and ZK declares the session dead and auto-deletes every ephemeral node that session created. That's the "liveness lease" — no guessed lock-TTL to mis-tune.

The lock is a queue built from ephemeral sequential znodes. Each client wanting the lock creates one child under /lock/, and ZK stamps it with an increasing number. The lowest number holds the lock. Crucially, a waiter watches only the node right before it — not the holder, not everyone:

When the holder finishes (deletes its node) or dies (session ends → node auto-deleted), only its immediate successor's watch fires; that client checks "am I the lowest now?" and, if so, takes the lock. The clients never talk to each other — they coordinate entirely through ZK's shared tree, and each watches just one neighbour, so a release wakes exactly one waiter (no stampede). That's why there's no "two holders" window: the lock belongs to exactly the lowest live node, and "live" is decided by the session, not a timer you guessed.

Which layer is this? This diagram is a lock recipe built on top of ZooKeeper — creating/deleting these znodes are writes to ZK's state machine (the znode tree), and watches are its change-notifications. It is not the ZAB consensus protocol of §04 — compare it to a Redis-lock recipe, not to Raft's internals. That's exactly why it looks nothing like the §04 consensus diagrams: a Raft diagram shows the replication layer (the state machine is an off-screen box entries get applied to), while here you're watching ZooKeeper's state machine being used directly. Same four layers underneath — the diagrams just depict different ones.

Fencing token — the truly safe fix

Even ZooKeeper can't stop a process that pauses past its session timeout: ZK frees the lock, the next client takes it, and the paused client later wakes still believing it holds the lock. The fix lives at the resource, not the lock — each grant hands out a fencing token, a number that only ever increases (ZK's znode sequence/version works). Every write carries its token, and the resource remembers the highest token it has seen and rejects anything lower:

sequenceDiagram participant C1 as Client 1 participant L as Lock service participant C2 as Client 2 participant R as Resource (DB) C1->>L: acquire lock L-->>C1: granted, token 33 Note over C1: long GC pause, session expires, lock freed C2->>L: acquire lock L-->>C2: granted, token 34 C2->>R: write (token 34) Note over R: highest token seen = 34 C1->>R: write (token 33) — woke up late R-->>C1: REJECTED, 33 is less than 34

So the "zombie" old holder is harmless — its stale token is refused. That's why the fully safe answer is "a CP lock plus a fencing token the resource enforces", not the lock alone.

The classic line (Kleppmann's Redlock critique): for an efficiency lock, single-Redis SET NX PX is fine; for a correctness lock you need a fencing token (a monotonic number the resource checks) or a CP system like ZooKeeper/etcd — because GC pauses and clock skew can let two clients believe they hold the lock.

07Distributed IDs

Once data is sharded, a single DB auto-increment no longer works — you need IDs that are globally unique, ideally roughly time-ordered (so they index well and sort by creation). Four standard approaches:

DB segment (号段)A table hands out ranges (e.g. 1–1000) to each app; serve locallyFew DB hits, ordered-ish; needs the DB available
Redis INCRAtomic counter, optionally per-prefixSimple & ordered; Redis becomes a dependency / SPOF
Snowflake64-bit: time + machine + sequence, generated locallyOrdered & no central call; needs unique machine IDs & sane clocks

Snowflake — the 64-bit layout

1 bit sign (always 0)   ·   41 bits timestamp (ms, ~69 yrs)   ·   10 bits machine id (1024 nodes)   ·   12 bits sequence (4096 / ms / node)
Snowflake's weakness is the clock: if a machine's clock jumps backwards (NTP correction), it can mint duplicate IDs. Implementations either refuse to issue until time catches up, or borrow bits — always mention clock-drift handling.
Pick by need: ordered + decentralized → Snowflake; simplest + already have a DB → segment; tiny scale → Redis INCR; only need uniqueness, not order → UUID.

09RPC — calling a remote function

RPC (Remote Procedure Call) lets you invoke a method on another service as if it were local. The framework hides the plumbing: a client stub serializes the arguments, sends them over the network, the server deserializes, runs the method, and sends the result back.

The pieces that matter: a serialization format (Protobuf, Thrift, JSON), a transport (HTTP/2 for gRPC, TCP), service discovery (find an instance), and load balancing. Examples: gRPC, Apache Dubbo, Thrift.

RPC vs REST: RPC is action-oriented ("call this method", binary, fast, strongly-typed contracts) — great for internal service-to-service calls. REST is resource-oriented (HTTP verbs on URLs, human-readable) — great for public/cross-team APIs. Also remember the fallacies of distributed computing: the network is not reliable, free, or zero-latency, so every RPC needs timeouts, retries (idempotent!), and circuit breakers.

10ZooKeeper & service discovery

ZooKeeper is a CP coordination service: a small, strongly-consistent, replicated tree of znodes (like a filesystem) that many clients share. It's the "single source of truth" other distributed systems lean on.

znode types

Persistent (stays until deleted), ephemeral (vanishes when the creator's session ends — perfect for liveness), and sequential (auto-appended counter — perfect for ordered locks/queues).

Watches

A client can watch a znode and get a one-shot notification when it changes — the basis for config updates, leader election, and lock hand-off.

What people build with it

  • Service discovery — services register as ephemeral znodes; if one dies, its node disappears and clients are notified.
  • Config management — store shared config in a znode; watchers get live updates.
  • Leader election & distributed locks — via ephemeral sequential nodes (see §06).
ZooKeeper (CP) vs Eureka (AP) for service discovery: ZooKeeper guarantees consistency but a partition can make it reject; Eureka stays available and may serve a slightly stale service list. For discovery, many argue AP is the better fit — a slightly stale list beats no list. etcd (Raft) and Consul are the modern alternatives.

11Rapid-fire cheat sheet

CAP / BASE

P is mandatory → under partition pick CP (reject, stay correct) or AP (serve, stay up). BASE = the AP philosophy: Basically Available, Soft state, Eventual consistency. Opposite of ACID.

Consensus

Agree on a replicated log via a majority quorum → odd node counts. Raft (etcd, Consul), Paxos (general, hard), ZAB (ZooKeeper).

Transactions

2PC = blocking, synchronous. Practice = Saga / local message table + MQ (eventual, idempotent), TCC for near-strong flows.

Locks

Redis SET NX PX + Lua release (AP, efficiency). ZooKeeper ephemeral-sequential (CP, correctness). Correctness → fencing token.

IDs

Ordered + decentralized → Snowflake (time+machine+seq, watch clock skew). Else segment / Redis INCR / UUID (unordered).

Rate limit

Fixed → sliding window → leaky bucket → token bucket (allows bursts). Distributed → Redis + Lua.

RPC

Stub + serialize + transport + discovery. Always: timeout, idempotent retry, circuit breaker.

13Boss-level questions EXPERT

These separate "I've used it" from "I understand it." Think first, then reveal.

Is CAP's "C" the same as ACID's "C"? MEDIUM
No — common trap. CAP's C is linearizability (every read sees the latest write across replicas). ACID's C is consistency in the sense of preserving invariants/constraints within a transaction (a write that violates a rule is rejected). Different concepts that share a letter.
You need a withdrawal to be globally exclusive across data centers. Redis lock or not? HARD
That's a correctness lock, so a single-instance Redis SET NX PX is not safe: a GC pause or clock skew can let a second client acquire the lock while the first still thinks it holds it. Options:
  1. A CP coordinator (ZooKeeper/etcd) with ephemeral nodes.
  2. A fencing token — the lock hands out a monotonically increasing number and the resource (DB) rejects any write with a stale token, so a "zombie" holder can't do damage.
Redlock alone doesn't solve the GC-pause problem.
How do you make a "reliable message" exactly-once across services? HARD
You can't get true exactly-once delivery — aim for at-least-once + idempotency. Use the local message table / transactional outbox: in one local DB transaction, write the business change and an outbox row; a relay reliably publishes outbox rows to the MQ (retrying). Consumers dedupe by a unique message id (idempotency key). Net effect = effectively-once.
Why do consensus clusters always want an odd number of nodes? WARM-UP
Progress needs a majority (quorum). With 2N+1 nodes you tolerate N failures; going from 3→4 still only tolerates 1 failure but makes the majority harder to reach and ties more likely. Odd counts maximize fault tolerance per node and avoid split votes.
A node is briefly partitioned, then rejoins. How does Raft avoid two leaders corrupting the log? MEDIUM
Each leader serves a term; a partitioned old leader can't get a majority to commit new entries, so it commits nothing. When it rejoins and sees a higher term, it steps down to follower and its uncommitted entries are overwritten by the current leader's log. Majority-commit + term numbers make stale writes impossible.
