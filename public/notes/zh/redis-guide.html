成长的故事

下面每一幕，都是团队真实会撞上的难题，以及那个一招解决它的 Redis 用法。

🔥 第 1 幕 —— 数据库要烧起来了

商品页每次访问都打到数据库。一万用户时风平浪静，到了十万，数据库 CPU 直接顶到 100%。你在前面加一层旁路缓存：先查 Redis，未命中再读数据库、把结果带上 TTL 写回。从此数据库只会看到"未命中"的那一小撮请求。

📍 对应机制：§03 String 类型 · §05 TTL 与淘汰 · §14 旁路缓存与三大失效

🧍 第 2 幕 —— 用户莫名其妙被登出

你在负载均衡器后面多加了几台应用服务器，结果用户开始随机掉登录——因为会话存在最先服务它的那台机器的内存里。把会话挪进共享的 Redis，每台机器看到的就是同一份数据；那个 TTL 还顺手充当了自动登出。

📍 对应机制：§01 同一个共享字典 · §03 用 Hash 存会话对象

🤖 第 3 幕 —— 机器人在猛刷 /login

一个 IP 每秒打来 5000 次请求。你给它设个上限：每个 IP 每分钟一次原子 INCR 加 EXPIRE；要更精确，就用 ZSet 滑动窗口。不写数据库，也没有竞态。

📍 对应机制：§06 为什么 INCR 是原子的 · §03 Sorted Set · §08 用 Lua 实现多步限流

🏆 第 4 幕 —— 运营想要实时排行榜

面向数百万用户、实时更新的前十名。一个 Sorted Set 就能以 O(log N) 按分数排名：ZINCRBY 加分，ZREVRANGE 0 9 秒读前十。排名实时更新，不用每天定时批量重算。

📍 对应机制：§03 Sorted Set · §04 内部编码让它省内存

🐌 第 5 幕 —— 结账卡顿

每笔订单都要发邮件、生成 PDF——这 3 秒不该让用户干等。请求先 LPUSH 一个任务就立刻返回；一组工作进程 BRPOP 取出来慢慢干。想要可靠投递？升级到带消费者组的 Streams。

📍 对应机制：§03 List（阻塞弹出）与 Streams

👯 第 6 幕 —— 两个工作进程发了同一笔订单

你有个定时任务——比如"每分钟扫一遍'已支付待发货'的订单去发货"——它部署在每台服务器上。到点时每台都触发了一次，于是同一笔订单被发了两遍。一把 SET NX EX 分布式锁能让整个集群里同一时刻只有一台真正执行（其余抢不到锁就跳过）；释放时用一小段 Lua 先校验 token 再删除，确保只删掉自己那把锁。

📍 对应机制：§09 分布式锁 · §08 Lua 脚本

⏰ 第 7 幕 —— 锁座 15 分钟，不付款就自动释放

用户锁定了一张票，15 分钟内不付款就得把座位放出来——可你又不能每秒去全库扫一遍，找哪些到期了。用延迟队列：拿一个 Sorted Set，分数就设成截止时间戳。下单锁座时 ZADD reservations <现在+15分钟> seat:42；一个工作进程不断 ZRANGEBYSCORE reservations -inf <现在> 把已经到点的捞出来，释放这些座位再 ZREM 掉。分数本身就是那个定时器——"取消超时未支付订单"、定时提醒，用的都是这一招。

📍 对应机制：§03 Sorted Set（分数 = 时间） · §08 用 Lua 原子地取出并删除

🛡️ 第 8 幕 —— 双十一：Redis 不能成为短板

现在一切都压在 Redis 上，它就得既扛得住崩溃，也扛得住节点宕机。落盘快照（RDB）加写命令日志（AOF），重启不再是冷启动；加副本分担读、做热备；让 Sentinel 自动提升副本，或者上 Cluster 把数据分片到多台机器。

01心智模型

说到底,Redis 就是一个驻留在内存里的巨大字典(键 → 值),只不过其中的值不只是一段二进制数据,而可以是多种数据结构。命令由单个线程执行,所以每条命令本身都是原子的。持久化和扩展能力都是围绕这个内核搭起来的:把快照/日志写入磁盘来实现持久化,用副本来分担读流量、提供高可用,用 Sentinel 实现自动故障转移,用 Cluster 实现水平分片。

02单线程事件循环

Redis 用一个 I/O 多路复用事件循环(epoll/kqueue)在单个线程上处理命令。命令进入队列后逐条执行到完成 —— 这正是每条命令什么都不用你管就天然原子的原因。

sequenceDiagram participant Cs as 客户端 participant EL as 事件循环(单线程) participant DS as 数据结构(内存) Cs->>EL: 多个套接字就绪(epoll) loop 一条命令执行完,再处理下一条 EL->>DS: 执行命令 A(原子) DS-->>EL: 回复 A EL->>DS: 执行命令 B(原子) DS-->>EL: 回复 B end EL-->>Cs: 回复(RESP)
这就像一位咖啡师一次只做一杯。订单不会互相冲突(原子!),也不会抢同一台浓缩咖啡机(无锁)。可一旦有顾客点了 500 杯拿铁(KEYS *),排在他后面的所有人都得干等。所以,订单要小。
坑就在这: 一条慢的 O(N) 命令会把所有人都堵住。一个 KEYS *、一个超大的 HGETALL,或对百万元素的集合执行 SMEMBERS,都会在执行期间冻住整个服务器。改用 SCAN/HSCAN/SSCAN 游标,别在热点路径上跑大的 O(N) 操作。
面试中的进阶细节: "单线程" 说的是命令执行这一环。现代 Redis(6+)对读写套接字用了多线程 I/O,后台线程则负责 UNLINK(异步删除)、RDB fork、AOF fsync 这类慢活儿。但键空间本身的改动依然是串行的。

这就是 Reactor 模式：一个循环对 socket 事件做出"反应"，再分发给对应的处理器。Redis 6+ 引入了多线程 I/O——额外的线程只负责读取/解析、写回 socket 的字节，命令本身仍在唯一的主线程上执行，所以原子性不受影响。另外还有后台线程（BIO）处理慢的回收/刷盘工作——UNLINK（异步删除）、AOF fsync、关闭大文件——这样它们就不会卡住主循环。

说准确点："单线程"指的是命令执行这一环是串行的。网络 I/O（6+）和后台杂活（BIO）都是多线程的。这也正是为什么删大键要用 UNLINK——内存回收会丢到主线程之外去做。

03数据类型及其命令

选对类型本身就是一种设计。下面逐一说清:每种类型是什么、什么时候用、以及哪些命令最重要。

String —— 字节、计数器、位图

最简单的值类型(最大 512 MB)。可以存文本、序列化后的 JSON、整数或原始位。缓存和原子计数器都靠它打底。

命令作用大 O
SET k v [EX s] [NX|XX]设置值;EX 设 TTL,NX 表示仅当键不存在时才设O(1)
GET k / GETSET / GETDEL读取 / 读取并设置 / 读取并删除O(1)
INCR k / INCRBY / DECR原子计数运算O(1)
MSET / MGET一次往返完成多个键的设置/读取O(N)
SETNX / SET k v NX EX 30锁原语(键不存在则设置 + 加 TTL)O(1)
SETBIT / GETBIT / BITCOUNT位图操作 —— 比如标记日活用户O(1)/O(N)
适用于: 缓存值、限流计数器(INCR + EXPIRE)、分布式锁(SET NX EX)、功能开关、原子 ID 生成。

Hash —— 带字段的对象

一个键下保存一组字段 → 值的映射。非常适合表示一个对象(用户、会话),改某个字段时不必把整个对象重新序列化一遍。

命令作用大 O

适用于: 用户资料、购物车、配置对象,以及任何需要单独改某个字段的场景。比拆成一堆独立的 string 键更省内存。

List —— 有序、双端队列、队列

字符串组成的链表;两端的 push/pop 都是 O(1)。最经典的简单队列 / 栈。

命令作用大 O

Set —— 唯一、无序的成员集合

一组不重复的字符串,支持快速判断成员是否存在,以及各种集合运算。

命令作用大 O

一种集合,每个成员都带一个浮点分数,成员始终按分数排好序。这是面试里最爱考的类型 —— 排行榜、优先级队列、限流器、时间序列索引全靠它。

底层揭秘 —— 让它快起来的那些结构

有四个底层结构在面试里反复出现——它们正是上面那些编码存在的原因。

SDS —— Redis 为什么不用 C 字符串

Redis 里每个字符串都是 SDS（Simple Dynamic String，简单动态字符串），而不是裸的 C 字符数组。它把长度和剩余空间跟字节内容存在一起：

  • O(1) 取长度——STRLEN 直接读一个字段；C 字符串得一路扫到 \0（O(N)）。
  • 二进制安全——靠长度前缀，能存任意字节（中间带 \0、图片等）；C 字符串遇到第一个 \0 就当结束了。
  • 不会缓冲区溢出——追加前先检查容量，再安全扩容。
  • 少 realloc——预分配 + 记录剩余空间，反复 APPEND 通常不必每次都 realloc。

跳表（skip list）—— O(log N) 的有序结构

较大的 Sorted Set 底层是跳表（再配一个哈希表做 O(1) 的分数查找）。跳表就是在普通链表上叠几层"快速通道"：上层一步能跨过很多节点，查找时一层层往下落——相当于在链表上做 O(log N) 的二分。每个节点的层高由抛硬币（概率约 1/4）随机决定，所以平均下来就是平衡的，不需要树那套旋转维护。

dict 与渐进式 rehash

键空间（以及较大的 Hash/Set）底层是哈希表（dict）。负载因子一高就得扩容——但一次性把上百万个条目重新哈希会卡死单线程。于是 Redis 同时留两张表（ht[0]、ht[1]），分批迁移：每次操作顺手搬几个桶过去。迁移期间，读会同时查两张表，写则落到新表，直到 ht[0] 清空。

渐进式 rehash 是面试常客——关键就在于把一次巨大的 O(N) 迁移，摊成无数个 O(1) 的小步，让延迟永远不会突然飙高。

ziplist 的连锁更新 → listpack

老的紧凑编码 ziplist，每个条目里都存了前一个条目的长度。如果靠前的某个条目涨过了 254 字节，后一个条目的"prevlen"字段就得变宽——这又可能让它自己变大，逼着再后一个也变宽：这就是连锁更新（连锁反应），最坏 O(N²)。listpack（Redis 7）解决了这个问题——每个条目自描述、只存自己的长度，没有了"前一个长度"的链条，自然也就没有连锁更新。

05过期与淘汰

过期的键是怎么被回收的

用 EXPIRE k 60 / SET k v EX 60 / PEXPIRE(毫秒)设置 TTL。Redis 用两种方式(配合使用)释放过期键:

① 惰性(被动)

访问某个键时,如果发现它已经过期,就当场删掉,命令的表现就跟这个键不存在一样。开销很低,但那些过期了又一直没人访问的键,会一直占着内存。

② 主动(采样)

有个后台任务每秒大约跑 10 次,抽样检查带 TTL 的键并删掉过期的;如果发现过期比例很高,就再来一轮。这是概率性的 —— 目的是把过期键占用的内存控制在一定范围内。

内存到达 maxmemory 时的淘汰

内存写满后,maxmemory-policy 决定该丢掉什么:

策略行为
noeviction直接拒绝写入并返回错误(把 Redis 当数据库用时的安全默认值)
allkeys-lru / allkeys-lfu在所有键里淘汰最近最少使用 / 最不常使用的 —— 经典缓存模式
volatile-lru / -lfu / -ttl / -random同上,但只在设置了 TTL 的键里淘汰
allkeys-random随机淘汰键
纯缓存场景用 allkeys-lru(访问分布很不均匀时用 lfu)。把 Redis 当主存储用时,选 noeviction,这样绝不会悄无声息地把数据丢掉。LFU(4.0 起)用一个带衰减的计数器跟踪访问频率 —— 对那些 "一直很热" 的条目更友好,而 LRU 反而可能把它们误删。

07事务:MULTI / EXEC / WATCH

Redis 事务在 MULTI 之后把命令先排进队列,到 EXEC 时作为一个隔离的整体执行,中途不会有别的客户端插进来。但它不是 SQL 那种事务:没有回滚。如果某条命令在执行时出现逻辑错误(比如对一个 string 执行 INCR),其余命令照样会执行。

08Lua 脚本与函数

用 EVAL / EVALSHA(或 7+ 里可持久化的 FUNCTION)把逻辑下发到服务端执行。整个脚本原子运行 —— 中途不会被打断 —— 所以你能在服务端、一次往返里安全地走完读取 → 判断 → 写入。

-- 原子地 "若有库存则扣减"(防超卖)
-- KEYS[1]=库存键, ARGV[1]=数量
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock and stock >= tonumber(ARGV[1]) then
  return redis.call('DECRBY', KEYS[1], ARGV[1])   -- 成功
else
  return -1                                        -- 库存不足
end
它好在哪: 整段逻辑里没有网络往返,没有竞态窗口,客户端和服务端之间的往返也更少。用 EVALSHA 配合已缓存的 SHA,就不用每次都把脚本正文重新发一遍。
脚本要短 —— 它和普通命令一样会阻塞单线程。键一定要通过 KEYS[] 传(别硬编码),这样 Cluster 才能正确路由。

09分布式锁

经典写法:SET lock:resource <random-token> NX EX 30。NX 让 "抢锁" 这一步是原子的;EX 保证持有者万一崩溃,锁也会自动过期(不会一直死锁下去)。

# 获取
SET lock:order:42 $token NX EX 30      # ok / nil

# 释放 —— 必须是原子的 "检查后删除"(用 Lua),
# 这样你只删除自己的锁,而不会删除一个已过期并被他人重新获取的锁
if redis.call('GET', KEYS[1]) == ARGV[1]
then return redis.call('DEL', KEYS[1]) else return 0 end
三个经典错误:(1) 不设 TTL → 一崩溃就死锁;(2) 删锁时只按键删、不检查 token → 你的锁过期后,可能误删了别人刚拿到的锁;(3) 干活时间超过了 TTL → 锁同时被两个人持有(可以用看门狗自动续期 TTL 来缓解)。
Redlock: 针对 "跨多个独立 Redis 主节点加锁" 这套方案,Martin Kleppmann 有过一段很有名的批评 —— 在 GC 停顿、时钟漂移的情况下,单实例锁对正确性关键的临界区并不安全。可以这样答:"如果锁只是为了效率,单实例的 SET NX EX 够用;如果关乎正确性,我会用真正的共识系统(ZooKeeper/etcd)或栅栏令牌(fencing token)。"

10持久化 —— RDB vs AOF

内存断电即失,所以 Redis 提供了两种落盘机制。你可以只用一种、两种都用,或者都不用。

RDB —— 时间点快照 紧凑

fork 出一个子进程,周期性地把整个数据集 dump 成一个二进制 dump.rdb 文件(例如 save 900 1)。靠写时复制(copy-on-write)让主线程在此期间照常服务。

+ 文件小、重启加载快,很适合做备份和复制时的引导。
− 一旦崩溃,上次快照之后写入的数据全没了。

AOF —— 只追加命令日志 持久

把每条写命令追加到文件里,重启时重放一遍。appendfsync 控制刷盘时机:always(最安全、最慢)、everysec(默认 —— 最多丢 1 秒)、no(交给操作系统决定)。

+ 丢的数据最少,而且大致能看懂内容。
− 文件更大、重启更慢。会定期重写(rewrite)来压缩文件。

副本是怎么同步的

  1. 全量同步(PSYNC): 首次连接时(或落后太多时),主节点 fork 出一个 RDB 快照发给副本,同时把这期间的新写入先存进复制积压缓冲区(replication backlog),随后再补发给副本。
  2. 部分重同步: 短暂断连重连后,副本会请求从自己的偏移量继续;只要这个偏移还在积压缓冲区里,主节点就只补发断开期间缺的那段 —— 不必再来一次全量快照。
异步 = 已确认的写入也可能丢。 如果主节点回复完客户端、还没来得及复制就崩了,那条写入在故障转移后就没了。WAIT numreplicas timeout 能让你阻塞到 N 个副本都确认为止 —— 更持久,但延迟更高。Redis 本身并不提供真正的同步复制。
主节点是在黑板上写字的老师,副本是埋头往笔记本上抄的学生。学生也能答问题(读扩展!),但总有那么一瞬,老师写的新内容后排还没抄上 —— 这就是复制延迟。要是老师在后排抄完最后一行之前晕倒了,那行就没了(异步 = 可能丢数据)。
读己之写(read-your-own-writes)要小心:写完主节点立刻去副本读,可能因为延迟而读到旧数据。办法有几种:把关键的读请求打到主节点,或者用 WAIT,再或者干脆接受最终一致性。面试时一定要把这个取舍讲明白。

Sentinel 就像盯着老板(主节点)的一群保安。单凭一个保安发现老板没反应还不算数(SDOWN —— 没准是这个保安自己眼花了)。只有当多数人投票认定老板确实出事(ODOWN),他们才会提拔副手(一个副本)上位,并向所有人宣布新老板是谁。保安人数要取奇数,投票才不会打平。
关键术语: SDOWN = 单个 Sentinel 认为主节点挂了;ODOWN = 达到法定人数、大家一致认定 → 触发故障转移。把奇数个(≥3)Sentinel 分散部署在不同主机上,这样脑裂时多数派依然能形成。客户端要用支持 Sentinel 的客户端库连接,才能始终找到当前的主节点。
Sentinel vs Cluster: Sentinel = 给单个分片做高可用(一份数据集,主 + 副本,自动故障转移)—— 它不对数据分片。Cluster = 高可用再加上水平分片。如果数据一个节点就装得下,你又只需要故障转移,那 Sentinel 更省事。

哨兵怎么选出领头者（类 Raft）

哨兵之间一直在流言（gossip）——通过一个发布订阅频道，互相交换各自对主节点、以及对彼此的看法。一旦达到法定人数、一致认定主节点 ODOWN，就必须由恰好一个哨兵来执行故障转移——否则两个哨兵可能各自提升出一个副本（也就是脑裂，split-brain）。于是它们走一轮类 Raft 的选举：

  1. 每次故障转移都带一个单调递增的纪元（epoch，相当于任期）。
  2. 发现 ODOWN 的哨兵，请求其他哨兵在这个纪元里投自己当领头者。
  3. 每个哨兵在每个纪元里只投一票（先到先得）；谁拿到多数票谁当选。
  4. 领头者挑出最合适的副本（数据最新、优先级数最小），用 REPLICAOF NO ONE 把它提升为主节点，再把其余副本重新指向它。
脑裂（split-brain）：如果网络分区让旧主节点在少数派那一侧还活着，那一侧的客户端可能继续往它写——等它重新入群、被降级时，这些写入就丢了。可以用 min-replicas-to-write 缓解（可达副本太少时，主节点干脆拒绝写入）。而部署奇数个（≥3）哨兵，正是为了保证任何时刻只有一侧能凑齐多数。

13Cluster —— 水平分片

当数据量或吞吐量超出一台机器的承受范围时,Redis Cluster 会把键空间分片到多个主节点上,每个主节点各自带副本。中间没有代理 —— 客户端直接连到对应的节点。

Cluster 与 CAP —— 你在拿什么做交换

按 CAP 定理，一个会发生网络分区的分布式存储，没法同时做到完美的一致性和可用性。Redis 的复制是异步的，所以 Redis Cluster 偏向 AP（保住可用性），而不是 CP：

  • 主节点是先回复客户端、再复制的，所以故障转移时可能丢掉最后那批还没复制出去的写入——不是强一致。
  • 节点之间靠集群总线上的流言（gossip）探测故障；只有多数主节点都同意，才会对某个主节点做故障转移——这正是少数派分区无法擅自提升副本的原因。
  • cluster-node-timeout 再加上对被孤立的少数派主节点的写入暂停，限制了它还能继续接受写入多久（从而压住脑裂带来的数据分叉）。
干脆利落地说："Redis Cluster 是异步复制的 AP 系统——优先保可用，并接受故障转移时有一小段可能丢写的窗口。要强一致就得上 CP 系统，或者用 WAIT 换更强的确认（代价是延迟）。"

穿透(Penetration)查的键在数据库里压根不存在 → 每个请求都直接打到数据库就算数据库里也查不到，也把这个空结果用很短的 TTL 缓存下来，后续一模一样的无效查询就不会再打到数据库。再在前面加一层布隆过滤器，一看就不可能存在的键，根本不放它去查库。

雪崩(Avalanche)大量键在同一刻集中过期(或 Redis 整个挂了)→ 数据库被打垮给每个键的 TTL 加上随机抖动，把过期时间错开，避免大家在同一刻集体失效。再配合多级缓存、熔断降级，以及 Redis 自身的高可用，确保缓存不会整个消失。
缓存与数据库的一致性: 双写没有完美方案。常见做法是"先更新数据库,再删除缓存"(cache-aside 失效)。别用 "先更新数据库,再更新缓存"(并发竞争会写进旧值)。想要更强的保证,就别靠应用代码,而是用数据库的 binlog/CDC(比如 Debezium)来触发缓存失效。

缓存与数据库一致性 —— 到底该怎么做

往两个系统里同时写、还想完美一致，是做不到的。所以现实里是一套层层递进的方案：越往后越可靠，也越复杂——按你的需求选到哪层就停：

  1. 基线 —— Cache Aside：「先更新数据库，再删缓存」。失效时用删而不是改（直接改缓存会和别的写抢，可能写进旧值），而且要在数据库提交之后再删。下一个读的人没命中，自然会从库里读到最新值，再重新缓存。
  2. 加强 —— 延迟双删：基线还留着一个小竞态——你这次删除，可能和"某个并发读正打算把旧值写回缓存"擦肩而过。于是删一次 → 写库 → 过一小会儿再删一次，把中途被塞回的旧值清掉。
  3. 最强 —— 用 binlog/CDC 驱动失效：前两层都靠业务代码记得去删；万一应用在"写完库、还没删缓存"之间崩了，这次失效就漏了。改成订阅数据库的变更日志（比如 Debezium → 删缓存），一条都不会漏。
认清现实：这是带一个极小旧值窗口的最终一致性，不是分布式事务。如果你真的需要"写完立刻读到自己写的"，那就在写完后直接读数据库（或主节点）的那个键。

布隆过滤器 —— 用极小内存挡掉不存在的键

布隆过滤器能用极小的内存回答："这个键一定不存在，还是可能存在？"。它是一个位数组 + k 个哈希函数：加一个键就把对应的 k 个位置 1；查的时候就看这 k 个位。只要有一个是 0 → 一定不存在（直接拒掉、根本不碰数据库 → 干掉缓存穿透）。如果 k 个全是 1 → 可能存在（偶有误判，但绝不会漏判）。

取舍：普通布隆过滤器删不掉元素（真要删就用计数型 / cuckoo 变体）。按你想要的误判率来定位数组大小和 k。

大 Key —— 沉默的杀手

大 key 就是单个键装了超大的值——一个好几 MB 的 String，或者带上百万成员的 Hash/Set/ZSet。

危害在哪

一次 O(N) 操作（或一把 DEL）就卡住单线程；内存在 Cluster 各分片上分布不均；一次 GET 就能把网卡打满；过期/删除时还会引发延迟尖刺。

怎么排查 & 解决

用 redis-cli --bigkeys 或 MEMORY USAGE 找出来。解决靠拆分（把一个大 hash 拆到很多键上）、只读局部（用 HSCAN 而不是 HGETALL）、删除用 UNLINK（异步）而不是 DEL。

热 Key —— 蜂拥而上的人群

热 key 是某一个键吃掉了多到离谱的流量（明星、秒杀商品）——它会把持有它的那个分片压垮。

危害在哪

对这个键的所有请求都（按哈希槽）路由到同一个主节点，于是它打满了、其他节点却闲着——而它一旦过期，所有客户端会在同一时刻涌向数据库。

怎么排查 & 解决

用 redis-cli --hotkeys / 监控找出来。解决靠在前面加本地（进程内）缓存、用副本 + 读写分离分摊读、或者把键拆开（把值复制到多个带后缀的键上，随机挑一个读）。

17Boss 级问题 专家

这些题,能把 "用过 Redis" 和 "真懂 Redis" 区分开。先自己想,再点开看答案。

为什么偏偏是 16384 个槽 —— 为什么不是一百万? 中等
每次心跳里,节点都要用位图把自己负责的槽流言出去。16384 位 = 每条消息 2 KB —— 一直发也不费什么。换成一百万个槽,每次心跳就臃肿了。而 16384 仍然远比现实中的节点数多,槽因此能分得很均匀。这正是 "大到足以分均匀、小到足以随便传" 的那个甜点位。
你最热的键在半夜过期,1 万个请求一下子全压到数据库上。怎么救? 困难
这是典型的缓存击穿。几种办法:(1) 互斥锁 —— 第一个没命中的请求拿到锁(SET NX)去重建,其他请求稍等片刻或先返回旧值。(2) 逻辑过期 —— 这个键不设物理过期;另存一个 "逻辑过期时间" 字段,读取时如果发现逻辑上已经过期,就派一个线程异步刷新,其他人继续拿旧值用。(3) 提前预热 + 给 TTL 加随机,让热点键不会同时到期(这一点顺带也能防雪崩)。
跨网络做读取-修改-写入,怎么保证原子 —— 以及为什么 WATCH 常常不是正确的选择? 中等
通常Lua / EVAL 最合适:整个读取→判断→写入在服务端一次性原子完成,只一次往返,没有竞态窗口。WATCH/MULTI 走的是乐观 CAS —— 被监视的键一变它就中止,你得重试,在高并发竞争下会演变成重试风暴和额外往返。纯算术用 INCR/HINCRBY;带条件判断的逻辑用 Lua;WATCH 只留给那种偶尔发生、竞争很低的场景。
Redis 的分布式锁真的安全吗? 困难
如果只是为了效率(避免重复干活)—— 安全,SET NX EX + Lua 释放完全够用。如果关乎正确性(绝不允许同时有两个持有者)—— 那就不保险了:单实例锁并非万无一失,一次 GC 停顿或时钟漂移,就可能让锁在你以为还握着的时候早已过期。后来有人提出 Redlock(多主),但 Kleppmann 的批评指出,在这些条件下它照样不安全。老实的答案是:对正确性关键的锁,要用栅栏令牌(fencing token,一个单调递增、由资源端校验的数),或者干脆用真正的共识存储(etcd/ZooKeeper)。
主节点挂了。一步步讲讲 Sentinel 都做了什么。 中等
(1) 各个 Sentinel PING 主节点;其中一个收不到回复 → 把它标记为 SDOWN(主观下线)。(2) 它通过流言去问其他节点;一旦达到配置的法定人数都同意 → ODOWN(客观下线)。(3) Sentinel 们选出一个领头者(类似 Raft)。(4) 领头者挑出最合适的副本(数据最新、优先级数最小),给它发 REPLICAOF NO ONE 把它提升为主节点。(5) 其余副本被改指向新主节点;来问 Sentinel 的客户端会拿到新地址。整个过程会有短暂不可用,还可能丢掉少量异步写入。
你给 100 万个键设了过期,可内存几乎没降。为什么? 中等
过期走的是惰性 + 主动采样,不是立刻清掉。一直没人访问的过期键会赖着不走,直到被访问到(惰性),或被那个约 10Hz 的采样周期抽中(它每轮只删一批,且是概率性的)。要想立刻批量清掉,就显式删除(大键用 UNLINK 异步释放),或者靠 maxmemory + 淘汰来处理。另外提醒一句:删除 / 过期本身也是单线程上的活儿,所以一大批键同时过期会引起延迟尖峰。
单线程什么时候会真的成为瓶颈,这时该怎么办? 困难
当单核的命令执行能力被打满,或者一条大的 O(N) 命令把一切都拖住时。应对办法:用 Cluster 分片(主节点越多 = 可用核越多);干掉 O(N) 的热点命令(用 SCAN 代替 KEYS,别跑超大的 HGETALL);用流水线摊薄往返开销;把 CPU 密集的活儿从 Lua 里挪出去;再借助 Redis 6+ 的多线程 I/O 分担套接字层的工作。要记住,键空间的改动按设计依然是串行的 —— 你能做的是横向扩出去,而不是把那个执行线程纵向加速。
