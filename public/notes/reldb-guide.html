01The relational model

A relational database stores data as tables (relations): rows (tuples/records) and columns (attributes), each column with a fixed type. Tables are linked by keys. You describe what you want with declarative SQL; the database's query planner figures out how to fetch it efficiently. This separation — plus strong consistency guarantees (ACID) — is why relational DBs remain the default for systems that need correctness.

A table is a spreadsheet with rules: every column has a type, every row is unique by its key, and you can't put text where a number belongs. Foreign keys are like cells that must point to a real row in another sheet — the database refuses to let the link dangle.
"SQL vs NoSQL?" — reach for relational when you need multi-row transactions, joins, and strong consistency over structured data with relationships (orders, payments, inventory). Reach for NoSQL when you need massive horizontal scale, flexible/sparse schema, or a specific access pattern (KV, document, wide-column) and can relax consistency.

02Keys & constraints

Constraints are how the database guarantees data integrity for you, instead of trusting application code to never make a mistake.

ConstraintGuarantees
PRIMARY KEYUnique + NOT NULL row identifier. One per table. Usually the clustering key.
FOREIGN KEYA column's values must exist in the referenced table — referential integrity. Supports ON DELETE CASCADE/RESTRICT/SET NULL.
UNIQUENo duplicate values (allows one+ NULLs depending on engine). Backed by a unique index.
NOT NULLValue is required.
CHECKArbitrary boolean rule, e.g. CHECK (price >= 0). MySQL enforced only since 8.0.16.
DEFAULTValue used when none supplied.

Natural vs surrogate keys

A natural key comes from the data (email, SSN). A surrogate key is a synthetic id (BIGINT auto-increment / SERIAL / IDENTITY, or UUID). Surrogates are usually preferred for stable PKs because natural values change and can be large.

UUID as PK caution: random UUID v4 PKs hurt write locality in a clustered index (random insert points → page splits, fragmentation). Prefer auto-increment BIGINT, or time-ordered IDs (UUID v7 / ULID / Snowflake) if you need globally-unique keys.

03SQL anatomy & logical execution order

SQL has sub-languages: DDL (define: CREATE/ALTER/DROP), DML (manipulate: SELECT/INSERT/UPDATE/DELETE), DCL (control: GRANT/REVOKE), TCL (transactions: BEGIN/COMMIT/ROLLBACK).

The single most useful thing to internalize: a SELECT is written in one order but logically executed in another. This explains why you can't use a SELECT alias in WHERE, but can in ORDER BY.

Why it matters: WHERE runs before SELECT, so column aliases defined in SELECT don't exist yet → can't filter on them. ORDER BY runs after SELECT, so aliases are available there. HAVING filters after grouping (use it for aggregate conditions); WHERE filters before (cheaper — filter early).

SELECT customer_id, COUNT(*) AS orders, SUM(total) AS revenue
FROM   "order"
WHERE  created_at >= '2026-01-01'      -- filter rows first (uses index)
GROUP  BY customer_id                  -- then group
HAVING SUM(total) > 1000               -- then filter groups
ORDER  BY revenue DESC                  -- alias OK here
LIMIT  10;

05Aggregation & grouping

Aggregate functions collapse many rows into one value. GROUP BY creates one output row per group.

FunctionNote
COUNT(*) vs COUNT(col)* counts rows; col skips NULLs. COUNT(DISTINCT col) for uniques.
SUM / AVG / MIN / MAXIgnore NULLs. AVG = SUM/COUNT of non-NULLs.
STRING_AGG PG / GROUP_CONCAT MySQLConcatenate group values into one string.
FILTER (WHERE ...) PGConditional aggregate, e.g. COUNT(*) FILTER (WHERE status='paid').
NULL is not zero and not equal to anything. NULL = NULL is unknown, not true. Use IS NULL, and COALESCE(x, 0) to substitute. COUNT(*) includes NULL rows; SUM over all-NULL returns NULL (not 0).
GROUP BY strictness: in standard SQL / PG, every non-aggregated SELECT column must appear in GROUP BY. MySQL historically allowed sloppy grouping (picks an arbitrary value) unless ONLY_FULL_GROUP_BY is on (default in 5.7+).

06Subqueries, CTEs & window functions

Subqueries

A query nested in another. Scalar (returns one value), IN / EXISTS (membership), or correlated (references the outer row — runs per outer row, can be slow).

EXISTS is often faster than IN for large/correlated checks because it short-circuits on the first match. Beware NOT IN with NULLs — a single NULL makes the whole thing return no rows.

CTEs (WITH)

Common Table Expressions name a subquery up front for readability, and enable recursion (hierarchies, graphs).

WITH RECURSIVE subordinates AS (
  SELECT id, manager_id, name FROM employee WHERE id = 1   -- anchor
  UNION ALL
  SELECT e.id, e.manager_id, e.name                          -- recurse
  FROM employee e JOIN subordinates s ON e.manager_id = s.id
)
SELECT * FROM subordinates;
PG historically materialized CTEs (an optimization fence); since PG12 they can be inlined unless you write WITH ... AS MATERIALIZED. Good to know when a CTE unexpectedly blocks index use.

Window functions

Compute across a set of rows related to the current row — without collapsing them like GROUP BY does. The superpower for analytics, rankings, running totals, and dedup.

SELECT name, dept, salary,
  RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
  AVG(salary)  OVER (PARTITION BY dept)                       AS dept_avg,
  SUM(salary)  OVER (ORDER BY hired_at)                       AS running_total
FROM employee;
Window fnUse
ROW_NUMBER()Unique sequential # — great for "keep latest per group" dedup
RANK / DENSE_RANKRanking with / without gaps on ties
LAG / LEADPrevious / next row's value (deltas, trends)
NTILE(n)Bucket rows into n groups (percentiles)
"Top-N per group" is a top SQL interview question. Answer: ROW_NUMBER() OVER (PARTITION BY group ORDER BY metric DESC) in a subquery/CTE, then filter WHERE rn <= N.

08Normalization (and when to denormalize)

Normalization organizes columns to eliminate redundancy and update anomalies. Each "normal form" is a stricter rule built on the previous.

FormRule (informal)Fixes
1NFAtomic values; no repeating groups/arrays in a column"tags: a,b,c" crammed in one cell
2NF1NF + no partial dependency on part of a composite keyColumn depending on only half the PK
3NF2NF + no transitive dependency (non-key → non-key)zip determining city in an orders table
BCNFStricter 3NF: every determinant is a candidate keyRare overlapping-candidate-key edge cases
Normalization is "don't write the same fact twice." Store a customer's address once in customer, and point to it from every order — so changing the address is one edit, not a hunt across thousands of rows (that hunt is an "update anomaly").
Denormalization is the deliberate reverse: duplicate data (e.g. cache an order_count on customer, or store a JSONB blob) to avoid expensive joins on hot read paths. Trade write complexity + consistency risk for read speed. Normalize first; denormalize only where measurements demand it.
Default target is 3NF for OLTP (transactional) systems — clean writes, integrity. Analytical/OLAP systems often denormalize into star schemas (facts + dimensions) for fast aggregation. Know which workload you're designing for.

09Indexes — the #1 performance lever

An index is a separate, sorted data structure that lets the DB find rows without scanning the whole table. Almost always a B+tree: balanced, O(log n) lookups, and great for range scans because leaves are linked in order.

An index is the index at the back of a textbook. Without it, finding "MVCC" means reading every page (a full table scan). With it, you jump to the sorted entry and flip straight to the right pages. And just like a book, indexing everything wastes space and slows down edits (every new page must update the index).

Clustered vs secondary InnoDB PG heap

Clustered index MySQL/InnoDB

The table rows are stored inside the primary-key B+tree (leaves hold full rows). One per table. PK lookups are very fast. Secondary indexes store the PK, not a row pointer — so a secondary lookup does two hops: secondary → PK → row.

Heap + secondary PostgreSQL

Rows live in an unordered heap; every index (including PK) points to a physical row location (ctid). No "clustered" table by default. Covering / index-only scans avoid the heap when all needed columns are in the index (and the visibility map allows).

Index types & flavors

IndexWhat / when
Composite (a,b,c)Multi-column. Leftmost-prefix rule: usable for a, a,b, a,b,c — not for b alone. Column order matters!
CoveringIndex contains all columns the query needs → answer from index alone, skip the table. PG INCLUDE columns.
UniqueEnforces uniqueness + speeds lookups.
Partial / filtered PGIndex only rows matching a predicate, e.g. WHERE active — smaller, faster.
HashO(1) equality only (no ranges). Niche.
GIN / GiST PGFull-text, JSONB, arrays, geometric/range data. MySQL: FULLTEXT, SPATIAL.

Why an index doesn't get used

  • Function on the column: WHERE YEAR(created_at)=2026 can't use an index on created_at — rewrite as a range, or add an expression index.
  • Leading wildcard: LIKE '%foo' can't seek; 'foo%' can.
  • Implicit type cast: comparing a string column to a number forces a scan.
  • Low selectivity: if a value matches most rows, the planner correctly prefers a full scan.
Indexes aren't free. Each one must be updated on every INSERT/UPDATE/DELETE and consumes space. Over-indexing slows writes. Index for your actual query patterns; drop unused ones.

12ACID — the transaction contract

A transaction groups statements into an all-or-nothing unit (BEGIN ... COMMIT/ROLLBACK). ACID is what it guarantees:

A — Atomicity

All statements commit, or none do. A failure mid-way rolls everything back. (Implemented via the undo log / rollback segment.)

C — Consistency

A transaction moves the DB from one valid state to another — constraints, FKs, triggers all hold. (Your invariants + the DB's rules.)

I — Isolation

Concurrent transactions don't step on each other; results look as if they ran in some serial order. How much is the isolation level (next section).

D — Durability

Once committed, it survives crashes/power loss. (Implemented via the write-ahead log fsync'd before commit returns.)

A transaction is a bank transfer: debit one account, credit another. Atomicity means you never debit without crediting (no money vanishes). Durability means once the receipt prints, a power cut can't undo it. Isolation means two simultaneous transfers don't read each other's half-finished state.

13Isolation levels & anomalies

Stronger isolation = fewer anomalies but more locking/contention. The SQL standard defines four levels by which anomalies they permit.

LevelDirty readNon-repeatable readPhantom
Read Uncommitted😱 yes😱 yes😱 yes
Read Committed PG default✅ no😱 yes😱 yes
Repeatable Read MySQL default✅ no✅ no⚠️ standard: yes
Serializable✅ no✅ no✅ no

The anomalies, plainly

  • Dirty read — you read another transaction's uncommitted change that may roll back.
  • Non-repeatable read — you read a row twice and get different values (someone committed an update between).
  • Phantom read — you re-run a range query and new rows appear (someone inserted matching rows).
  • Write skew — two transactions each read a shared state, then write based on it, producing a result impossible under any serial order (only Serializable prevents it).
Engine specifics worth saying out loud: MySQL/InnoDB default is Repeatable Read, and it largely prevents phantoms via next-key locks (gap + row locks). PostgreSQL default is Read Committed; its Repeatable Read is snapshot isolation (prevents non-repeatable reads & most phantoms but allows write skew); Serializable uses SSI (Serializable Snapshot Isolation) and may abort transactions with a serialization error you must retry.
Be ready to give a concrete write-skew example: two on-call doctors each check "≥1 other doctor is on duty" and both go off-call simultaneously → zero coverage. Both reads were valid; the combination isn't. Only SERIALIZABLE (or explicit locking) prevents it.

14Concurrency control: locking & MVCC

How do many transactions run at once without corrupting data? Two mechanisms, used together.

Locking

LockMeaning

MVCC — Multi-Version Concurrency Control

The big idea: readers don't block writers and writers don't block readers. Instead of overwriting in place, the DB keeps multiple versions of a row. Each transaction sees a consistent snapshot as of its start (or statement). A reader sees the old version while a writer creates a new one.

sequenceDiagram participant T1 as Txn 1 (reader) participant Row as Row "balance" participant T2 as Txn 2 (writer) Note over Row: version A = 500 (visible) T1->>Row: read → sees 500 (its snapshot) T2->>Row: UPDATE → creates version B = 400 Note over Row: A still kept for T1 T1->>Row: read again → STILL 500 (no block, repeatable) T2->>T2: COMMIT Note over Row: new txns see 400, A reclaimable later

PostgreSQL MVCC

New row versions written into the heap; old versions stay until VACUUM reclaims them. Visibility via transaction-id (xmin/xmax). Trade-off: table bloat & the need for (auto)vacuum.

MySQL/InnoDB MVCC

Current row lives in the table; old versions reconstructed from undo logs (rollback segment). Cleaned by the purge thread. Long transactions bloat the undo history.

Long-running transactions are the enemy of MVCC. An open transaction holds an old snapshot, so the DB can't reclaim row versions newer than it — causing bloat (PG) or huge undo (MySQL) and degraded performance. Keep transactions short; don't BEGIN then wait on a slow external call.

15Deadlocks

Two transactions each hold a lock the other needs → neither can proceed. The DB detects the cycle and kills one (the "victim") with a deadlock error; you retry it.

flowchart LR T1(("Txn 1")):::t -->|holds| A[(Row A)]:::r T1 -->|wants| B[(Row B)]:::r T2(("Txn 2")):::t -->|holds| B T2 -->|wants| A classDef t fill:#fde6e4,stroke:#dc382d,color:#7a1810; classDef r fill:#fbf3da,stroke:#c9a83a,color:#6b5212;
How to avoid them: (1) acquire locks in a consistent order everywhere (e.g. always lock the lower id first); (2) keep transactions short & touch fewer rows; (3) use appropriate indexes so locks are precise (a missing index can lock extra rows/gaps); (4) always wrap writes in retry logic — deadlocks are normal under load, not a bug to eliminate entirely.
Distinguish deadlock (cycle, auto-resolved by killing a victim) from lock wait timeout (one txn waits too long for a lock that isn't a cycle) from livelock (txns keep retrying and colliding). Interviewers probe whether you know the DB resolves deadlocks automatically.

The four InnoDB logs: undo · Read View · redo · binlog — one picture

Interviews love to blur these four together. How one UPDATE flows through all four

Watch steps ③ and ⑤: redo writes a "prepare" first, then the binlog is written, then redo writes "commit" — that's the two-phase commit (internal XA) between redo and binlog, keeping the two logs consistent after a crash (so you never get "rolled back on the primary but executed on the replica").

Why two-phase commit? Say the binlog was written but the server crashed before redo's commit — recovery finds that redo in the prepare state and checks whether the txn is fully written in the binlog: if yes, commit it; if not, roll back. That's what keeps "the local data" and "the binlog shipped to replicas" in agreement.

How undo + Read View power consistent reads (MVCC)

Every row carries hidden columns DB_TRX_ID (the txn that last changed it) and DB_ROLL_PTR (a pointer to the previous version in undo). On a snapshot read, the txn uses its Read View to decide whether the current version is visible; if not, it walks back the undo version chain via DB_ROLL_PTR until it finds the first visible version.

Add that redo guarantees durability, binlog drives replication, and the two are aligned by two-phase commit, and it's complete.

  • write pos: where new redo is written. checkpoint: everything before it has dirty pages already flushed to the data files, so that redo can be overwritten.

  • Once write pos catches up to checkpoint (ring is full), the engine must force-flush dirty pages and advance the checkpoint before continuing — writes stall during this.
  • LSN (Log Sequence Number) is a monotonically increasing number threaded through redo, data pages, and the checkpoint; recovery uses it to decide whether a given page needs redoing.

Read View — a snapshot of active transactions

It isn't persisted; it's just four values the txn keeps in memory, used with the version chain for visibility:

FieldMeaning
m_idsList of all active (uncommitted) transaction ids at the moment the snapshot was taken
min_trx_idThe smallest value in m_ids
max_trx_idThe next txn id to be assigned (greater than all current ones)
creator_trx_idThis transaction's own id
Visibility check (compare a version's DB_TRX_ID): ① < min_trx_id → committed long ago, visible; ② ≥ max_trx_id → a txn that started after the snapshot, not visible (follow roll_ptr to an older version); ③ in between → if it's in m_ids it was still uncommitted then, not visible, otherwise visible. Your own changes (== creator_trx_id) are visible, of course.

18High availability & failover

Replication alone gives a standby, but something must detect a dead primary and promote a replica, then redirect traffic. That orchestration is HA.

sequenceDiagram participant M as Manager (Patroni/Orchestrator) participant P as Primary participant R as Replica participant App M->>P: health check P--xM: no response (down) Note over M: confirm via consensus/quorum M->>R: promote to primary M->>App: update routing (VIP / DNS / proxy) App->>R: writes now go here ✅
Tooling: PG commonly uses Patroni (+ etcd/Consul/ZooKeeper for leader election) or repmgr. MySQL uses Orchestrator, InnoDB Cluster (Group Replication + MySQL Router), or managed services (RDS/Aurora). A proxy (ProxySQL, HAProxy, PgBouncer + a VIP) hides the topology from apps.
Split-brain is the nightmare: a network partition makes two nodes both think they're primary, accepting divergent writes. Prevented with quorum/consensus (an odd number of voters) and fencing (forcibly isolate the old primary). This is why you need an external arbiter, not just two database nodes.
Know your objectives: RPO (Recovery Point Objective — how much data you can lose) and RTO (Recovery Time Objective — how long to recover). Async replication → RPO > 0; synchronous → RPO ≈ 0 at latency cost. These frame every HA design discussion.

19Partitioning & sharding

Two different "split the data" ideas people conflate:

Partitioning (one server)

Split one big table into pieces within the same database by a key. Queries hitting one partition skip the rest (partition pruning); old partitions drop instantly. By range (dates), list (region), or hash.

Sharding (many servers)

Split data across independent database servers to scale writes/storage beyond one machine. Each shard is a full DB holding a subset of rows by a shard key.

flowchart TB K["row: user_id = 8124"]:::a --> H{"shard key →
hash(user_id) % N"}:::h H -->|0| S0[(Shard 0)]:::m H -->|1| S1[(Shard 1 ✓)]:::mh H -->|2| S2[(Shard 2)]:::m classDef a fill:#eef4ff,stroke:#4a8fd6,color:#1a3a5c; classDef h fill:#f1e9fc,stroke:#9a6fe0,color:#4a2d7a; classDef m fill:#eef1f5,stroke:#bcc6d2,color:#2a3340; classDef mh fill:#fde6e4,stroke:#dc382d,color:#7a1810;
Sharding is a last resort — it's expensive. You lose easy cross-shard joins, cross-shard transactions, and AUTO_INCREMENT uniqueness; rebalancing is hard. Exhaust the cheaper levers first: indexing, read replicas, caching, partitioning, a bigger box. Choose the shard key to avoid hot shards and to keep related rows together.
Vertical vs horizontal: vertical = move different tables/columns to different servers (split by feature); horizontal = split the rows of one table across servers (split by key). Managed options: Vitess (MySQL), Citus (PG), CockroachDB/Spanner (distributed SQL that shards transparently).

20Connection pooling

Each DB connection costs memory and (in PG) a backend process. Opening one per request is slow and exhausts the server's max_connections fast. A pool keeps a set of warm connections and hands them out.

Rule of thumb: a right-sized pool is often smaller than people expect. Beyond ~(cores × 2–4) active connections, you add context-switching contention, not throughput. Queue at the pool, don't pile connections on the DB.

22Security essentials

SQL injection — the #1 risk

Concatenating user input into SQL lets an attacker rewrite your query ('; DROP TABLE users;--). The fix is non-negotiable: parameterized queries / prepared statements — the driver sends SQL and data separately so input is never parsed as code. Never string-build SQL from user input; an ORM helps but you must still avoid raw interpolation.

-- ❌ injectable
"SELECT * FROM users WHERE email = '" + input + "'"
-- ✅ parameterized
"SELECT * FROM users WHERE email = $1"   // bind input separately

Access control

  • Least privilege: app role gets only the grants it needs (no SUPERUSER/GRANT ALL). Separate read-only roles.
  • Row-Level Security (RLS) PG: policies restrict which rows a role can see — great for multi-tenant isolation in the DB itself.
  • Encryption: TLS in transit; at-rest encryption (TDE / disk); hash passwords (bcrypt/argon2), never store plaintext secrets.
If asked "how do you stop SQL injection," the one-word answer is parameterization (prepared statements / bind variables), not "escaping" or "validation" — those are defense-in-depth, but binding is the actual fix.

CAP theorem often comes up here: under a network Partition you must choose Consistency or Availability. Traditional SQL leans CP (refuse stale/conflicting writes); many NoSQL stores lean AP (stay available, reconcile later). The pragmatic modern view (PACELC): also consider latency-vs-consistency even when there's no partition. Don't recite it dogmatically — use it to justify a trade-off.
Don't think "either/or" — most real systems are polyglot. Postgres as the source of truth, Redis for caching, Elasticsearch for search, a graph DB for recommendations. Also note the line is blurring: PG's JSONB gives document-style flexibility, and distributed SQL (CockroachDB, Spanner, Vitess) offers NoSQL-like scale with SQL + ACID.
SQL is a strict accountant: every entry follows the rules, the books always balance, nothing's lost — but you work at the accountant's pace and structure. NoSQL is a pile of labeled boxes in a huge warehouse: incredibly fast to toss things in and scale across many warehouses, but you're responsible for keeping related things together and reconciling duplicates.

26Boss-level questions EXPERT

The ones that separate "wrote SQL" from "understands databases." Think first, then tap to reveal.

Walk me through exactly what happens, on disk and in memory, when I COMMIT. MEDIUM
Changes were made to pages in the buffer pool / shared_buffers (RAM) and recorded in the WAL/redo log buffer. On COMMIT: the WAL records up to this commit are flushed and fsync'd to durable storage — only then does COMMIT return success. The modified data pages are still dirty in memory; they're written to the actual data files later, asynchronously, at a checkpoint. If the server crashes before that, recovery replays the WAL from the last checkpoint to redo committed changes and rolls back uncommitted ones. That's how you get durability without a random-write per commit.
A query is slow. Give me your end-to-end diagnosis process. MEDIUM
(1) Find it: slow-query log / pg_stat_statements / APM. (2) EXPLAIN ANALYZE: look for full/seq scans on big tables, bad row estimates (estimated vs actual far apart → stale stats, run ANALYZE), expensive sorts, nested loops with high row counts (missing index on inner side). (3) Fix: add/adjust an index (mind selectivity & the leftmost-prefix rule), make predicates sargable (no functions on the column), select fewer columns to enable a covering/index-only scan, or rewrite the query (EXISTS vs IN, keyset pagination). (4) Re-measure. (5) Zoom out: is it really N+1 from the app? Is connection pool saturated? Is the box I/O-bound? Don't index blindly — each index taxes writes.
Two transactions read a balance of 100 and each subtract 100. Both "succeed." How? How do you prevent it? HARD
This is a lost update / write skew under weak isolation. Under Read Committed, both read 100, both compute 0, both write 0 — one update is effectively lost, balance goes to 0 instead of -100 being rejected. Prevent it with: (a) atomic write — UPDATE acct SET bal = bal - 100 WHERE id=? AND bal >= 100 and check rows-affected; (b) pessimistic lock — SELECT ... FOR UPDATE to serialize; (c) optimistic concurrency — a version column, update WHERE version = :read, retry on mismatch; (d) SERIALIZABLE isolation (PG SSI will abort one txn → retry). The do-the-math-in-the-UPDATE option is simplest and avoids the read-then-write race entirely.
Why does PostgreSQL need VACUUM, and what is "bloat"? HARD
PG's MVCC writes a new row version on update/delete and leaves the old one in the heap, marked dead, so concurrent snapshots can still see it. VACUUM reclaims those dead tuples' space for reuse and updates the visibility map (enabling index-only scans); autovacuum does it automatically. If dead tuples accumulate faster than vacuum reclaims (high churn, or a long-running transaction holding an old snapshot that prevents cleanup), the table/index bloats — grows far beyond its live data, slowing scans and wasting disk. Also critical: VACUUM handles transaction-id wraparound; if it falls too far behind, PG will force-stop writes to protect data. Mitigations: tune autovacuum, avoid long idle-in-transaction sessions, and use VACUUM FULL/pg_repack to reclaim space (rewrites the table).
You've added read replicas, but users sometimes don't see their own just-saved change. Why, and what are the options? MEDIUM
Replication lag: the write committed on the primary but the replica hasn't applied it yet, and the read was routed to the replica. Options, by strength: (1) route read-after-write to the primary (e.g. "sticky to primary for N seconds after a write" or for that user); (2) read-your-writes via log position — remember the WAL/GTID position of the write and only read from a replica that has caught up to it; (3) synchronous replication for those writes (latency cost); (4) accept eventual consistency where the UX tolerates it. The right answer is usually per-operation: critical reads → primary, everything else → replicas.
When would you shard, and what breaks when you do? HARD
When: only after exhausting indexing, query tuning, caching, read replicas, partitioning, and vertical scaling — i.e. when a single primary genuinely can't hold the write throughput or data volume. What breaks: cross-shard joins and transactions become application-level or impossible (or need 2PC, which is slow/fragile); global uniqueness/auto-increment needs a scheme (UUID/Snowflake/central allocator); rebalancing shards and avoiding hot shards is operationally hard; aggregate queries must scatter-gather. Shard-key choice is everything — pick one with even distribution that co-locates rows you query together (e.g. by tenant_id so a tenant's data lives on one shard). Consider distributed SQL (Vitess/Citus/CockroachDB/Spanner) to get sharding with less of the manual pain.
I run SELECT * FROM t WHERE status = 'active' and it ignores my index on status. Why might that be correct? MEDIUM
Low selectivity. If most rows are active, using the index means many random row fetches (index → heap hops), which is slower than a single sequential full scan. The cost-based optimizer estimates this from statistics and correctly chooses a seq scan. Other reasons an index is skipped: stale statistics (run ANALYZE), a function/implicit cast on the column making it non-sargable, the SELECT * needing columns not in the index (so no index-only scan benefit), or a small table where a scan is trivially cheap. The fix isn't "force the index" — it's a partial index on the rare value, or fetching fewer columns, or accepting the scan is genuinely optimal.
