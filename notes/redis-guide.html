01The mental model

At its core Redis is a giant dictionary (key → value) living in RAM, where the value can be one of several data structures, not just a blob. Operations are executed by a single thread, so every command is atomic on its own. Durability and scale are bolted on around that core: snapshots/logs to disk for persistence, replicas for read-scaling + HA, Sentinel for automatic failover, and Cluster for horizontal sharding.

Think of Redis as a whiteboard right next to your desk vs. a database that's a filing cabinet down the hall. The whiteboard is tiny and wipes if the power cuts (volatile RAM) — but reading/writing it is instant. Persistence, replicas, and Cluster are all about photographing the whiteboard and cloning it across rooms so you don't lose it.
Be ready to answer "why is Redis fast?" with three reasons: (1) data is in memory, (2) a single thread avoids locks/context-switching and makes ops atomic, (3) an efficient event loop (epoll) with optimized data structures and a simple binary protocol (RESP).

02The single-threaded event loop

Redis processes commands on one thread using an I/O multiplexing event loop (epoll/kqueue). Commands are queued and run one at a time to completion — which is exactly why each individual command is atomic without you doing anything.

sequenceDiagram participant Cs as Clients participant EL as Event Loop (1 thread) participant DS as Data structures (RAM) Cs->>EL: many sockets ready (epoll) loop process one command fully, then next EL->>DS: execute cmd A (atomic) DS-->>EL: reply A EL->>DS: execute cmd B (atomic) DS-->>EL: reply B end EL-->>Cs: replies (RESP)
It's a single barista making drinks one at a time. Orders never collide (atomic!) and there's no fighting over the espresso machine (no locks). But if one customer orders 500 lattes (KEYS *), everyone behind them waits. Keep orders small.
The catch: one slow O(N) command blocks everyone. A KEYS *, a huge HGETALL, or a SMEMBERS on a million-element set will freeze the whole server for the duration. Use SCAN/HSCAN/SSCAN cursors instead, and avoid big O(N) ops on hot paths.
Nuance for senior interviews: "single-threaded" refers to command execution. Modern Redis (6+) has threaded I/O for reading/writing sockets, and background threads handle slow tasks like UNLINK (async delete), RDB fork, and AOF fsync. The keyspace mutation itself is still serial.

03Data types & their commands

Picking the right type is the design. Below: what each is, when to reach for it, and the commands that matter.

String — bytes, counters, bitmaps

The simplest value (max 512 MB). Holds text, serialized JSON, integers, or raw bits. Backbone of caching and atomic counters.

Sorted Set (ZSet) — ranked by score

A set where each member has a floating-point score; members are kept sorted by score. The single most "interview-loved" type — it powers leaderboards, priority queues, rate limiters, and time-series indexes.

Sliding-window rate limiter is a top question. Use a ZSet per user: ZADD the request with timestamp as score, ZREMRANGEBYSCORE to drop entries older than the window, then ZCARD to count what's left — all inside one Lua script for atomicity.

Specialized types

Streams (XADD/XREAD)

Append-only log with consumer groups, IDs, and acks — Redis's answer to Kafka-lite messaging. Use XADD, XREADGROUP, XACK for durable at-least-once delivery with multiple workers.

HyperLogLog (PFADD/PFCOUNT)

Probabilistic unique-count in ~12 KB with ~0.81% error — count millions of uniques (e.g. daily uniques) without storing them. Trades exactness for tiny memory.

Bitmap (SETBIT/BITCOUNT)

A string used as a bit array. 1 bit per user → daily active users, A/B flags, presence — extremely memory-cheap.

Geospatial (GEOADD/GEOSEARCH)

Store lon/lat (backed by a ZSet of geohashes); query "what's within N km of this point". Powers nearby-search.

05Expiration & eviction

How TTLs are reclaimed

Set a TTL with EXPIRE k 60 / SET k v EX 60 / PEXPIRE (ms). Redis frees expired keys two ways, combined:

① Lazy (passive)

On access, if a key is found expired, it's deleted then and the command behaves as if the key was gone. Cheap, but expired-yet-untouched keys linger in RAM.

② Active (sampling)

A background cycle ~10×/sec samples keys with TTLs and deletes the expired ones; if a high fraction were expired, it repeats. Probabilistic — keeps stale-key memory bounded.

Eviction when maxmemory is hit

When memory fills, the maxmemory-policy decides what to drop:

PolicyBehavior
noevictionReject writes with an error (safe default for a DB role)
allkeys-lru / allkeys-lfuEvict least-recently / least-frequently used across all keys — classic cache mode
volatile-lru / -lfu / -ttl / -randomSame, but only among keys that have a TTL set
allkeys-randomEvict random keys
For a pure cache, use allkeys-lru (or lfu for skewed access). For Redis as a primary store, use noeviction so you never silently lose data. LFU (since 4.0) tracks frequency with a decaying counter — better for "popular forever" items that LRU would wrongly evict.

"Atomic" gets thrown around loosely. Be precise about the four mechanisms and what each guarantees:

Like updating your bank balance: if you read $100, then walk away, then write $90 — but someone deposited $50 while you were gone — you just erased their deposit. INCR/Lua/WATCH are the "do the read and write without leaving the counter" guarantees.
Key gotcha: commands like GET then SET from your app are two round trips — another client can sneak in between. To make "read-modify-write" atomic you need INCR (if it's just math), a Lua script, or WATCH/MULTI.

07Transactions: MULTI / EXEC / WATCH

A Redis transaction queues commands after MULTI and runs them as one isolated unit at EXEC. No other client interleaves. But it is not a SQL transaction: there's no rollback. If a command fails logically at runtime (e.g. INCR on a string), the others still apply.

WATCH balance              # optimistic lock: watch a key
val = GET balance          # read
MULTI                      # begin queuing
SET balance {val-100}      # queued (not yet run)
EXEC                       # runs ONLY if 'balance' was not
                           # modified since WATCH; else returns nil → retry
sequenceDiagram participant App participant R as Redis App->>R: WATCH balance App->>R: GET balance → 500 App->>R: MULTI App->>R: SET balance 400 (queued) Note over R: another client changes balance? App->>R: EXEC alt watched key untouched R-->>App: [OK] ✅ applied else watched key changed R-->>App: (nil) ❌ aborted → retry end
This is Redis's optimistic concurrency control (compare-and-set). Contrast with a pessimistic distributed lock. For most read-modify-write, a Lua script is simpler than WATCH retry loops because it's a single atomic server-side execution with no contention loop.

08Lua scripting & Functions

Send logic to the server with EVAL / EVALSHA (or persistent FUNCTION in 7+). The entire script runs atomically — nothing interleaves — so you can do read → decide → write safely in one shot, server-side, in one round trip.

-- Atomic "decrement stock if available" (oversell-proof)
-- KEYS[1]=stock key, ARGV[1]=qty
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock and stock >= tonumber(ARGV[1]) then
  return redis.call('DECRBY', KEYS[1], ARGV[1])   -- success
else
  return -1                                        -- not enough
end
Why it wins: no network round trips mid-logic, no race window, fewer client/server hops. Use EVALSHA with a cached SHA to avoid resending the body.
Keep scripts short — they block the single thread like any command. Always pass keys via KEYS[] (not hardcoded) so Cluster can route correctly.

09Distributed locks

The canonical pattern: SET lock:resource <random-token> NX EX 30. NX makes acquisition atomic; EX guarantees the lock self-expires if the holder crashes (no permanent deadlock).

# acquire
SET lock:order:42 $token NX EX 30      # ok / nil

# release — MUST be atomic check-then-delete (Lua),
# so you only delete YOUR lock, not one that already expired & got reacquired
if redis.call('GET', KEYS[1]) == ARGV[1]
then return redis.call('DEL', KEYS[1]) else return 0 end
Three classic mistakes: (1) no TTL → deadlock on crash; (2) deleting by key without checking the token → you delete someone else's lock after yours expired; (3) work outlasting the TTL → two holders at once (mitigate with a watchdog that extends TTL).
Redlock: for locking across multiple independent Redis masters, Martin Kleppmann's critique is famous — single-instance locks aren't safe under GC pauses/clock skew for correctness-critical sections. Say: "for efficiency locks, single-instance SET NX EX is fine; for correctness I'd use a real consensus system (ZooKeeper/etcd) or a fencing token."

10Persistence — RDB vs AOF

RAM is volatile, so Redis offers two on-disk mechanisms. You can run either, both, or neither.

RDB — point-in-time snapshot compact

Forks the process and dumps the whole dataset to a binary dump.rdb file periodically (e.g. save 900 1). Uses copy-on-write so the main thread keeps serving.

+ tiny files, fast restart/load, great for backups & replication bootstrap.
− you lose everything written since the last snapshot on a crash.

AOF — append-only command log durable

Logs every write command to a file, replayed on restart. appendfsync controls flushing: always (safest, slowest), everysec (default — ≤1s loss), no (OS decides).

+ minimal data loss, human-readable-ish.
− bigger files, slower restart. Periodic rewrite compacts it.

RDB = taking a photo of your desk every hour: small, quick to restore, but you lose whatever you scribbled since the last photo. AOF = keeping a diary of every single thing you wrote: replay it to rebuild exactly, but the diary gets long. Pros keep both — a recent photo to load fast, plus the diary's last page for the gap.
Production recommendation: enable both. Redis 7 uses a hybrid rewrite — the AOF starts with an RDB preamble (fast load) then appends recent commands (low loss). Best of both. Note: persistence ≠ backup — copy the files off-box.

11Replication & read/write split

A replica (REPLICAOF host port) maintains a copy of a master. Replication is asynchronous: the master replies to the client immediately, then streams writes to replicas. This gives read-scaling and a hot standby — at the cost of possible brief staleness.

How a replica syncs

  1. Full sync (PSYNC): on first connect (or if too far behind), master forks an RDB snapshot, ships it, and buffers new writes in a replication backlog, then streams them.
  2. Partial resync: after a brief disconnect, the replica asks to resume from its offset; if still in the backlog buffer, only the gap is sent — no full snapshot.
Asynchronous = you can lose acknowledged writes. If the master crashes after replying but before replicating, that write is gone after failover. WAIT numreplicas timeout lets you block until N replicas ack — stronger durability, higher latency. True synchronous replication is not Redis's model.
The master is the teacher writing on the board; replicas are students copying it into their notebooks. Students can answer questions (reads scale!), but there's a split-second where the teacher wrote something the back row hasn't copied yet — that's replication lag. If the teacher faints before the back row copies the last line, that line is lost (async = possible data loss).
Read-your-own-writes caveat: reading from a replica right after writing to the master may return stale data due to lag. Solutions: route critical reads to the master, or use WAIT, or accept eventual consistency. Always articulate this trade-off.

12Sentinel — automatic failover (HA)

Replication alone gives you a standby but no automatic promotion. Sentinel is a separate set of monitoring processes that watch the master, agree (via quorum) when it's down, elect a leader Sentinel, promote a replica to master, and tell clients about the new topology.

Sentinels are security guards watching the boss (master). One guard noticing the boss is unresponsive isn't enough (SDOWN — could be the guard's bad eyesight). Only when a majority vote agrees the boss is really down (ODOWN) do they promote the deputy (a replica) and announce the new boss to everyone. Odd number of guards so a vote can't tie.
Key terms: SDOWN = one Sentinel thinks it's down; ODOWN = quorum agrees → triggers failover. Run an odd number (≥3) of Sentinels on separate hosts so the majority vote survives a split. Clients connect through Sentinel-aware libraries to always find the current master.
Sentinel vs Cluster: Sentinel = HA for a single shard (one dataset, master+replicas, auto-failover) — does not shard data. Cluster = HA plus horizontal sharding. If your data fits one node and you just need failover, Sentinel is simpler.

13Cluster — horizontal sharding

When data or throughput exceeds one machine, Redis Cluster shards the keyspace across multiple masters, each with its own replicas. There's no proxy — clients talk directly to the right node.

The 16384 hash slots

The keyspace is partitioned into a fixed 16384 slots. A key's slot = CRC16(key) mod 16384. Each master owns a contiguous range of slots. To find a key's node: compute its slot, look up which master owns that slot.

Imagine a library with 16,384 numbered shelves split across 3 buildings. A book's shelf number is decided by a formula on its title (CRC16). To grow, you don't renumber every book — you just hand some shelf ranges to a new building (resharding). Want two related books guaranteed in the same building? Put a {tag} in both titles so they hash to the same shelf zone.

MOVED / ASK redirection

If a client hits the wrong node, the node replies MOVED <slot> host:port (permanent — slot lives elsewhere) or ASK (temporary — slot is mid-migration). Smart clients cache the slot map and route directly; they only get redirected when the topology changes.

Multi-key ops must share a slot. MGET a b, SINTER, transactions, and Lua across keys only work if all keys hash to the same slot. Force that with a hash tag: {user:42}:profile and {user:42}:cart — only the part in {} is hashed, so both land together.
ConcernHow Cluster handles it
Sharding16384 slots spread across masters; key → CRC16 → slot → node

ReshardingMove slots between nodes live; keys migrate, ASK redirection covers the window

Why 16384 and not more? The gossip heartbeat carries a bitmap of each node's slots; 16384 bits = 2 KB, small enough to ship cheaply between nodes, while still being far more than any realistic node count so slots distribute evenly. Classic trivia — worth memorizing.
Decision tree: single node fits + want HA → Sentinel. Data/throughput too big for one node → Cluster. Just a cache, can tolerate loss → maybe neither, just replicas.

15Rapid-fire cheat sheet

Why fast?

RAM + single-thread (atomic, lock-free) + epoll event loop + efficient structures + RESP protocol + pipelining.

O(N) commands to avoid on hot paths

KEYS *, HGETALL, SMEMBERS, LRANGE 0 -1, FLUSHALL (sync). Prefer SCAN family, UNLINK over DEL for big keys.

Atomic toolkit

Single cmd · INCR · MULTI/EXEC · WATCH (CAS) · Lua EVAL.

Pick the type

Counter → String/INCR · object → Hash · queue → List/Stream · uniqueness/tags → Set · ranking/leaderboard/rate-limit → ZSet · uniques-count → HLL · presence flags → Bitmap · geo → GEO.

HA / scale decision

Failover only → Sentinel. Shard + failover → Cluster (16384 slots, hash tags for multi-key). Read scale → replicas (async, can be stale).

Durability dial

RDB (snapshot, fast, lossy) + AOF (log, ≤1s loss) → run both / hybrid. WAIT for stronger replica ack.

One-line summaries to have ready: "Redis is single-threaded so every command is atomic." · "Replication is async, so failover can lose unacked writes." · "Transactions queue + isolate but don't roll back." · "Cluster shards into 16384 slots via CRC16; multi-key needs same slot." · "Sentinel = HA for one shard; Cluster = HA + sharding." · "For a cache use allkeys-lru; as a DB use noeviction."

17Boss-level questions EXPERT

The ones that separate "used Redis" from "understands Redis." Think first, then tap to reveal.

Why exactly 16384 slots — why not a million? MEDIUM
Nodes gossip their slot ownership as a bitmap in every heartbeat. 16384 bits = 2 KB per message — cheap to send constantly. A million slots would bloat every heartbeat. 16384 is still vastly larger than any realistic node count, so slots spread evenly. Sweet spot of "big enough to balance, small enough to gossip."
Your hottest key expires at midnight and 10k requests stampede the DB. Fix it. HARD
That's cache breakdown. Options: (1) mutex — first miss acquires a lock (SET NX) and rebuilds; others briefly wait or serve stale. (2) Logical expiry — never physically expire the key; store an "expires-at" field, and on read if it's logically stale, one thread async-refreshes while everyone keeps serving the old value. (3) Pre-warm + randomized TTL so hot keys don't all die together (that last one also prevents avalanche).
How do you make read-modify-write atomic across the network — and why is WATCH often the wrong tool? MEDIUM
Lua / EVAL is usually best: the whole read→decide→write runs server-side in one atomic shot, one round trip, zero race window. WATCH/MULTI is optimistic CAS — it aborts & you retry if the watched key changed, which under contention becomes a retry storm and extra round trips. Use INCR/HINCRBY if it's pure math; Lua for conditional logic; WATCH only for occasional low-contention cases.
Is a Redis distributed lock actually safe? HARD
For efficiency (avoid duplicate work) — yes, SET NX EX + Lua release is fine. For correctness (must never have two holders) — no, single-instance isn't bulletproof: a GC pause or clock skew can let your lock expire while you think you hold it. Redlock (multi-master) was proposed but Kleppmann's critique shows it's still not safe under those conditions. The honest answer: use a fencing token (monotonic number checked by the resource) or a real consensus store (etcd/ZooKeeper) for correctness-critical locks.
Master fails. Walk me through what Sentinel does, second by second. MEDIUM
(1) Sentinels PING the master; one stops getting replies → marks it SDOWN (subjective). (2) It asks the others via gossip; once a configured quorum agrees → ODOWN (objective). (3) Sentinels elect a leader (Raft-ish). (4) Leader picks the best replica (most up-to-date, lowest priority number) and sends REPLICAOF NO ONE to promote it. (5) Other replicas are re-pointed at the new master; clients querying Sentinel get the new address. Brief unavailability + possibly a few lost async writes.
You set 1M keys to expire but RAM barely drops. Why? MEDIUM
Expiry is lazy + active-sampling, not instant. Untouched expired keys linger until either accessed (lazy) or caught by the ~10Hz sampling cycle (which only deletes a probabilistic batch). For a hard bulk purge, delete explicitly (UNLINK for big keys to free async), or rely on maxmemory+eviction. Also: deleting/expiring is itself work on the single thread, so a giant simultaneous expiry can cause latency spikes.
When is single-threaded a real bottleneck, and what do you do? HARD
When one core's worth of command execution is saturated, or a single big O(N) command stalls everything. Fixes: shard with Cluster (more masters = more cores), eliminate O(N) hot commands (SCAN not KEYS, avoid huge HGETALL), pipeline to amortize round trips, move CPU-heavy work out of Lua, and lean on Redis 6+ threaded I/O for the socket layer. Note the keyspace mutation stays serial by design — you scale out, not up the exec thread.
