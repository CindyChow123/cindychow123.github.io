01关系模型

关系型数据库以表（关系）的形式存储数据：行（元组/记录）配上列（属性），每一列都有固定的类型，表与表之间通过键关联。你用声明式 SQL 描述想要什么，至于怎样高效地把数据取出来，交给数据库的查询规划器去想。正是这种分工，加上强一致性保证（ACID），让关系型数据库成了凡是讲究正确性的系统的默认之选。

"用 SQL 还是 NoSQL？"——如果要在带关联关系的结构化数据（订单、支付、库存）上做多行事务、连接和强一致性，就用关系型；如果要的是海量水平扩展、灵活或稀疏的模式，或者只有某种固定的访问模式（KV、文档、宽列）且能放宽一致性，那就用 NoSQL。

02键与约束

约束是数据库替你把数据完整性兜底的手段，省得你去指望应用代码永远不出错。

约束保证
PRIMARY KEY唯一 + NOT NULL 的行标识符。每张表一个。通常就是聚簇键。
FOREIGN KEY某列的值必须在被引用的表里真实存在，也就是引用完整性。支持 ON DELETE CASCADE/RESTRICT/SET NULL。
UNIQUE无重复值（视引擎可允许一个或多个 NULL）。由唯一索引支撑。
NOT NULL值必填。
CHECK任意布尔规则，例如 CHECK (price >= 0)。MySQL 从 8.0.16 起才真正强制执行。
DEFAULT未提供值时使用的默认值。

自然键 vs 代理键

自然键取自数据本身（邮箱、身份证号），代理键则是人造的 id（自增 BIGINT / SERIAL / IDENTITY，或 UUID）。代理键通常更适合做稳定的主键，因为自然值会变、还可能很长。

用 UUID 做主键要当心：随机的 UUID v4 主键会破坏聚簇索引的写入局部性（插入点四处乱跳，导致页分裂和碎片化）。优先用自增 BIGINT；确实需要全局唯一键时，改用按时间有序的 ID（UUID v7 / ULID / Snowflake）。

03SQL 结构与逻辑执行顺序

SQL 分为几个子语言：DDL（定义：CREATE/ALTER/DROP）、DML（操作：SELECT/INSERT/UPDATE/DELETE）、DCL（控制：GRANT/REVOKE）、TCL（事务：BEGIN/COMMIT/ROLLBACK）。

最有用、也最该烂熟于心的一点是：一条 SELECT 的书写顺序和它的逻辑执行顺序并不一样。这就解释了为什么 SELECT 里定义的别名不能用在 WHERE 里，却能用在 ORDER BY 里。

SELECT customer_id, COUNT(*) AS orders, SUM(total) AS revenue
FROM   "order"
WHERE  created_at >= '2026-01-01'      -- 先过滤行（可用索引）
GROUP  BY customer_id                  -- 然后分组
HAVING SUM(total) > 1000               -- 然后过滤分组
ORDER  BY revenue DESC                  -- 这里可以用别名
LIMIT  10;

05聚合与分组

聚合函数把多行压成一个值，GROUP BY 则为每个分组输出一行。

函数说明
COUNT(*) vs COUNT(col)* 统计行数；col 跳过 NULL。COUNT(DISTINCT col) 统计去重值。
SUM / AVG / MIN / MAX忽略 NULL。AVG = 非 NULL 值的 SUM/COUNT。
STRING_AGG PG / GROUP_CONCAT MySQL把分组内的多个值拼成一个字符串。
FILTER (WHERE ...) PG条件聚合，例如 COUNT(*) FILTER (WHERE status='paid')。
NULL 不是零，也不等于任何值。NULL = NULL 的结果是未知，而不是真，所以判空要用 IS NULL，替换则用 COALESCE(x, 0)。COUNT(*) 会把含 NULL 的行也算进去；对一列全是 NULL 的值求 SUM，返回的是 NULL 而不是 0。
GROUP BY 的严格程度：在标准 SQL 和 PG 里，SELECT 中每个非聚合列都必须出现在 GROUP BY 里。MySQL 早年允许宽松分组（随便取一个值），除非开了 ONLY_FULL_GROUP_BY（5.7+ 默认开启）。

06子查询、CTE 与窗口函数

子查询

就是套在另一个查询里的查询。分为标量子查询（返回单个值）、IN / EXISTS（判断是否存在），以及关联子查询（引用了外层的行——外层每来一行就执行一次，可能很慢）。

做大数据量或关联性的存在判断时，EXISTS 往往比 IN 快，因为它一找到匹配就短路返回。还要当心 NOT IN 碰上 NULL——只要集合里有一个 NULL，整个表达式就会一行都返回不了。

CTE（WITH）

公用表表达式（Common Table Expression）给子查询起个名字放在前面，既提升可读性，又能支持递归（处理层级、图结构）。

WITH RECURSIVE subordinates AS (
  SELECT id, manager_id, name FROM employee WHERE id = 1   -- 锚定部分
  UNION ALL
  SELECT e.id, e.manager_id, e.name                          -- 递归部分
  FROM employee e JOIN subordinates s ON e.manager_id = s.id
)
SELECT * FROM subordinates;
PG 早年会把 CTE 物化（相当于一道优化围栏）；从 PG12 起，除非你显式写 WITH ... AS MATERIALIZED，否则 CTE 可以被内联。当某个 CTE 莫名其妙地让索引用不上时，知道这一点就很有用。

窗口函数

它在与当前行相关的一组行上做计算，但不像 GROUP BY 那样把这些行压成一行。做分析、排名、累计、去重时，它就是一项利器。

SELECT name, dept, salary,
  RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
  AVG(salary)  OVER (PARTITION BY dept)                       AS dept_avg,
  SUM(salary)  OVER (ORDER BY hired_at)                       AS running_total
FROM employee;
窗口函数用途
ROW_NUMBER()连续不重复的编号——很适合做"每组只保留最新一条"的去重
RANK / DENSE_RANK排名，遇到并列时分别留间隙 / 不留间隙
LAG / LEAD取上一行 / 下一行的值（算差值、看趋势）
NTILE(n)把行均分成 n 个桶（分位数）
"每组取前 N 条（Top-N per group）"是一道高频 SQL 面试题。套路是：先在子查询或 CTE 里写 ROW_NUMBER() OVER (PARTITION BY group ORDER BY metric DESC)，再用 WHERE rn <= N 过滤。

08范式化（以及何时反范式）

范式化靠合理地组织列来消除冗余和更新异常。每一种"范式"都建立在前一种之上，规则一级比一级严。

范式规则（通俗版）解决的问题
1NF每个值都是原子的；列里不放重复组或数组把 "tags: a,b,c" 塞进一个单元格
2NF1NF + 不存在对复合键的部分依赖某列只依赖主键的一半
3NF2NF + 不存在传递依赖（非键 → 非键）订单表里由 zip 决定 city
BCNF更严格的 3NF：每个决定因素都得是候选键候选键彼此重叠的少见边界情况
范式化说白了就是"同一个事实别写两遍"。客户地址只在 customer 里存一份，每个订单都指向它——改地址只需改一处，不用在成千上万行里一处处改（漏改就成了"更新异常"）。
反范式化则是有意反着来：故意复制数据（比如在 customer 上缓存一个 order_count，或者存一个大的 JSONB 字段），好在读多的热路径上省掉昂贵的连接。这是拿写入的复杂度和一致性风险，去换读取速度。原则是：先范式化，只有当数据指标真有需要时才反范式。
OLTP（事务型）系统默认奔着 3NF 去——写入干净、完整性好。分析型 / OLAP 系统则常反范式成星型模式（事实表 + 维度表），把聚合做快。关键是搞清楚自己在为哪种负载做设计。

聚簇索引 vs 二级索引 InnoDB PG heap

聚簇索引 MySQL/InnoDB

表里的行本身就存在主键 B+tree 里（叶子节点直接保存整行），每张表一个，所以主键查找极快。二级索引存的是主键值而不是行指针——因此一次二级查找要跳两跳：二级索引 → 主键 → 行。

堆 + 二级索引 PostgreSQL

行散放在无序的堆里，每个索引（主键也算）都指向行的物理位置（ctid），默认没有"聚簇"表的概念。当查询要的列全在索引里（且可见性映射允许）时，覆盖扫描 / 仅索引扫描就能跳过堆。

索引类型与变种

索引是什么 / 何时用
复合索引 (a,b,c)多列联合。最左前缀规则：能用于 a、a,b、a,b,c，但不能单独用于 b。列的顺序很关键！
覆盖索引索引里包含了查询要的全部列，光靠索引就能出结果，不用回表。对应 PG 的 INCLUDE 列。
唯一索引既保证唯一性，又加速查找。
部分 / 过滤索引 PG只给满足某条件的行建索引，例如 WHERE active，索引更小、更快。
哈希索引只支持 O(1) 等值查找（不支持范围）。用得少。
GIN / GiST PG用于全文、JSONB、数组、几何/范围数据。MySQL 对应的是 FULLTEXT、SPATIAL。

为什么索引没被用上

  • 列上套了函数：WHERE YEAR(created_at)=2026 用不上 created_at 的索引——改写成范围条件，或者加一个表达式索引。
  • 前导通配符：LIKE '%foo' 没法走索引定位；'foo%' 则可以。
  • 隐式类型转换：拿字符串列去和数字比较，会被迫全表扫描。
  • 选择性太低：如果某个值能匹配到大多数行，规划器会很合理地选择全表扫描。
索引不是白来的。每个索引都得在每次 INSERT/UPDATE/DELETE 时同步更新，还占空间。索引建太多会拖慢写入。按真实的查询模式来建，没用上的就删掉。

12ACID —— 事务的契约

事务把一组语句打包成一个要么全做、要么全不做的整体（BEGIN ... COMMIT/ROLLBACK）。ACID 说的就是它给你的几条保证：

A —— 原子性（Atomicity）

所有语句要么全部提交，要么一条都不提交。中途出错就把改动全部回滚。（靠 undo 日志 / 回滚段实现。）

C —— 一致性（Consistency）

事务让数据库从一个合法状态进入另一个合法状态——约束、外键、触发器一个都不破。（你定的不变量 + 数据库自身的规则。）

I —— 隔离性（Isolation）

并发事务互不干扰，结果看起来就像它们曾按某个串行顺序一个个跑过。隔离到什么程度由隔离级别决定（见下一节）。

D —— 持久性（Durability）

一旦提交，崩溃或断电也丢不了。（靠在提交返回前对预写日志做 fsync 实现。）

事务就好比一次银行转账：一个账户扣钱，另一个账户入账。原子性保证你绝不会只扣钱不入账（钱不会凭空蒸发）；持久性保证回执一旦打出来，断电也撤不回；隔离性保证两笔同时进行的转账，谁都看不到对方做了一半的中间状态。

13隔离级别与异常

隔离越强，能出的异常越少，但加锁和争用也越多。SQL 标准按"各级别允许哪些异常"定义了四个隔离级别。

级别脏读不可重复读幻读

这几种异常，说白了就是

  • 脏读（Dirty read）——你读到了另一个事务还没提交、之后还可能回滚掉的改动。
  • 不可重复读（Non-repeatable read）——同一行你读两次，值却不一样（期间有人提交了更新）。
  • 幻读（Phantom read）——同一个范围查询重跑一遍，凭空多出了几行（有人插入了符合条件的新行）。
  • 写偏斜（Write skew）——两个事务各读了一份共享状态，再分别据此写入，最终得到一个在任何串行顺序下都不可能出现的结果（只有 Serializable 能挡住）。
面试时值得点出来的引擎细节： MySQL/InnoDB 默认是 Repeatable Read，并靠 next-key 锁（间隙锁 + 行锁）在很大程度上堵住了幻读。PostgreSQL 默认是 Read Committed；它的 Repeatable Read 走的是快照隔离（挡住不可重复读和幻读，但放过写偏斜 / 序列化异常）；它的 Serializable 用的是 SSI（可串行化快照隔离），可能因序列化冲突而中止事务，需要你自己重试。
最好能随手举一个写偏斜的例子：两名值班医生各自确认"还有 ≥1 名其他医生在岗"，于是同时下班 → 结果没人值班了。两次读取单看都成立，可它们凑在一起就出了问题。只有 SERIALIZABLE（或显式加锁）才挡得住。

MVCC —— 多版本并发控制

核心思想是：读不挡写，写也不挡读。数据库不在原地覆盖，而是为一行保留多个版本。每个事务看到的，都是它开始那一刻（或语句那一刻）的一致快照。写者去创建新版本时，读者照样读得到旧版本。

PostgreSQL 的 MVCC

新版本的行直接写进堆，旧版本一直留着，直到 VACUUM 把它们回收。可见性靠事务 id（xmin/xmax）判断。代价是表膨胀，以及离不开（自动）vacuum。

MySQL/InnoDB 的 MVCC

当前版本的行存在表里，旧版本则从 undo 日志（回滚段）临时重建，由 purge 线程清理。事务一长，undo 历史就会越积越多。

长事务是 MVCC 的天敌。一个迟迟不结束的事务一直握着旧快照，数据库就没法回收比它更新的那些行版本——结果要么膨胀（PG），要么 undo 撑得很大（MySQL），性能随之下滑。事务要短；别 BEGIN 之后还杵在那儿等一个慢吞吞的外部调用。

18高可用与故障切换

光有复制，也只是多了个备库；还得有东西能察觉主库挂了，把某个从库提升为新主，再把流量切过去。这一整套调度编排，就是高可用（HA）。

要先想清楚两个目标：RPO（恢复点目标——最多能容忍丢多少数据）和 RTO（恢复时间目标——多久能恢复服务）。异步复制 → RPO > 0；同步复制 → RPO ≈ 0，但要拿延迟来换。这两个指标基本框定了每一场 HA 设计的讨论。

19分区与分片

有两个"拆分数据"的概念常被人混为一谈：

分区（单台服务器）

按某个键把一张大表切成几块，但这些块仍在同一个数据库里。只命中某个分区的查询会跳过其余分区（分区裁剪），旧分区也能瞬间删掉。可以按范围（日期）、列表（地区）或哈希来分。

分片（多台服务器）

把数据分散到多个相互独立的数据库服务器上，让写入和存储突破单台机器的上限。每个分片本身就是一个完整的数据库，按分片键持有其中一部分行。

20连接池

每个数据库连接都要占内存，而且在 PG 里还对应一个后端进程。每来一个请求就新开一个连接，既慢，又会很快把服务器的 max_connections 耗光。连接池的做法是维持一批热连接，按需分发出去。

PostgreSQL 对此尤其敏感（每个连接一个进程）——上了规模，PgBouncer 几乎是标配。MySQL 用的是线程（更轻），但用上应用侧连接池（HikariCP）或 ProxySQL 同样有好处。连接池有两种模式：会话级（连接绑定给客户端会话）和事务级（每个事务结束就归还——并发能高出一大截，但会破坏预处理语句、SET 这类依赖会话状态的特性）。
经验法则：合理的连接池往往比大家以为的要小。活跃连接一旦超过大约（核数 × 2–4）个，你换来的就是上下文切换的争用，而不是更高的吞吐量。让请求在池子这一端排队，别把连接一股脑堆到数据库上。

22安全要点

SQL 注入 —— 头号风险

把用户输入直接拼进 SQL，等于让攻击者有机会改写你的查询（'; DROP TABLE users;--）。修复办法没得商量：参数化查询 / 预处理语句——驱动会把 SQL 和数据分开传，输入永远不会被当成代码来解析。绝不要拿用户输入去拼 SQL 字符串；ORM 能帮上忙，但你仍然得避开裸的字符串拼接。

-- ❌ 可被注入
"SELECT * FROM users WHERE email = '" + input + "'"
-- ✅ 参数化
"SELECT * FROM users WHERE email = $1"   // 单独绑定输入

访问控制

  • 最小权限：应用角色只授予它真正需要的权限（别给 SUPERUSER/GRANT ALL），并单独拆出只读角色。
  • 行级安全（RLS） PG：用策略限制某个角色能看到哪些行——很适合在数据库这一层做多租户隔离。
  • 加密：传输走 TLS；静态数据做加密（TDE / 磁盘）；密码用 bcrypt/argon2 做哈希，绝不明文存密钥。
被问到"你怎么防 SQL 注入"，标准答案就一个词：参数化（预处理语句 / 绑定变量），而不是"转义"或"校验"——那些只是纵深防御，真正能根治的是参数绑定。

带我走一遍：我执行 COMMIT 时，磁盘上和内存里到底发生了什么。MEDIUM
这时变更早已落在缓冲池 / shared_buffers（RAM）的页面上，并记进了 WAL/redo 日志缓冲区。COMMIT 一来：截至这次提交的 WAL 记录被刷盘并 fsync 到持久化存储——只有完成这一步，COMMIT 才返回成功。被改过的数据页在内存里还是脏的，要等到之后的检查点时才异步写入真正的数据文件。万一服务器在那之前崩了，恢复时会从上一个检查点重放 WAL，把已提交的变更重做、未提交的回滚。这样一来，不必每次提交都做随机写，也照样拿到了持久性。
有条查询很慢。说说你从头到尾的排查流程。MEDIUM
（1）先找到它：慢查询日志 / pg_stat_statements / APM。（2）跑 EXPLAIN ANALYZE：揪出大表上的全表 / 顺序扫描、离谱的行估算（估算和实际差太多 → 统计信息过时，跑一下 ANALYZE）、昂贵的排序、行数很大的嵌套循环（内表那一侧缺索引）。（3）动手修：加索引或调索引（留意选择性和最左前缀规则）、让谓词可 sargable（列上别套函数）、少选几列以触发覆盖 / 仅索引扫描，或者改写查询（EXISTS vs IN、键集分页）。（4）再测一遍。（5）跳出来看全局：是不是应用侧的 N+1？连接池是不是满了？机器是不是 I/O 撑爆了？别闭着眼睛乱加索引——每个索引都要给写入交"税"。
两个事务都读到余额 100，各自减去 100，结果两个都"成功"了。这怎么发生的？你怎么防？HARD
这是弱隔离下的丢失更新（lost update）——两个事务读改写同一行，是写偏斜的一种特例（写偏斜更一般地指两个事务基于同一份读取去写不同的行）。在 Read Committed 下，两个事务都读到 100，都算出 0，都写回 0——其中一次更新其实被覆盖丢掉了，余额成了 0，而不是本应被拒绝的 -100。怎么防：（a）原子写入——用 UPDATE acct SET bal = bal - 100 WHERE id=? AND bal >= 100 并检查受影响行数；（b）悲观锁——用 SELECT ... FOR UPDATE 把它们串行化；（c）乐观并发——加一个 version 列，更新时带上 WHERE version = :read，对不上就重试；（d）SERIALIZABLE 隔离（PG 的 SSI 会中止其中一个事务 → 重试）。把计算直接写进 UPDATE 这招最简单，从根上避开了"先读后写"的竞态。
PostgreSQL 为什么需要 VACUUM，"膨胀（bloat）"又是什么？HARD
PG 的 MVCC 在更新 / 删除时会写一个新的行版本，把旧版本留在堆里标记为"死"，好让并发的快照还能看到它。VACUUM 负责回收这些死元组的空间供后续复用，同时更新可见性映射（从而支持仅索引扫描），由 autovacuum 自动来做。一旦死元组堆积的速度超过 vacuum 回收的速度（改动太频繁，或者一个握着旧快照的长事务挡住了清理），表和索引就会膨胀——撑得远比存活数据该有的体积大，拖慢扫描、白占磁盘。还有关键一点：VACUUM 还负责处理事务 id 回卷（wraparound）；它要是落后太多，PG 会强制停写来保护数据。缓解办法：调优 autovacuum、别让会话长时间停在 idle-in-transaction 状态，必要时用 VACUUM FULL/pg_repack 把空间收回来（这会重写整张表）。
你加了读从库，可用户有时看不到自己刚保存的改动。为什么？有哪些办法？MEDIUM
问题在复制延迟：写已经在主库提交，但从库还没应用上，而这次读偏偏被路由到了从库。按力度从强到弱排：（1）把写后紧接的读路由到主库（比如"写完后 N 秒内，该用户的读都黏在主库"）；（2）用日志位点实现读己之所写——记住刚写入的 WAL/GTID 位点，只从已追上该位点的从库读；（3）对这些写入改用同步复制（代价是延迟）；（4）在用户体验能接受的地方，干脆接受最终一致性。通常合理的答案是按操作区别对待：关键读走主库，其余走从库。
你会在什么时候分片？分片之后又有哪些东西会变得不好用？HARD
什么时候分：只有在索引、查询调优、缓存、读从库、分区、纵向扩展统统用尽之后——也就是单个主库实在扛不住写吞吐或数据量的时候。什么会变难：跨分片的连接和事务要么挪到应用层做，要么干脆做不了（或得上 2PC，又慢又脆）；全局唯一性 / 自增得另想办法（UUID / Snowflake / 中心分配器）；再平衡分片、避开热点分片在运维上都很棘手；聚合查询得 scatter-gather。其中分片键怎么选最为关键——要挑一个分布均匀、又能把常一起查的行放在一起的键（比如按 tenant_id，让同一个租户的数据落在同一个分片）。也可以考虑分布式 SQL（Vitess/Citus/CockroachDB/Spanner），用更少的手工折腾换来分片能力。
我执行 SELECT * FROM t WHERE status = 'active'，它却没用我在 status 上建的索引。为什么这有可能是对的？MEDIUM
选择性太低。如果大多数行都是 active，走索引就意味着大量随机回表（索引 → 堆 来回跳），反而比一次顺序的全表扫描更慢。基于代价的优化器从统计信息里估出了这一点，于是很正确地选了顺序扫描。索引被跳过还有别的原因：统计信息过时（跑 ANALYZE）、列上套了函数 / 有隐式转换导致不可 sargable、SELECT * 要取索引里没有的列（于是享受不到仅索引扫描的好处），又或者表本来就小、扫一遍便宜到可以忽略。解法不是"强制走索引"——而是给那个稀有值建一个部分索引、少取几列，或者干脆接受"这次扫描本来就是最优的"。
