01「分布式」到底是什么意思

分布式系统是一组各自独立的机器，它们通过网络相互协调，对用户而言看起来就像一个系统。走向分布式通常出于三个理由：扩展（单台机器扛不住）、可用性（一台机器挂了系统照常运行）和就近（离用户更近）。代价是，计算里所有棘手的东西 —— 故障、时间、顺序、一致性 —— 都被成倍放大。

部分故障
一部分节点挂了，另一部分还在跑 —— 不存在干脆的「整体宕或整体活」
没有时钟
没有共享的全局时间，你无法确信两个事件在不同节点上「谁先谁后」
异步
消息可能被延迟、乱序、重复，甚至丢失

分布式 vs 微服务 —— 不是同一个维度

「分布式」讲的是物理部署（工作被拆到多台机器上）。「微服务」讲的是软件架构（一个应用按业务能力拆成一个个小而可独立部署的服务）。微服务只是构建分布式系统的一种方式：你可以不用微服务也很分布式（比如一个分片数据库），也可以精神上很「微」却并非真正分布式（比如模块化单体）。

分布式系统就像一间有很多厨师的餐厅后厨：比一个大厨更快、更抗造，但现在他们必须协调起来 —— 订单会丢、两个厨师抢同一口锅、没人对得上现在几点。下面每一个主题，都是解决这类协调问题的工具。
把整个领域框定在三个「做不到」上：你躲不开部分故障，你共享不了一个完美时钟，并且（按 CAP）你在分区期间无法同时拥有一致性和可用性。分布式系统，就是为这三件事工程化地给出「足够好」的答案。

02CAP 定理

对于一份在多个节点间复制的数据，下面三者你最多只能同时拥有两个：Consistency 一致性（每次读都能看到最新的写）、Availability 可用性（每个请求都能拿到非错误响应）、Partition tolerance 分区容错（网络被切开时系统照常工作）。

拒绝服务 / 报错（不读到旧数据）"]:::cp CHOOSE -->|保 可用性| AP["AP —— 照样响应，
但可能返回旧数据"]:::ap classDef q fill:#f1e9fc,stroke:#9a6fe0,color:#4a2d7a; classDef ok fill:#e4f5e9,stroke:#3aa856,color:#1d6b32; classDef cp fill:#e7ecfb,stroke:#5b54c7,color:#2a2470; classDef ap fill:#fbeee2,stroke:#c98a3a,color:#7a4a12;
最容易被忽略的一点：P 是不可选的 —— 在任何真实网络里，分区都会发生。所以 CAP 真正的含义是：在分区期间做一道二选一题 —— 选 CP（牺牲可用性 —— 宁可拒绝请求也不返回旧数据），还是 AP（牺牲一致性 —— 保持在线，事后再对账）。所谓「CA」只存在于一个永不分区的单节点里。
选择含义例子
CP一致性优先于可用性；少数派一侧停止服务ZooKeeper、etcd、HBase（Redis Cluster 在多数派一侧偏向这一边）
AP可用性优先于一致性；先响应，事后对账Cassandra、DynamoDB、Eureka、DNS
两位银行柜员之间的电话线断了（分区）。CP：在线路恢复前两人都拒绝取款 —— 不会出现错误余额，但客户得等。AP：两人都按各自最后已知的余额继续办理 —— 没人等待，但在同步之前两边账目可能对不上。
永远别说「我的系统是 CA」。要说：「分区是既定前提，所以这里我选 CP（比如配置 / 锁必须正确），那里我选 AP（比如商品目录必须保持在线）。CAP 是按功能逐项决策的，而不是给整个系统贴一个标签。」

03BASE 与一致性模型

BASE 是 AP 一侧的处事哲学，与数据库的 ACID 相对：Basically Available（基本可用）、Soft state（软状态）、Eventual consistency（最终一致性）。你放弃「此刻永远正确」，换来「永远有应答，并最终收敛到正确」。

基本可用

系统在故障下仍保持响应 —— 也许会降级（变慢、只提供部分功能），但不会整个宕掉。

软状态

即便没有新的写入，节点之间的状态也可能在一段时间内处于「在途 / 不一致」的状态。

最终一致性

停止写入后，假以时日，所有副本都会收敛到同一个值。

一致性的光谱

模型保证取舍
强一致 / 线性一致每次读都能看到最新的写，仿佛只有一份副本慢，需要共识，分区时会阻塞（CP）
读己之写你总能看到自己最新的那次写会话粘连，或读主库
最终一致「晚一点」才收敛，期间读到的可能是旧数据便宜、快、可用（AP）
ACID vs BASE 和 CP vs AP 是同一道取舍题，只是上升了一个层次：当错误数据不可接受时（钱、锁）选 ACID/CP，当在线时长更重要、短暂读到旧数据也无妨时（信息流、商品目录、计数器）选 BASE/AP。

04共识 —— 让节点们达成一致

在部分节点崩溃的情况下，多个节点如何就同一个值（或同一份有序的操作日志）达成一致？这就是共识问题，它是领导者选举、复制状态机、协调服务的底层基石。所有实用的算法都需要凑齐多数派（quorum，法定人数）才能推进 —— 这也正是集群通常采用奇数个节点的原因。

Raft —— 务必烂熟于心的那一个

一句话记住：单点写入控制同步进度，心跳 + 多数投票选主。

Raft 把共识拆成领导者选举和日志复制两块。时间被切成一个个任期（term，逻辑时钟），每个任期至多一个领导者；每个节点要么是 Follower（跟随者）、Candidate（候选人），要么是 Leader（领导者）。

领导者选举

  1. 跟随者会一直期待领导者的心跳。在自己（随机）的选举超时内一个心跳都没等到，它就转成候选人：把任期号加一、先投自己一票，再向其他所有节点发 RequestVote 拉票。
  2. 拿到多数票就当选 Leader。每个节点在每个任期里最多投一票，而且只投给日志至少和自己一样新的候选人——正是这条"选举限制"保证了新领导者一定已经握有全部已提交的日志。
  3. 由于超时是随机的，选票被瓜分（谁都没过半）很少见，而且能自愈：各节点在不同时刻超时，下一轮通常就有人胜出。

日志复制

  1. 所有客户端写入都发给领导者；它先把这条记录追加到自己的日志（尚未提交），再用 AppendEntries 同步给跟随者——空的 AppendEntries 同时就当心跳。
  2. 一旦多数节点都存下了它，领导者就提交这条记录、应用到状态机、给客户端回复，并推进自己的提交位点（commit index）——再把这个位点告诉跟随者，让它们也跟着应用。
  3. 日志匹配：每条 AppendEntries 都带着前一条日志的下标和任期；跟随者一旦对不上就拒绝，于是领导者把 nextIndex 往回退、重发，直到对齐为止，其间会覆盖跟随者那些冲突的条目。这样各节点日志收敛，已提交的记录永不丢失。

Raft 里容易绕晕的几个词

术语到底指什么
append → commit → apply一条日志的三个阶段：追加（append）= 写进日志，但还暂定（可能丢）；提交（commit）= 多数派存下了 → 从此永久、再也不会丢或改；应用（apply）= 真正作用到状态机上（并回复客户端）。只有已提交的条目才会被应用。
commitIndex最高的已提交位置——每个节点都按序把日志应用到这里为止。
nextIndex[跟随者]每个跟随者一个的游标 = 领导者下一条要发给它的日志。日志对不上时领导者把它往回退、重发，所以同一条 AppendEntries 既追加新日志、又补齐落后的跟随者——Raft 不需要单独的"同步"协议（空的 AppendEntries 也就是心跳）。
"发现更高的任期"每条 RPC 都带着发送方的任期。任何节点——哪怕是被分区隔开的旧领导者——一旦收到更高的任期，就退回成 Follower；于是旧领导者发现自己已被取代，绝不会有两个领导者同时提交。
Raft 就像一支每一轮（任期）靠多数票推选队长的球队。队长喊出每一次战术（写入），而一次战术只有在队里大多数人都记下来之后才算数。要是队长突然没声了，就会有人超时并发起新一轮选举。

Paxos —— 最早，也出了名地难

三种角色：提议者（Proposer）提出值，接受者（Acceptor）投票，学习者（Learner）只负责获知结果。Basic Paxos 让整个集群就一个值达成一致，分两个阶段、每个阶段都要凑齐多数派——可以这么理解：阶段一 = 占个坑，并打听有没有值已经被选定了；阶段二 = 真正把值敲定下来。（全程记住：n 是提案编号——只是个递增序号，用来给互相竞争的提案排序，不是数据；v 才是要达成一致的那个值。被选定、并交给 Learner 的是 v，永远不是 n。）

  1. 准备 / 承诺（Prepare / Promise，阶段一 —— 占坑）：提议者挑一个不断递增的编号 n，发出 Prepare(n)。一个还没见过更大编号的接受者会承诺不再接受任何更小编号的提案，并把它已经接受过的、编号最大的那个值回报上来（如果有的话）。这一步既占住了 n，又把可能已经在流转的值探了出来。
  2. 接受 / 已接受（Accept / Accepted，阶段二 —— 敲定）：Accept(n, v) 就是提议者对接受者说"请投票，接受编号 n 下的值 v"。关键在于：v 并不能随便填——只要有任何一个承诺回报了已接受的值，提议者就必须沿用其中编号最大的那个（只有都没有时，才能用自己的值）。接受者只要之后没再承诺过更大的 n，就接受它。一旦多数派都接受了 (n, v)，v 就被选定。
sequenceDiagram participant P as 提议者 participant A1 as 接受者 1 participant A2 as 接受者 2 participant A3 as 接受者 3 Note over P,A3: 阶段一 —— Prepare / Promise P->>A1: Prepare(n) P->>A2: Prepare(n) A1-->>P: Promise(n)，暂无已接受值 A2-->>P: Promise(n)，暂无已接受值 Note over P,A3: 阶段二 —— Accept / Accepted P->>A1: Accept(n, v) P->>A2: Accept(n, v) A1-->>P: Accepted(n, v) A2-->>P: Accepted(n, v) Note over P,A3: 多数已接受，v 被选定

"选定"意味着什么、之后又会怎样：只要多数派接受了某个值，它就在那一刻被选定——而且从此永不改变。接受者把这个结果传播给学习者（Learner），由它们应用并回复客户端。为什么不可变？正是因为上面阶段二那条规则：任何后来的提议者，哪怕编号更大，也会在自己的准备阶段发现这个已选定的值，从而被迫提出同一个 v——于是整个集群永远收敛到同一个值。

Multi-Paxos —— 从一个值到一整条日志

真实系统要达成一致的不是单个值，而是一条有序的命令日志——所以每个日志槽位都是一个独立的 Paxos 实例。给每一条都跑完整两个阶段既慢又容易引发"打架"，于是 Multi-Paxos 选出一个稳定的领导者（一个特定的提议者）：阶段一只做一次，之后每条新记录只需要走阶段二。这个"一个领导者 + 一条只追加的复制日志"的形态，基本就是 Raft 后来用更好懂的方式重新包装的东西。

活锁陷阱（提议者互相打架）

一旦有两个提议者竞争，Basic Paxos 可能永远推进不下去：P1 准备 n=1；P2 准备 n=2（接受者现在都承诺了 2，于是 P1 的 Accept(1,…) 被拒）；P1 改用 n=3 重试（这下 P2 的 Accept(2,…) 又被拒）；两人就这样互相抢占，谁都走不完阶段二。解法就是别再竞争——随机退避，或者干脆选一个唯一的领导者（→ Multi-Paxos）。这正是裸用 Basic Paxos 几乎不可行的现实原因。

ZAB —— ZooKeeper 原子广播

基于领导者，有两种模式：

  • 原子广播（正常运行时）：领导者给每个写入打上单调递增的 zxid，然后用类 2PC 的方式广播——PROPOSE → 多数派 ACK → COMMIT——从而得到严格的写入全序。
  • 崩溃恢复：领导者挂了就重新选一个——zxid 最大的节点胜出（它持有最完整的已提交数据）——把各跟随者同步到它的进度，再恢复广播。zxid 里嵌了一个 epoch（类似 Raft 的任期），这样旧领导者的写入不会和新的混淆。

④ 领导权与恢复每个 term 一个领导者；新领导者 = 日志最新；追赶被揉进普通的 AppendEntries，所以选完主就能立刻对外服务每个 epoch 一个领导者；新领导者 = zxid 最大；先有一个明确的恢复阶段把多数派同步到新主，然后才切到广播、对外服务
那它们到底差在哪？骨架——领导者 + 复制的有序日志 + 多数派提交 + 应用到状态机——是一样的（没错，ZooKeeper 有状态机：就是那棵 znode 树，已提交的 zxid 会按序应用到它上面）。真正不同的只有三点：
  1. Raft 的状态机是通用的；ZAB 则写死成 znode 树。
  2. 选主之后，Raft 立刻就能对外服务、在普通 AppendEntries 过程中顺带把跟随者追平；而 ZAB 把"对外服务"挡在一个明确的"恢复"阶段之后，先把多数派同步到新主——最终结果一样（一个一致的多数派），区别只在"持续地做" vs "作为前置步骤做"。
  3. Raft 把领导任期和日志下标分成两个数；ZAB 把它们合进一个 zxid。
Raft vs Paxos vs ZAB：目标相同——通过多数派 quorum 就一份有序日志达成一致。Paxos 最通用但微妙难懂；Raft 用一点通用性换来可理解性（etcd、Consul）；ZAB 与 Raft 神似，是为 ZooKeeper 的主备复制量身打造的。记得报出：etcd / Consul → Raft，ZooKeeper → ZAB。

05分布式事务

当一个逻辑操作横跨多个服务或数据库时（扣库存且扣款且创建订单），你需要它们要么全部提交、要么全部回滚。本地数据库事务跨不了机器，于是你只能从下面这几种模式里挑一个。

2PC —— 两阶段提交

sequenceDiagram participant Co as 协调者 participant A as 服务 A participant B as 服务 B Co->>A: 阶段一 —— 准备好了吗？ Co->>B: 阶段一 —— 准备好了吗？ A-->>Co: 好的，已就绪（已加锁） B-->>Co: 好的，已就绪（已加锁） Note over Co: 所有人都投了赞成票 Co->>A: 阶段二 —— 提交 Co->>B: 阶段二 —— 提交
2PC 的硬伤：它是同步且阻塞的——参与者在等待阶段二期间一直持有锁；而一旦协调者在「准备」之后挂掉，参与者既不敢擅自提交、也不敢擅自回滚，就会卡死（陷入不确定状态）。它还难以横向扩展。

3PC —— 三阶段提交

3PC 专治 2PC 的阻塞：把"准备"拆成两步，并在两端都加上超时：

sequenceDiagram participant Co as 协调者 participant P as 参与者 Co->>P: 1. CanCommit？（轻量探问，先不加锁） P-->>Co: 行 / 不行 Note over Co: 全部同意 Co->>P: 2. PreCommit（这时才加锁、做准备） P-->>Co: ack Co->>P: 3. DoCommit P-->>Co: 已提交
  1. CanCommit：协调者先问一句"你能提交吗？"——一次不加锁的轻量探问。只要有谁说"不行"，就早早中止。
  2. PreCommit：如果都说行，大家这才真正加锁、写好 undo/redo，然后 ack。到这一步，所有节点都已经知道最终决定是"提交"。
  3. DoCommit：协调者通知大家真正提交。

好处在于超时：一个已经收到 PreCommit、却随后联系不上协调者的参与者，会在超时后径直提交（因为 PreCommit 本就意味着"大家都同意了"）；而还停在 CanCommit/PreCommit 苦等的参与者，则会超时后中止——于是谁都不会无限期卡死。

但 3PC 在网络分区下依然不安全：如果集群在 PreCommit 之后被分开，能联系上的那一侧超时后提交，而一个没收到 PreCommit、被隔离的参与者却中止 → 数据不一致。所以 3PC 是拿 2PC 的"阻塞"换了"小概率不一致"，还多搭进去一轮延迟。实践中两者都用得不多——下面的最终一致性方案才是主流。

实战中常用的模式

模式思路取舍
TCC（Try-Confirm-Cancel，尝试-确认-取消）应用层的 2PC：先预留资源（Try），再 Confirm 或 Cancel掌控力强，但每个动作都要写 3 个方法

TCC —— Try / Confirm / Cancel（尝试 / 确认 / 取消）

业务层的 2PC：每个动作你都要实现三个方法。Try 只预留资源、不最终落定（冻结金额、占住库存）。如果所有 Try 都成功，Confirm 就用预留的那部分真正提交；只要有一个失败，Cancel 就把预留释放掉。Confirm/Cancel 必须幂等，还要处理空回滚（Cancel 比它的 Try 先到）。掌控力强，但代码量是三倍——只留给支付这类高价值流程。

Saga —— 一串本地事务

把全局事务拆成本地步骤 T1…Tn，每一步配一个补偿动作 Ci。正向依次执行；某一步失败了，就反向跑补偿，把已经提交的部分一一回退。跨服务期间不持有锁（可用性高），但你得设计出正确且幂等的补偿逻辑。

两种风格：编排（orchestration）——由一个中心协调者依次调用每一步；或编舞（choreography）——每个服务发出事件，下一个服务监听响应。

本地消息表 / 事务消息表 —— 日常首选

要让"改自己的库并且可靠地通知另一个服务"这件事原子化，靠的就是这个套路：在同一个本地事务里，既写业务数据，也往消息表（outbox）里写一行事件记录。然后一个中继程序不断扫描消息表、投递到 MQ，直到收到确认为止；消费者幂等处理（按消息 id 去重）。这样，消息当且仅当业务数据提交成功才会发出——既不会丢，也不会凭空多发。

直白地说：「强分布式事务（2PC）代价高且会阻塞，所以实践中我们用最终一致性 —— Saga，或者可靠消息（本地消息表 + MQ）配合幂等消费者 —— 只把 TCC 留给少数真正需要接近强一致保证的流程，比如支付。」

06分布式锁

一把能跨机器生效的互斥锁 —— 同一时刻只允许一个节点持有。两种常见的后端实现：

Redis

SET key token NX PX 30000 —— 原子地获取锁 + 自动过期，这样持锁者崩溃也不会死锁。释放时用一段 Lua 做先校验 token 再 DEL，确保你只释放自己的锁。Redlock 把它扩展到 N 个相互独立的 master 上（在「对正确性要求很高」的场景里其安全性仍有争议）。

ZooKeeper

创建一个临时顺序（ephemeral sequential）znode；序号最小的那个持有锁。每个等待者只监听（watch）排在自己前面的那个节点。临时 = 持锁者的会话一断，锁自动释放 —— 不必去猜 TTL 设多少。

Redis 锁ZooKeeper 锁
风格AP —— 快，但故障切换时可能不安全CP —— 安全，略慢一些
过期TTL 需要你自己调（再加看门狗 watchdog）基于会话 / 临时节点，自动处理
适用场景效率锁（避免重复做同一件事）正确性锁（必须严格互斥）

为什么一个只配做"效率锁"、另一个能做"正确性锁"？

Redis 锁有两种方式会破坏互斥：

  1. TTL 到期——如果持有者卡顿（一次 GC 的 stop-the-world、一次慢磁盘）超过了 TTL，这个 key 就自动过期，于是第二个客户端拿到了锁——这下两个一起在跑，而 Redis 和被保护的资源都浑然不觉。
  2. 异步故障转移——如果主节点发出锁之后、还没复制就崩了，被提升的副本根本没有这把锁的记录，于是又有客户端把它锁上。

这对效率锁来说可以忍（最坏不过多干一遍活），但对正确性锁就是致命的（两个写入者 = 数据损坏）。

"效率锁"和"正确性锁"到底差在哪？先厘清一点：锁是一张许可证（"这件事现在归我做"），它本身不是那件活——两种锁的流程都一样：拿锁 → 干活 → 放锁。"效率/正确性"形容的是万一锁没锁住、两个客户端同时持有时会出什么事。效率锁只是为了别重复干活——这件事就算被执行两遍也无害（或本身幂等），两个持有者顶多浪费点 CPU：比如刷新缓存、发日报、处理一个同事已经抢走的任务。正确性锁则是互斥本身就是正确性的前提——两个持有者会写出错误数据：扣余额、转账，或任何非原子的"读-改-写"。所以"可以忍、最坏不过多干一遍"只适用于前一种；对后一种，两个持有者 = 数据损坏。

ZooKeeper 把这些洞堵上了——再加一层兜底，连残留的极端情况也防住：

  1. 会话租约——锁的存活靠客户端持续心跳维持的会话，而不是一个猜出来的 TTL，所以没有"我还在干活、锁却过期了"那段需要费心去调的间隙。（堵住 Redis 的第 ① 个洞。）
  2. 强一致——锁状态由 ZAB 多数派达成一致，故障转移也绝不会忘了谁持有它。（堵住第 ② 个洞。）
  3. 隔离令牌 —— 兜底——连 ZK 自己都拦不住"持有者卡顿超过会话超时"这种极端情况；所以每次发锁都带一个单调递增的令牌，资源端只认见过的最大令牌、拒绝更小的——"僵尸"旧持有者根本写不进去。详见下方。

ZooKeeper 锁到底是怎么跑的

先说会话（session）：客户端一连上来，ZooKeeper 就为它开一个带超时的会话，靠客户端定期发心跳维持。心跳断够久了（崩溃、长时间卡顿、网断了），ZK 就判定会话死亡，并自动删掉这个会话创建的所有临时节点。这就是那张"存活租约"——没有需要你去猜的锁 TTL。

锁是用临时顺序（ephemeral sequential）节点排出来的一个队列。每个想拿锁的客户端，都在 /lock/ 下建一个子节点，ZK 给它打上一个递增的编号。编号最小的那个持有锁。关键在于：等待者只监听排在它前面的那一个节点——不监听持有者，也不监听所有人：

当持有者干完活（删掉自己的节点）或者挂掉（会话结束 → 节点被自动删除）时，只有它的紧邻后继者的监听会被触发；那个客户端检查一下"我现在是不是最小了？"，是就拿锁。客户端之间从不直接通信——它们全程通过 ZK 的共享树来协调，而且各自只盯着一个邻居，所以一次释放只唤醒一个等待者（不会惊群）。这就是为什么不存在"两个持有者"的窗口：锁永远归编号最小的那个活着的节点，而"活着"由会话说了算，不是你拍脑袋定的定时器。

看清这是哪一层。这张图是一个搭在 ZooKeeper 之上的锁配方——你建/删的这些 znode，都是在对 ZK 的状态机（znode 树）做写入，watch 则是它的变更通知。它不是 §04 里的 ZAB 共识协议——该对标的是"用 Redis 搭的锁"，而不是 Raft 的内部实现。这也正是它和 §04 共识图长得完全不一样的原因：Raft 那张画的是复制层（状态机是画面外、被 apply 进去的一个盒子），而这里你看到的是"ZooKeeper 的状态机正被直接使用"。底下都是同样的四层——只是图画的是不同层而已。

隔离令牌（fencing token）—— 真正安全的兜底

即便是 ZooKeeper，也拦不住一个卡顿到超过会话超时的进程：ZK 把锁放了、下一个客户端拿到了锁，而那个卡住的客户端醒来后仍以为自己还握着锁。真正的修法在资源端，而不在锁本身——每次发锁都附带一个隔离令牌，一个只增不减的数字（ZK 节点的序号/版本号就能用）。每次写入都带上自己的令牌，资源端记住见过的最大令牌，并拒绝任何更小的：

sequenceDiagram participant C1 as 客户端 1 participant L as 锁服务 participant C2 as 客户端 2 participant R as 资源（数据库） C1->>L: 请求锁 L-->>C1: 授予，令牌 33 Note over C1: 长时间 GC 停顿，会话过期，锁被释放 C2->>L: 请求锁 L-->>C2: 授予，令牌 34 C2->>R: 写入（令牌 34） Note over R: 见过的最大令牌 = 34 C1->>R: 写入（令牌 33）—— 醒得太晚 R-->>C1: 拒绝，33 小于 34

于是那个"僵尸"旧持有者就无害了——它那张过期的令牌会被拒掉。这正是为什么真正安全的答案是"CP 锁外加一个由资源端校验的隔离令牌"，而不是只靠锁本身。

那句经典论断（出自 Kleppmann 对 Redlock 的批评）：对于效率锁，单机 Redis 的 SET NX PX 就够了；但对于正确性锁，你需要一个隔离令牌（fencing token，由资源端校验的单调递增数字），或者像 ZooKeeper / etcd 这样的 CP 系统 —— 因为 GC 停顿和时钟偏移可能让两个客户端都以为自己持有锁。

07分布式 ID

一旦数据被分片，单库自增主键就不再奏效了 —— 你需要全局唯一的 ID，最好还能大致按时间有序（这样索引友好、也能按创建时间排序）。四种标准做法：

做法怎么做坑在哪
UUID128 位随机数，任何地方都能生成唯一但无序且占用空间大 → 对 B+ 树索引的局部性不友好
数据库号段（segment）用一张表给每个应用分发一段区间（如 1–1000），之后在本地发号很少访问数据库、大致有序；但依赖数据库可用
Redis INCR原子计数器，还可按前缀分别计数简单且有序；但 Redis 变成依赖 / 单点故障（SPOF）
Snowflake64 位：时间 + 机器 + 序列号，在本地生成有序且无需中心调用；但要求机器 ID 唯一、时钟正常

Snowflake —— 64 位的位布局

1 位 符号位（恒为 0）   ·   41 位 时间戳（毫秒，约 69 年）   ·   10 位 机器 ID（1024 个节点）   ·   12 位 序列号（每毫秒每节点 4096 个）
Snowflake 的软肋是时钟：如果一台机器的时钟往回跳（NTP 校正），它就可能生成重复的 ID。各种实现要么在时间追上来之前拒绝发号，要么借用某些位 —— 一定要提到对时钟漂移的处理。
按需求选型：有序 + 去中心化 → Snowflake；最省事且手头已有数据库 → 号段；规模很小 → Redis INCR；只要唯一、不要有序 → UUID。

真正重要的几块拼图：序列化格式（Protobuf、Thrift、JSON）、传输（gRPC 用 HTTP/2，或 TCP）、服务发现（找到一个实例）和负载均衡。代表：gRPC、Apache Dubbo、Thrift。

RPC vs REST：RPC 面向动作（「调用这个方法」，二进制、快、强类型契约）—— 非常适合内部服务间调用。REST 面向资源（在 URL 上用 HTTP 动词，可读性好）—— 非常适合对外 / 跨团队的 API。另外记住分布式计算的若干谬误：网络并不可靠、免费或零延迟，所以每一次 RPC 都需要超时、重试（务必幂等！）和熔断器。

10ZooKeeper 与服务发现

ZooKeeper 是一个 CP 协调服务：一棵小巧、强一致、可复制的 znode 树（很像文件系统），由众多客户端共享。它是其他分布式系统所依赖的「单一可信来源」。

znode 类型

持久（persistent）节点（删除前一直存在）、临时（ephemeral）节点（创建者会话结束就消失 —— 用来判活再合适不过）、以及顺序（sequential）节点（自动追加一个递增计数器 —— 非常适合有序的锁 / 队列）。

监听（Watch）

客户端可以监听一个 znode，在它发生变化时收到一次性通知 —— 这是配置更新、领导者选举和锁交接的基础。

人们用它来搭什么

  • 服务发现 —— 服务以临时 znode 的形式注册；某个实例挂掉，它的节点随之消失，客户端立刻被通知。
  • 配置管理 —— 把共享配置存进 znode；监听者能实时收到更新。
  • 领导者选举与分布式锁 —— 通过临时顺序节点实现（见 §06）。
服务发现里的 ZooKeeper（CP）vs Eureka（AP）：ZooKeeper 保证一致性，但分区时可能会拒绝服务；Eureka 保持可用，可能返回一份略微陈旧的服务列表。对于服务发现，很多人认为 AP 更合适 —— 一份稍旧的列表也好过没有列表。etcd（基于 Raft）和 Consul 是更现代的替代方案。

11速答速查表

CAP / BASE

P 是必选 → 分区时选 CP（拒绝请求，保持正确）或 AP（照常服务，保持在线）。BASE = AP 一侧的哲学：基本可用、软状态、最终一致。与 ACID 相对。

共识

通过多数派 quorum 就一份复制日志达成一致 → 节点数取奇数。Raft（etcd、Consul）、Paxos（通用、难懂）、ZAB（ZooKeeper）。

事务

2PC = 阻塞、同步。实践中 = Saga / 本地消息表 + MQ（最终一致、幂等），TCC 用于需要接近强一致的流程。

锁

Redis SET NX PX + Lua 释放（AP，效率锁）。ZooKeeper 临时顺序节点（CP，正确性锁）。要正确性 → 隔离令牌（fencing token）。

ID

有序 + 去中心化 → Snowflake（时间+机器+序列号，留意时钟偏移）。否则用号段 / Redis INCR / UUID（无序）。

限流

固定窗口 → 滑动窗口 → 漏桶 → 令牌桶（允许突发）。分布式 → Redis + Lua。

RPC

存根 + 序列化 + 传输 + 服务发现。永远记得：超时、幂等重试、熔断器。

13Boss 级问题 专家

这些问题能把「我用过」和「我真懂」区分开来。先自己想，再揭晓答案。

CAP 里的「C」和 ACID 里的「C」是一回事吗？ 中等
不是 —— 常见陷阱。CAP 的 C 指线性一致性（跨副本，每次读都能看到最新的写）。ACID 的 C 指一致性意义上的「保持不变量 / 约束」（事务内任何违反规则的写都会被拒绝）。两者只是共用了一个字母，概念完全不同。
你需要一笔取款在多个数据中心间全局互斥。用不用 Redis 锁？ 困难
这是一把正确性锁，所以单实例 Redis 的 SET NX PX 是不安全的：GC 停顿或时钟偏移可能让第二个客户端拿到锁，而第一个还以为自己持有。可选方案：
  1. 用带临时节点的 CP 协调者（ZooKeeper / etcd）。
  2. 用隔离令牌（fencing token） —— 锁发放一个单调递增的数字，资源端（数据库）拒绝任何携带过期令牌的写，这样「僵尸」持锁者就无法造成破坏。
仅靠 Redlock 解决不了 GC 停顿这个问题。
怎样让一条「可靠消息」在多个服务间做到恰好一次（exactly-once）？ 困难
真正的「恰好一次」投递是做不到的 —— 目标应是至少一次 + 幂等。用本地消息表 / 事务消息表（transactional outbox）：在一个本地数据库事务里，同时写入业务变更和一行 outbox 记录；由一个中继可靠地把 outbox 记录投递到 MQ（失败重试）。消费者按唯一的消息 ID（幂等键）去重。最终效果 = 实际上的恰好一次（effectively-once）。
为什么共识集群总是希望节点数为奇数？ 热身
推进需要多数派（quorum）。2N+1 个节点可以容忍 N 个故障；从 3 个加到 4 个，仍然只能容忍 1 个故障，却让多数派更难凑齐、也更容易出现平票。奇数能让「每个节点带来的容错能力」最大化，并避免选票僵局。
一个节点短暂分区后又重新加入。Raft 如何避免两个领导者把日志搞乱？ 中等
每个领导者只服务于一个任期；被分区的旧领导者无法凑齐多数派来提交新条目，所以它什么都提交不了。当它重新加入、看到一个更高的任期时，便退回为跟随者，它那些未提交的条目会被当前领导者的日志覆盖。多数派提交 + 任期编号，让陈旧的写入不可能生效。
